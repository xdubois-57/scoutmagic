# Architecture

This document is the architectural reference for the project. Every contribution — human or agent-generated — must conform to it. When in doubt between a "simpler" solution and one that respects this document, this document takes priority.

## 1. Overview

### Purpose

Open-source PHP website for Belgian scout units ("Les Scouts" federation). Same codebase reusable across units — all unit-specific data is configurable, never hardcoded. Deployable via FTP on shared hosting with a MySQL database.

### Dependencies

Only a small, explicitly justified set of external dependencies is allowed:

| Dependency | Justification |
|---|---|
| Twig | Auto-escaping prevents XSS across all templates; reimplementing a secure template engine with inheritance and contextual escaping is too large and too risky. |
| Bootstrap 5 | Mobile-first responsive grid, forms, navigation, and table components; compiled CSS+JS files only — no Sass, no webpack, no npm on the server. |
| PHPMailer | SMTP authentication, STARTTLS, and DKIM signing; reimplementing email delivery correctly is a project in itself with real deliverability risks. |
| smalot/pdfparser | Extracts a PDF's embedded text layer (`Core\File\PdfTextExtractor`) — parsing PDF's internal object/stream structure correctly (compression filters, font encodings, cross-reference tables) is not something worth hand-rolling for one feature (Modules\Finance\Task\ExtractReceiptDataHandler: reading a receipt/invoice PDF's real text is exact and provider-agnostic, versus sending the file to a vision model and hoping it's supported/accurate). |
| dompdf/dompdf | Renders HTML+CSS to PDF for printable A4 posters (`Core\Pdf\PosterPdfService`); pure PHP, no system binaries required on shared hosting. |
| endroid/qr-code | Generates QR code images (PNG/SVG) server-side for posters and SEPA payment codes; pure PHP, no external API call. |
| phpoffice/phpspreadsheet | Reads and writes XLSX files with formula and style support; needed for form response export (`Modules\News`) and future financial spreadsheet imports. |
| aws/aws-sdk-php | S3-compatible object storage backend for the gallery module (`Modules\Gallery\Service\Storage\S3StorageBackend`) — correctly implementing multipart upload, presigned URLs, and provider-specific auth quirks (AWS S3, and S3-compatible providers) by hand is not worth it for one storage backend among several. |
| minishlink/web-push | Web Push (RFC 8030/8291) sending for `Core\Notification\NotificationService`: VAPID ES256 JWT signing, ECDH key agreement, and the RFC 8291 `aes128gcm` payload encryption. Reimplementing this elliptic-curve crypto by hand is real security-sensitive surface area (a subtly wrong HKDF/AEAD derivation silently breaks or, worse, weakens delivery) for a well-defined, narrow protocol a maintained library already gets right. |
| webklex/php-imap | Pure-PHP IMAP client over sockets (`Modules\InboundMail\Client\ImapMailboxClient`, §7 of the inbound-mail spec). **`ext-imap` was removed from PHP's core in 8.4 and moved to PECL**, which puts it out of reach of essentially every shared host ScoutMagic targets — so an extension-free implementation is not a preference, it is the only option. Hand-rolling one would mean implementing IMAP4rev1 command pipelining, literal handling, UIDVALIDITY semantics, MIME structure parsing and TLS negotiation correctly, on a protocol where a mistake either loses somebody's mail or writes to their mailbox. Its Laravel-adjacent transitive dependencies (`illuminate/support`, `nesbot/carbon`, `symfony/http-foundation`) are the real cost of this entry and are the reason it is worth stating: they are pulled in for `Collection` and date handling only, no framework is bootstrapped, and nothing outside this module's `Client/` directory references them. |
| ifsnop/mysqldump-php | Pure-PHP `mysqldump` reimplementation (`Core\Database\DatabaseDumper`, §8.15.1) that dumps over a PDO connection it opens itself — no `mysqldump` binary, no shell-execution function, and none of the shared-hosting failure modes (missing `$PATH`, `disable_functions`, a `libmysqlclient` build that can't load the `mysql_native_password` auth plugin) a shelled-out dump used to hit. |

Everything else is written in-house. Composer is used for autoloading and dependency resolution during CI build — `vendor/` is built by CI and deployed via FTP; Composer is never required on the hosting server.

No frontend build tools for production (Sass, webpack, an application bundler, a transpiler). Bootstrap is loaded from compiled files (CDN or `public/assets/vendor/bootstrap/` fallback). npm/Node are used, strictly as development/test tooling, to run the two Node-based test stacks (§15): Vitest unit tests against first-party browser JavaScript, and Playwright end-to-end tests driving a headless Chromium against the real application. A browser automation runtime is test infrastructure, not frontend architecture — Playwright drives the site the way a visitor's browser does and compiles, bundles, or transpiles nothing. None of it is ever a runtime or build requirement for a deployed ScoutMagic installation, and no build step is required to run, deploy, or serve `public/assets/js/`.

## 2. Layered MVC architecture

Every request traverses the same layers in the same order:

```
Front controller (public/index.php)
      │
      ▼
Router                         → resolves route from path
      │
      ▼
RBAC guard                     → checks role BEFORE instantiating the controller
      │
      ▼
Controller                     → orchestrates, contains no business logic
      │
      ▼
Service                        → module business logic
      │
      ▼
Repository                     → database access (PDO, prepared statements only)
      │
      ▼
View (Twig)                    → rendering, automatic escaping
```

**Absolute rule**: the RBAC guard is never called manually from a controller. It is invoked systematically by the Router for every route, before executing anything. A controller may re-check a fine-grained permission inside an action (e.g. "can this member edit this specific activity"), but this is never the primary protection — route access itself is always filtered upstream.

## 3. Roles and menus

Three-level system: **function** (configurable per unit, e.g. "Animateur Baladins", "Trésorier") → **role** (fixed, hierarchical) → **menu**.

| Role | Level | UI label | Associated menu (minimum) |
|---|---|---|---|
| `public` | 0 | — | Notre unité |
| `identified` | 1 | — | Espace animés |
| `intendant` | 2 | Intendant | Partial Espace chefs |
| `chief` | 3 | Chef | Full Espace chefs |
| `admin` | 4 | Chef d'Unité | + Espace chefs d'U |
| `superadmin` | 5 | — (top site administrator) | + Configuration |

Hierarchy is **cumulative**: a role at level N sees all menus at level ≤ N. `admin` and `superadmin` are both defined in `Core\Security\Role` (`level()`) — `admin` is displayed as "Chef d'Unité" in the UI (e.g. Config Desk's function role picker), never as "Admin"; `superadmin` has no distinct UI label beyond gating the Configuration menu. A route may set a `role_min` stricter than its menu's own minimum but never more permissive — one core exception is documented at §8.15 (the Maintenance page sits in the `superadmin`-gated Configuration menu but its own routes are `role_min: admin`, a deliberate spec choice, not a module-manifest-validated route so the usual stricter-only rule doesn't apply).

Functions themselves (name, associated role) are managed via a core page (`Configuration > Config Desk`), not via a module. The same page also manages section name/visibility (see §8.8).

Routes within "Espace chefs" declare `role_min: "intendant"` or `role_min: "chief"` individually — the menu appears for intendants but with filtered content.

## 4. Identity model

### Email → members → role

A person logs in with an email address, not with a member account.

- `user_accounts` contains only an email (unique) + optional info (name, surname).
- At login, the system finds all `member_years` for the current scout year whose email matches.
- Effective role = the **highest** among the functions of all linked members.
- The person can then navigate between "their" members (e.g. a parent sees the page of each of their children).

### Display name convention

Everywhere on the site: `totem ?? first_name`. A global Twig helper (`{{ member|display_name }}`) applies this rule once.

The groups module names people one level up from this, because a message has an *author* and an author is a human rather than a membership: it writes the account first, then the memberships that account carries, in parentheses — `Marie Dupont (Akéla, Baloo)`. Each name inside those parentheses is still this rule, unchanged, applied by the same helper. See §8.40.

### Scout year

A scout year runs from September to August (e.g. 2025-2026). All member-related tables carry a `scout_year_id`. History is preserved across years — the `members` table holds the persistent identity (`desk_id`), while `member_years` holds the annual snapshot.

## 5. Authentication

Three methods, all resolving to the same email address:

| Method | Fields required | Requires prior setup |
|---|---|---|
| Magic link (default) | Email only | No |
| Password | Email + password | Yes (set in "Mon compte") |
| Passkey (WebAuthn) | None (discoverable) | Yes (registered in "Mon compte") |

Magic link is always available as a fallback. Password and passkey methods can be enabled/disabled site-wide via settings.

Magic link tokens: cryptographically random, single-use, 15-minute expiry, stored hashed in database. The login page polls (or uses SSE) for confirmation — the link can be clicked on a different device.

### Login security

- Identical error message for "unknown email" and "wrong password" (no account enumeration).
- Progressive lockout on failed attempts.
- Session ID regenerated at login.
- Cookies: `HttpOnly`, `Secure`, `SameSite`.

## 6. Cookie consent

### 6.1 Consent model

The site categorizes cookies into:

| Category | Consent required | Examples |
|---|---|---|
| Strictly necessary | No (always active) | Session cookie, CSRF token, cookie consent choice |
| Functional | Yes | Configuration mode preference, last selected section |
| Analytics | Yes | Usage statistics (if a module adds this) |

Modules can register additional cookie categories via their `module.json`.

### 6.2 Consent banner

Displayed on first visit (no cookie consent choice stored yet). Offers: "Accepter tout", "Refuser tout", "Personnaliser". Choice stored in a strictly-necessary cookie (`cookie_consent`, JSON, 13-month expiry per ePrivacy directive).

### 6.3 Cookie preferences page

Accessible from:
- The consent banner ("Personnaliser" button).
- The RGPD public page (link).
- The "Mon compte" page (for identified users).

Displays each cookie category with description and toggle. Strictly necessary category shown but not toggleable (always on, explained).

### 6.4 Enforcement

Before setting any non-essential cookie, code must check consent via `CookieConsentService::isAllowed($category)`. Modules that add cookies must declare them in their `module.json` with category, name, purpose, and duration.

## 7. Module system

### Structure

```
modules/
  <module_name>/
    module.json      Manifest (see §7.1)
    schema.sql       Complete current schema for this module's tables
    src/
      Controller/
      Service/
      Repository/
    views/           Twig templates namespaced (@<module_name>/...)
```

### 7.1 Module manifest (`module.json`)

```json
{
  "id": "calendar",
  "name": "Calendrier des activités",
  "version": "1.2.0",
  "routes": [
    {
      "path": "/calendar",
      "controller": "Modules\\Calendar\\Controller\\CalendarController",
      "action": "index",
      "menu": "espace_animes",
      "role_min": "identified"
    }
  ],
  "settings": [...],
  "storage": {...},
  "scheduled_tasks": [...],
  "cookies": [
    {
      "name": "calendar_view",
      "category": "functional",
      "purpose": "Mémorise le type d'affichage choisi (mois/semaine)",
      "duration": "1 an"
    }
  ]
}
```

Validation rules enforced by `ModuleManager` at load time:
- `role_min` is **mandatory** on every route. A route without `role_min` is rejected (fail-safe: no access by default).
- `menu` must be one of: `notre_unite`, `espace_animes`, `espace_chefs`, `espace_admin`, `configuration`.
- A route may require a stricter role than its menu's minimum, never more permissive.
- A route's optional `menu_order` (int, default 100) controls where its menu entry sorts *relative to other module pages in the same menu* — lower sorts earlier. **It never reaches outside the module group.** `Core\View\MenuBuilder::buildPages()` sorts every menu by entry type first — dynamic entries (e.g. `espace_animes`'s per-member pages), then core static pages, then module pages, always in that order — and only falls back to `menu_order` to break ties *within* whichever group an entry belongs to. A module page can no longer place itself ahead of a dynamic entry or a core page by declaring a low `menu_order`, however low — this is a deliberate semantic change from an earlier version of this rule (a module page setting e.g. `menu_order: 5` used to land before per-member entries or core pages that used a higher numeric order; that was a real, exploitable-by-accident footgun — two modules did exactly this — not just a theoretical one). A module author who wants to sort ahead of *other modules* in the same menu still uses a lower `menu_order`; sorting ahead of core/dynamic entries is no longer possible at all. The sort is stable (PHP's `usort()` since 8.0), so two entries with the same group and the same `menu_order` keep their registration order.
- Modules can be reordered on the general configuration page (`/config/modules`, superadmin — drag-and-drop, or up/down arrows on mobile, same list component as the banner list). This persists to `module_registry.sort_order` and determines both that page's own listing order and, for routes left at the default `menu_order`, a base offset (`1000 * module position`) added on top — so those pages sort by module order relative to each other; per the paragraph above, this offset only ever matters within the module group, never against core or dynamic entries.
- A module's optional top-level `requires` (array of module ids, default empty) declares **hard dependencies**: modules it cannot function without. `ModuleManifest::fromArray()` rejects a non-array, an empty or non-string element, a duplicate, or a self-reference. `ModuleManager` resolves it against the whole discovered module set — order-independent, no extra query — and a module is loaded or activated only when every required module is present on disk, free of validation errors, and enabled, recursively (an unsatisfied dependency satisfies nobody; every module in a dependency cycle is unsatisfiable). An unsatisfied module is simply not loaded (no routes, settings, menu entries or task handlers; journaled as `module_requirements_unmet`), never a fatal error and never a half-loaded module — so a dependency deleted from disk degrades its dependent to "not loaded" on the next request while the site keeps working. `activate()` refuses before migrating the module's schema; `deactivate()` refuses while an enabled module still requires it. A dependency is never auto-enabled and a deactivation is never cascaded — both stay the admin's explicit decision on `/config/modules`, which shows each module's dependencies by name and disables the toggle while they are unmet. This is distinct from §7.5's optional module-to-module dependency, which stays as it is: `requires` is for the case where there is nothing to degrade to. It lives in the manifest only — no registry column.
- A module's optional top-level `enabled_by_default` (bool, default false) auto-activates it the very first time it is discovered on disk (no `module_registry` row yet). An admin's later explicit deactivation always sticks.
- A module's optional top-level `receiver_only` (bool, default false) marks a module that only makes sense on the installation receiving usage statistics (§8.49). `ModuleManager` takes an already-resolved `$isStatisticsReceiver` boolean and filters such a manifest out of `discoverModules()` everywhere else — one filtering point, so routes, menus, the registry page and the scheduler all follow. Strictly typed: a non-boolean value is a load-time error, because a truthy `"false"` would hide the module on every installation and the symptom (a module that silently does not exist) is close to undebuggable. This is an ergonomic mask, **not** a security boundary — the real protection is that an unloaded module has no routes.
- A disabled module: all routes return 404, menu entries disappear, but data and schema remain.
- No route may be unconditionally shadowed by an earlier one in the same module (`ModuleManifest::validateNoShadowedRoutes()`) — `Core\Http\Router::resolve()` matches in registration order and stops at the first pattern match, so a `{param}` segment happily matches a literal word too. An earlier route whose pattern fully subsumes a later one (same HTTP method, same segment count, a wildcard everywhere the later route has a fixed word) makes the later route unreachable — real incident: `/inscriptions/suivi/{id}/{token}` declared before `/inscriptions/suivi/demande/{id}` swallowed every "Espace animés" link to a family's own pending request as `id="demande", token="<the real id>"`, `(int) "demande"` casting to 0, a plain 404 with no clue why. Only this always-triggered direction is rejected — the reverse (a literal action route declared before a `{id}` catch-all, e.g. `/news/manage` before `/news/{id}`) is the standard, safe way to keep a literal action from being swallowed as an id, and a *coincidental* overlap that only collides for one specific contrived wildcard value (e.g. a numeric `{id}` that would have to literally equal another route's fixed word) is deliberately not flagged, since reordering can't remove that kind of overlap anyway — it only swaps which route it would hit.

### 7.2 Module registry

```
module_registry: id, module_id (unique string), enabled, installed_version, enabled_at, enabled_by
```

### 7.3 Module lifecycle

Activation: run schema migration → create default settings → register routes → log activation.
Deactivation: unregister routes → log deactivation. **Never** touch tables or settings — data stays intact.

### 7.4 Core hooks for module-provided configuration

A module that needs to extend a *core* configuration page (e.g. attach flags to a core entity) must not be depended on by core code directly. Instead, core defines a small interface (e.g. `Core\Module\FunctionFlagsProvider`, used by the Config Desk page to let a module declare a per-function flag without the core page hardcoding any module or function name), the module implements it, and the composition root (`public/index.php`) wires the concrete implementation into the core controller only when that module is enabled. Same precedent as `Core\Scheduler\TaskHandlerInterface`. `Core\Module\MenuEntryProvider` is the same pattern applied to the **menus** themselves rather than to a controller: the module's hook implementation contributes extra entries alongside the core-built ones.

`MenuEntryProvider::getMenuEntries(?string $email)` returns `Core\Module\MenuEntry` value objects, each carrying its own target menu id, `roleMin`, sort `order`, `group` and `isDynamic` flag. Both of those parameters are deliberate generalisations of the earlier, narrower `EspaceAnimesEntryProvider` this replaced (which took a non-nullable email and could only ever reach `espace_animes`): the menu id moved into the entry so a provider can target *any* menu, and the email became nullable so a provider can contribute **public** entries for an anonymous visitor — a module page in `notre_unite` is not expressible otherwise.

Because `MenuBuilder::build()` — and the per-request active-menu highlight — must run before module services are wired later in `public/index.php`, the composition root calls back into the builder from inside the module's own conditional block and re-derives `$menus`/`active_menu_id`/`active_page_url` from the updated list; `MenuBuilder::build()` itself is a pure read of its internal page list, so calling it twice is safe. `Core\View\DynamicMenuRegistrar` encapsulates exactly that two-step: `register()` applies a list of providers to the builder and returns what it added, `resolveActive()` re-runs the active-page scan over just those entries, carrying the first scan's best match forward. Use it rather than hand-writing the re-derivation per module — a copy that silently drops the highlight refresh yields a correct page with no nav highlight, a bug no route test would catch.

**A menu entry is never a permission.** `MenuEntry::$roleMin` filters *display* only; the route it points at carries its own `role_min`, and any per-object rule is re-checked server-side in the controller (§12).

### 7.5 Core optionally consuming a module's public API

The reverse direction: a module that offers a capability other code may want to *use* (not extend) publishes a stable public interface under its own `Api` namespace (e.g. `Modules\LlmConnector\Api\LlmConnectorInterface`) rather than core defining the interface. Code that wants to use the capability declares a nullable constructor dependency on that interface and must degrade gracefully (feature simply unavailable) when it is `null`. The composition root (`public/index.php`) instantiates the module's concrete implementation and injects it only when the providing module is enabled in `ModuleManager::getEnabledModuleIds()`; the consumer never references the module's classes when it is disabled. Two examples in the codebase: `Core\View\RgpdContentService` (core consuming `llm_connector`, to generate RGPD text) and `Modules\Finance\Service\ReceiptExtractionService` (one module consuming another, to suggest a receipt's amount/date/merchant) — the pattern is identical either way, since a *module* consuming another module's API optionally is the same shape as core doing it.

**One wiring wrinkle worth knowing about**, visible in `Modules\Groups\Service\PostEventService` (groups optionally consuming `Modules\Calendar\Api\CalendarEventLookupInterface`, to let a post name the event it is about): `public/index.php` is a straight-line script, and the calendar's own lookup is only assembled in a *second* calendar block near the end of the file, after `retro` (calendar's `CalendarService` takes retro's link lookup, and retro's block runs after groups'). Groups' block therefore registers its controllers once without the event service, and that final calendar block re-registers exactly two of them — `GroupController` and `PostController` — with it, the same re-registration precedent `PageController` already follows for the homepage hooks (§7.4). Nothing else changes: with `calendar` disabled the second registration never happens, the first one stands, and every affected surface degrades to "no event" — a post keeps a `calendar_event_id` that resolves to nothing, and the composer does not offer the picker at all. `modules/groups/schema.sql` deliberately puts **no foreign key** on that column for exactly this reason.

### 7.6 A module extended by another module

The third direction, and the one §7.4 and §7.5 between them do not cover: not core extended by a module, and not one module *using* another's capability, but a module whose own output another module **contributes to**. `calendar` renders a calendar; `rental` has occupancy that belongs on it. Neither owns the other's data, and the calendar must keep working with `rental` disabled exactly as `rental` must keep working with `calendar` disabled.

The pattern is a **mutable registry**, owned by the extended module, published under its `Api` namespace alongside the interface providers implement:

- The extended module (`calendar`) defines the contribution interface (`Modules\Calendar\Api\VirtualEventProviderInterface`), the value object it returns (`Api\VirtualEvent`), and the resolved-viewer object it is handed (`Api\VirtualEventViewer`). None of these ever names a contributing module — if they did, disabling the contributor would break the extended module at autoload time rather than merely leaving it with one fewer source.
- The extended module also owns the registry (`Service\VirtualEventRegistry`) and hands **the object, not a snapshot of its contents**, to its own controllers.
- The composition root creates the registry inside the extended module's block, and the contributing module's block — which runs later in the straight-line script — appends its provider to that same object. A provider registered after the controllers were constructed still reaches them.

That ordering is what breaks what would otherwise be a construction cycle. Both halves are guarded the way §7.5 guards every optional dependency: the registry variable is seeded `null` before the extended module's block, so the contributor's block guards on `!== null` rather than assuming it exists, and the contributor's own consumption of the extended module (here, `rental` borrowing `CalendarService` and `IcsBuilder`) goes through the same null-seeded `…ForOthers` handles every other cross-module dependency uses.

**Three rules a contribution interface should impose, and this one does:**

1. **One call per window, never one per entity or per day.** A month view carries dozens of bars and a feed hundreds; a provider is asked once for a date range and answers with everything in it.
2. **Rights are resolved once per generation**, at the top of the provider, and handed in as a single resolved viewer object rather than re-derived per item.
3. **Build only what the viewer may see.** The privacy decision belongs *before* serialisation, in separate builders rather than one builder with a flag — a field that is never constructed cannot leak through a template, a JSON payload, a tooltip or an ICS line.

`VirtualEventRegistry::collect()` swallows a provider's exception rather than propagating it: one contributing module in trouble must not take the calendar down. It also deduplicates by UID, so the same underlying thing reaching a reader through two subscribed calendars is one event rather than two — which is only possible because the contract requires a **stable, provider-owned UID** rather than a generated one.

## 8. Core services

### 8.1 Desk CSV import

- Lines grouped by `desk_id`.
- Raw values resolved via mapping tables (functions, branches, tariffs, sections).
- New functions default to lowest role — require admin confirmation.
- CSV deleted immediately after import.
- Import journaled (metadata only).

**`scout_year_offset` survives the year boundary** (`MemberYearRepository::inheritedScoutYearOffset()`). It is the one `member_years` column Desk knows nothing about — ScoutMagic-local, set by a chief on the member page for someone who skipped or repeated a year (§8.26, `MemberYearService::getEffectiveAge()`). The import's INSERT never listed it, so every newly imported scout year silently reset it to the schema default `0`, and an advanced or held-back member's branch and year-in-branch quietly became wrong the moment their new year was imported — on the member page, in `member_stats`, in the registration module's capacity projections, and most starkly on Prévisions (§8.38), where a member Desk had just placed in Éclaireurs was still ranked by a Louveteaux-era effective age. A brand-new row now inherits the offset from the member's most recent **earlier** scout year, ordered by `scout_years.start_date` — never by row id or scout year id, neither of which stays chronological once a past year is back-filled. Deliberately on INSERT only: the UPDATE branch never touches the column, so a chief's correction to an existing row always survives a re-import of that same year. Note this repairs the mechanism, not history: rows already flattened to `0` by a past import keep that value until a chief sets them again.

### 8.2 Editable content system (configuration mode)

- Session-only flag, admin role re-verified server-side on every save.
- Rich text sanitized with HTML tag whitelist before storage.
- Images: MIME validated, EXIF stripped, filename randomized.

### 8.3 File access guard

All files outside `public/assets/` stored under `storage/` (outside webroot). Every file access through `/files/{id}`. No exceptions.

`Core\File\FileAccessGuard` additionally supports owner-scoping, generic to any file (not just one feature): `files.owner_member_id` is a nullable FK to `members.id` (persistent identity, not `member_years.id` — ownership outlives a single scout year); when set, `FileAccessGuard::check()` requires the requesting session's linked member ids (resolved via blind-index email match, same rule as `MemberService::canAccess()`) to include it, on top of the usual `role_min` floor. Deliberately no chief/admin bypass — a higher `role_min` never substitutes for being the actual owner, so an owner-scoped file stays inaccessible to staff who aren't themselves linked to that member. **One exception, added deliberately**: the temporary member override (§8.42) enters through `MemberService::getLinkedMembers()`, which is where `$linkedMemberIds` comes from, so an admin holding an active override reads that member's owner-scoped files. It is still not a role bypass — an admin without an override is refused exactly as before — but it is a way for staff to reach these files, and SECURITY.md § Temporary member addition records it as accepted risk. First consumer: member-page private documents (§8.22). `FileController::serve()` journals every successful access to an owner-scoped file (`owner_scoped_file_accessed`, level `info`, `file_id`/`owner_member_id` only — never personal data) — deliberately only owner-scoped ones, so ordinary `/files/{id}` traffic (public assets, other role-gated content) stays unlogged noise-free; denied access to any file (owner-scoped or not) was already journaled as `file_access_denied`.

Alongside that one special case, the guard carries a **generic ownership registry**: `files.owner_type` (a string naming the kind of owner) plus `files.owner_id` (the owning row's id), resolved through `Core\File\FileOwnershipCheckerInterface`. A feature that needs finer-grained access than a flat `role_min` floor stores those two columns on its file (`FileRepository::create()`'s last two parameters) and registers one implementation of that interface; `FileAccessGuard::check()` then consults it after the `role_min` check. Properties that are not negotiable:

- **Fail-closed.** `isAllowedByRegistry()` returns `false` when no registered checker claims the file's `owner_type` — a file whose checker is missing (module disabled, uninstalled, never wired) is denied, never allowed by default. Same posture as RBAC's own "no `role_min` = no access".
- **No chief/admin bypass**, exactly like `owner_member_id` above: a higher `role_min` never substitutes for satisfying the checker. Individual checkers may of course choose to grant staff themselves (`Core\Member\SectionDocumentOwnershipChecker` does), but that is the checker's own rule, not the guard's.
- **A checker can only narrow**, never widen: the `role_min` floor is checked first and independently, so a checker returning `true` cannot hand out a file the requester's role wouldn't already have reached.
- **`owner_type` values must be unique across checkers.** `isAllowedByRegistry()` returns on the first checker whose `supports()` is true, so two checkers claiming the same value would make access depend on registration order. Prefix a module's own values with its module id to keep them distinct.
- **Module-provided checkers are wired in the composition root only when the module is enabled** (§7.4's precedent). `public/index.php` seeds `$fileOwnershipCheckers` with core's own checker where its dependencies exist, each enabled module appends its own inside its `getEnabledModuleIds()` block, and `new FileAccessGuard(...)` runs only after every one of those blocks — the guard is immutable (no setter, no `addOwnershipChecker()`), so its registry has to be complete before construction. `FileController` is its only consumer, which is what makes constructing it that late possible. `tests/Core/File/FileOwnershipCheckerWiringTest.php` pins that order: moving the construction back up would silently drop every module checker, fail-closed and invisible to behavioural tests.

A checker is a pure decision function — it never writes to the journal and never receives personal data. `FileController::serve()` already journals denials (`file_access_denied`) and owner-scoped accesses.

### 8.4 Settings system

Generic key-value with type, label, description (NOT NULL), optional regex validation. Grouped by module. Editable via dialog.

### 8.5 Scheduler

Two triggers (real cron + poor man's cron), atomic task claim. Modules declare handlers in `module.json`.

**`SchedulerRepository::claimOverdue()`'s per-row claim**: genuinely atomic under concurrent callers (two requests' poor-man's-cron tail firing close together, or a real crontab hitting `public/cron.php` at the same moment a request does) — each candidate row is claimed via its own `UPDATE ... WHERE id = ? AND status = 'pending'`, and only a row whose `rowCount()` comes back 1 (i.e. THIS call's UPDATE actually flipped it) is returned to that caller. An earlier version ran one blanket `UPDATE ... WHERE status = 'pending'` covering every due row, then re-`SELECT`ed *every* row currently `'processing'` — indistinguishable from a row a concurrent caller had just claimed a moment earlier, so two callers could both receive the same row and both run its handler at once. This let two overlapping `Task\InstallUpdateHandler` runs both copy an extracted archive over the live install directory at the same time, once leaving a production site with a route in `module.json` pointing at a controller method the deployed `.php` file didn't actually have — `Core\Maintenance\GitHubWebhookService::handlePushEvent()` additionally cancels any still-`'pending'` (never a `'processing'` one already running) earlier push-triggered install before scheduling a new one, so two pushes seconds apart can no longer even queue two separate `install_update` rows that might both become due at once in the first place.

Central `JournalService::log()`. No personal data in entries. Modules never write their own log tables.

### 8.10 Photo per person/year (`Core\Photo`)

Generic, reusable component: a photo (`member_photos`: member_id, scout_year_id, file_id) is tied to a member AND a scout year. `MemberPhotoService::resolveFileId()` returns the photo for a given year, falling back to the most recent earlier year, else null. The `member_photo()` Twig function (registered in `TwigFactory`) renders it — an initials-in-a-circle avatar (same style as the account menu) when none exists — and, in configuration mode, the same click-to-replace overlay as `editable_image()` (upload context `member_photo`, key `"{memberId}:{scoutYearId}"`, handled by `UploadController`). Not specific to any module. It renders `/files/{id}/thumb`, never the bare `/files/{id}` original — see §8.39 for the derivative pipeline this and every other core photo context now go through.

`Core\Photo\SectionPhotoService`/`SectionPhotoRepository` are the section-keyed twin of the above (`section_staff_photos`: section_id, scout_year_id, file_id — one group photo per section per year, same per-year-with-earlier-year-fallback resolution). `Core\Photo\SectionPhotoProcessor` center-crops the uploaded image to a fixed 4:3 landscape ratio (correcting EXIF orientation first) and caps the width at 1600px before storage, via a `UploadController::processSectionPhoto()` step that runs before the generic `UploadHandler::handle()`. The `section_photo()` Twig function mirrors `member_photo()`'s rendering/overlay behavior but has no initials-style fallback — with no photo and outside configuration mode it renders nothing at all, so a section that never had a group photo uploaded shows no empty box. Used on the Staffs page and, unauthenticated, on the public Contact and Sections pages (`section_photo($sectionId, ...)`) — the underlying file's `role_min` is `'public'` (§8.39's write-up of a real bug this was, until fixed), and it renders `/files/{id}/md`, same derivative pipeline as `member_photo()` above.

### 8.11 Badges (`Core\Badge`)

Transversal roles assignable to chiefs/chief-d'unité (e.g. Infirmier, Trésorier) — a global concept (`badges`: name, is_default, is_active) configured once from Configuration > Badges (`Core\Http\Controller\ConfigBadgesController`, split out of the former "Configuration générale" page alongside the module registry — see §7.1's own note on that page's current, much smaller scope), with assignment scoped per member per scout year via `member_badges.member_year_id` (so history across years is preserved automatically, the same way `member_years` already works). Badges are plain text/name only — no logo/icon.

Default badges (Infirmier, Trésorier) are seeded idempotently by `BadgeService::ensureDefaults()` (called on every `/config/badges` request, same pattern as `SettingService::register()`) and can never be deleted or renamed, only deactivated. Any badge already assigned to a member — even in a past year — can likewise never be deleted, only deactivated: `BadgeService::delete()`/`update()` refuse both cases, preserving historical data; the admin UI reflects this by disabling the delete button and making the name read-only rather than letting the request round-trip and fail. A deactivated badge is invisible everywhere (assignment picker, trombinoscope) but existing `member_badges` rows are untouched, so reactivating it brings past assignments back.

`Core\Member\SectionService::hydrateMemberProfile()` fetches a member's active badges into `MemberProfile::$badges` — the single hydration path shared by the Staffs page and (via `SectionService::hydrateMemberProfile()` reuse, see §8.8-adjacent Trombinoscope note) the trombinoscope module, so badges surface in both without either needing its own plumbing. `SectionService::getSectionStaff()` also filters to chief/admin-role functions only — a section's animés carry the same `section_id` on their `member_functions` row, so this filter is what keeps the Staffs/badge-assignment page staff-only.

On the Staffs page, an editing chief's assignment picker is a `partials/chip_picker.html.twig` (§8.30) instance per member, `mode: multi` — the same wrapping-chips-plus-"+N"-sheet component and style as the section picker above it, rather than an unbounded row of toggle buttons that used to grow with the active badge count. A non-editing viewer (or a member with zero assigned badges) still just sees plain `<span class="badge">` chips, unchanged — that list is always small (assigned badges only), so it never needed the picker's truncation/overflow behavior.

**Referent badges**: `badges.referent_section_id` (nullable FK to `sections`) marks a badge as an auto-generated "Référent {section name}" badge, one per currently-visible non-STAFFDU section. `BadgeService::syncSectionReferentBadges()` is idempotent and self-healing — called on every relevant page load (Configuration > Badges, Config Desk, Staffs) plus directly after a section name/visibility change for immediate effect: it creates a badge only for a visible section (never for a hidden one) and renames it on a name mismatch, but never touches `is_active` after creation, so a manual activate/deactivate is never silently overwritten by a later sync. Referent badges are `is_default = true` (read-only name, same non-deletable treatment as Infirmier/Trésorier above) but — unlike other default badges — their "Actif" toggle stays editable. Assignment is restricted to members currently in the Staff d'U section: enforced both in the UI (`StaffsController` filters the picker) and server-side in `BadgeService::toggleAssignment()` via `SectionService::isMemberYearInSection()`, so the restriction holds regardless of which page's picker triggers the request.

### 8.12 "Staff d'U" section (`Core\Member\UnitStaffSectionService`)

Chef-d'unité staff (role `admin`) are represented by a real `sections` row (`desk_code = 'STAFFDU'`, branch `"Staff d'U"`, canonical `sort_order = 50` between Pionniers and Route — see `AgeBranchRepository::canonicalSortOrder()`) — not a virtual/synthetic entry. Because membership is expressed the same way as any other section (`member_functions.section_id` pointing at it), it flows through `SectionService::getAllWithBranches()`/`getSectionStaff()`, the SectionPicker, and the trombinoscope with zero special-casing anywhere. `UnitStaffSectionService::ensureSection()` idempotently creates the branch/section and forces it active — it must survive `MappingResolver::deactivateAllSections()` even though no Desk CSV row ever references `STAFFDU` directly (§8.8's deactivate-then-reactivate pattern only reactivates sections a CSV row actually names).

Because a function's role is only known once an admin confirms it on Config Desk (`FunctionsController::update()`) — never at raw Desk import time, where new functions always import as `role = 'identified'` — membership must be (re)synced in two places: `UnitStaffSectionService::syncMembership($scoutYearId)` runs at the end of `DeskImportService::import()` (covers already-confirmed `admin` functions) and again after every `FunctionsController::update()` role change (covers promotions/demotions to/from `admin` post-import). It's a bulk, idempotent two-step select/update: any unassigned `admin`-role function gets `section_id = STAFFDU`; any `STAFFDU`-assigned function whose role is no longer `admin` gets `section_id` cleared back to `NULL`.

`Core\View\SectionRepository` (the public "Notre unité > Sections" read-model) explicitly excludes `desk_code = 'STAFFDU'` — the section is real and generic for internal purposes but never listed publicly.

### 8.13 Generic list editor (`partials/list_editor.html.twig`) and rich text field (`partials/rich_text_field.html.twig`)

Reusable, content-agnostic core components for any module that manages a configurable, orderable list (introduced by the `banner` module — homepage banners — but not specific to it; a future FAQ or useful-links module reuses both unchanged). `list_editor.html.twig` owns only the list chrome: add button, native HTML5 drag-and-drop reordering, an active toggle, and delete (with an optional `can_delete`/`delete_blocked_reason` per item — same "used elsewhere, deactivate instead" pattern as Badges/§8.11). It knows nothing about what an item *is* — the caller supplies each item's body via Twig's `{% embed %}` block-override mechanism (`item_content`, declared as a real `{% block %}` inside the partial's `{% for item in items %}` loop, not a `{{ block() }}` call — only a genuine block declaration lets `{% embed %}` re-render the caller's override per iteration with `item` in scope). `public/assets/js/list-editor.js` persists reordering silently in the background; add/delete reload the page, since those change the item set itself.

`rich_text_field.html.twig` is the child content component the banner module plugs into `item_content`: a preview + "Modifier" button reusing the exact same modal/toolbar markup as `editable()`'s configuration-mode overlay (`partials/rich_text_editor.html.twig`, `document.execCommand`-based, no editor dependency) and the same rich-text engine (`Core\Security\HtmlSanitizer` via `Core\View\EditableContentService`) — but never gated behind configuration mode, since the admin page embedding it already provides its own `role_min` authorization. It saves via the generic core endpoint `POST /api/rich-text-content` (`EditableContentController::updateField()`, role_min superadmin) — same body shape as `/api/editable-content` but without the configuration-mode check — so a module reusing this partial needs no save endpoint of its own for the text itself. `public/assets/js/rich-text-field.js` is safe to load alongside `editable.js` on the same page: both bind to the shared `#richTextEditorModal`, but `editable.js` only loads when configuration mode is active, which a dedicated admin config page never is.

The banner module's list items themselves (`banners`: id, is_active, sort_order, role_min — no text column) illustrate the intended split: dynamic collection metadata lives in the module's own table, while each item's formatted text is stored in the core `editable_contents` table under a per-item key (`banner_content_{id}`) — reusing the exact same storage/sanitization as any other `editable()` content instead of a second rich-text mechanism. `role_min` (`'public'`/`'identified'`/`'chief'`) gates a banner's visibility the same way route `role_min` does everywhere else (`Core\Security\Role`'s hierarchy) — deliberately capped at `chief`, since `admin`/`superadmin` alone would have no realistic audience on the always-public homepage.

`Core\Module\HomeBannerProvider` is the module-into-core hook (same §7.4 precedent as `FunctionFlagsProvider`) letting the banner module inject a randomly-chosen active banner's HTML onto `PageController::home()` without core depending on the module: `getRandomBannerHtml(string $viewerRole)` picks fresh (never cached) on every call, only among banners whose `role_min` the viewer satisfies, and returns `null` when there are no active banners or none visible at that role, which the homepage template treats as "render nothing," not an empty box.

### 8.14 Encrypted file storage (`Core\File\EncryptedFileStorageService`)

Generic, module-agnostic counterpart to `Core\File\UploadHandler` for files that must never touch disk in plaintext (introduced for the `finance` module's receipts, but not specific to it). Uses the same master key as `Core\Security\EncryptionService`: `store()` encrypts the given content and writes it under a caller-chosen subdirectory of `storage/`, then registers a `FileRecord` via `Core\File\FileRepository::create()` with `encrypted = true`; `retrieve()` reads the file back and decrypts it; `delete()` removes both the encrypted file and its `FileRecord` — a genuine physical deletion, unlike a module's own "archive, never delete" convention for the record that *references* the file. `Core\Http\Controller\FileController::serve()` is the single integration point: it already runs every request through `FileAccessGuard`'s `role_min` check, and now branches on `FileRecord::$encrypted` to call `EncryptedFileStorageService::retrieve()` instead of reading the file directly, so decryption is transparent to any caller downloading via `/files/{id}` regardless of which module owns the file. A task handler that needs file access reconstructs this service from `TaskContext::$storagePath` (added for this purpose) the same way it reconstructs any other repository/service from `TaskContext::$connection`.

### 8.15 On-demand backups (`Core\Maintenance`)

Configuration > Maintenance page (`role_min: admin`, matching the spec's explicit choice even though every other Configuration-menu route in this codebase uses `superadmin`) for FTP/shared-hosting deployments that have no server-level backup mechanism of their own. `BackupService` is a deliberately "pure mechanical" service — no `BackupRepository`/`FileRepository` dependency — reusable by future update/reset iterations, not just this one: `createDatabaseDump()` (full dump, every table structure + data), `createConfigOnlyDump()` (every table's structure, but row data for only a hardcoded whitelist of config-only tables — `settings`, `module_registry` — deliberately narrow rather than a broad "config tables" guess, since module settings all funnel through the generic `settings` table already), `createFileBackup(bool $includeGallery)` (zips `core/`/`modules/`/`public/`/`storage/`, always excluding `storage/keys/`, `storage/config/`, `storage/temp/`), and `createFullBackup(string $scope, string $password)` (combines a dump with a `ZipArchive::EM_AES_256`-encrypted file backup; returns both paths — `array{zipPath, dbDumpPath}` rather than the single path a naive reading of "one backup" might suggest — because the `backups` schema needs a separate `db_dump_file_id`, and bookkeeping/registration is deliberately left to the caller). Both dump methods go through `Core\Database\DatabaseDumper` (`Ifsnop\Mysqldump\Mysqldump`, a pure-PHP mysqldump reimplementation that dumps over PDO) rather than shelling out to a `mysqldump` binary — see §8.15.1. `supportsZipEncryption()` self-tests the runtime's libzip crypto support with a throwaway zip so the UI can fail cleanly (disable the full-backup option with an explanatory message) on environments without it, rather than generating a silently-unencrypted archive.

#### 8.15.1 Database dumping without a `mysqldump` binary (`Core\Database\DatabaseDumper`)

Every database dump in this codebase — `BackupService`'s two dump methods above, and `MigrationRunner`'s pre-migration safety backup (§3, `attemptBackup()`) — used to shell out to the `mysqldump` CLI via `Core\System\ShellExecutor`/`ExecutableLocator`. That broke on a real production host (scoutmagic.be, LWS shared hosting): its `mysqldump` client build couldn't load the `mysql_native_password` authentication plugin (`Got error: 2059`), even though PHP's own PDO connection to the exact same MySQL server worked instantly — PDO's `mysqlnd` driver doesn't depend on that plugin at all, only the separate `libmysqlclient`-based CLI tools do. No combination of `disable_functions`/`$PATH` workarounds fixes a missing shared library, so the shelled-out approach was replaced entirely rather than patched further.

`Core\Database\DatabaseDumper::dump(host, port, dbName, user, password, outputPath, ?skipDataForTables)` wraps `ifsnop/mysqldump-php` (`Ifsnop\Mysqldump\Mysqldump`), a pure-PHP mysqldump reimplementation that connects and dumps entirely over a PDO connection it opens itself from the given DSN — no shell, no external binary, no `disable_functions`/`$PATH`/auth-plugin failure modes at all. `$skipDataForTables` is the library's `'no-data'` setting given a table list instead of `true`: every table's structure is always dumped, but row data is skipped for the tables named — used by `BackupService::createConfigOnlyDump()` to keep every table's schema while excluding member/business data (it computes "skip data for every table except the config whitelist" via `SchemaIntrospector::getTables()` + `array_diff()`). `'add-drop-table' => true` is set explicitly to match real mysqldump's default `--opt` behavior, so a dump can be restored over an already-migrated schema without "table already exists" errors.

Restoring a dump (`BackupService::restoreDatabase()`) still shells out to the `mysql` CLI client via `ExecutableLocator`/`ShellExecutor` — out of scope for this fix, since it's a different binary with a different (PDO-independent) failure mode, and restores are comparatively rare, admin-triggered, error-visible operations rather than something that silently degrades every page load the way the old daily-polling `mysqldump` backup did.

A full backup runs as a background scheduled task (`core`/`create_backup`, `CreateBackupHandler`, registered directly in `public/index.php` rather than through a module's `scheduled_tasks` — the first core-level, non-module task handler) so a large gallery-inclusive zip doesn't block the request: the controller encrypts the user-supplied password with `EncryptionService` and embeds it (base64) in the scheduled task's payload, decrypted only inside the handler right before use. On completion the handler registers both files via `FileRepository` (`role_min: 'admin'`, unencrypted-at-rest since the zip's own AES-256 password is the protection mechanism here, deliberately not layered with `EncryptedFileStorageService`), purges backup rows beyond the 5 most recent (deleting their files too), and notifies the requesting admin via `Core\Notification\NotificationService` (`$context->notifications`) — reusing `requested_by_user_account_id` (§8.16) to know who to notify without the payload needing to carry it explicitly. The Maintenance page polls `GET /api/maintenance/backup-status/{id}` (same `setInterval` pattern as the magic-link login poll) until the task completes or fails.

A separate, unencrypted `auto_backup` type (`Task\AutoBackupHandler`) covers recurring, unattended backups — frequency (`none`/`daily`/`weekly`/`biweekly`/`monthly`, default `monthly`) is a `SettingService` key editable from the same page, gallery always excluded (no admin present to opt into it), no push notification (no human requester). It self-reschedules at the end of every run rather than being a first-class recurring task — same pattern as `Modules\LlmConnector\Task\RefreshModelsHandler`'s weekly refresh, since `Core\Scheduler` has no first-class recurring-task concept — re-reading the frequency setting each time so a change takes effect on the next run. Shares the same 5-backup quota as every other type via `BackupRepository::findBeyond()`.

### 8.16 `requested_by_user_account_id` on scheduled tasks (`Core\Scheduler`)

`scheduled_actions` carries a nullable `requested_by_user_account_id` FK, and `SchedulerService::schedule()`/`scheduleAfter()` accept it as a trailing optional param. `SchedulerRunner::processOverdue()` always merges it into the payload under the reserved key `requested_by_user_account_id` (int or null) before calling a handler, regardless of what the original caller put in the payload — so any `TaskHandlerInterface::handle()` can read who (if anyone) asked for a given run without every caller having to thread it through its own payload shape by convention. Introduced for backup completion/failure notifications (§8.15) but generic to any future "notify the person who asked for this" scheduled task.

### 8.17 Update from GitHub (`Core\Maintenance`, "Mise à jour")

Extends §8.15's Configuration > Maintenance page for FTP/shared hosting with no SSH/Git/Composer: `VersionFile` (`Core\Maintenance\VersionFile::read()`/`write()`) reads/writes a plain `VERSION` file at the project root — the installed-version source of truth, deliberately a filesystem fact rather than a database row, since a fresh deploy must be able to report its version before the DB is even configured. `scripts/release.sh` commits this file as part of every tagged release so it always matches the release artifact it ships inside.

`Core\Maintenance\GitHubReleaseClient` (behind `GitHubReleaseClientInterface`, so callers are testable without the network) is a minimal unauthenticated REST client — same `file_get_contents()`/`stream_context_create()` approach as `Modules\LlmConnector\Provider\AnthropicProvider`, the only other outbound-HTTP precedent in this codebase, no new Composer dependency. `GET /repos/{owner}/{repo}/releases/latest` already excludes drafts and prereleases on GitHub's side. The owner/repo are `Core\Config\SettingService` keys (`update_github_owner`/`update_github_repo`), never hardcoded, so a fork can point at its own repository.

Version detection is primarily **webhook-driven**, not polled: `POST /api/webhook/github` (`Core\Http\Controller\WebhookController`, the only `role_min: 'public'` route in the codebase with no CSRF check at all — GitHub is a machine caller with no session, so a shared-secret HMAC-SHA256 signature, `X-Hub-Signature-256`, verified in constant time via `hash_equals()`, is what authenticates it instead) replaces an earlier daily-polling task handler entirely. The stable channel (patch/minor/major) additionally has a daily fallback poll (`Task\CheckStableUpdateHandler`, below) in case a webhook delivery is missed or never configured — development mode has no such fallback, since it has no equivalent "poll for a new commit" cadence worth reusing. The signing secret is `random_bytes(32)` hex, generated/regenerated from the Maintenance page (`MaintenanceController::generateWebhookSecret()`) and stored **only** in `secrets.enc` (`Core\Security\SecretManager`) — shown to the admin exactly once, in the generation response, never persisted anywhere it could be read back, and never in `Core\Config\SettingService` (a `settings` row would leak it, even dimmed, to any superadmin on the generic Paramètres page). An invalid or missing signature journal-logs `github_webhook_signature_invalid` at `level: 'security'` and returns 403; every other outcome — including an event this site doesn't act on — returns 200, since GitHub retries on non-2xx and there's nothing to retry for an intentionally-ignored event.

`Core\Maintenance\GitHubWebhookService` handles the two events the webhook cares about. A `release` event (`action: 'published'`) always refreshes the same `SettingService` cache the old polling handler used to (`update_latest_version`/`update_release_notes`/`update_release_html_url`/`update_download_url`/`update_checked_at`/`update_dependencies_changed`, the last via the same `GET .../compare/{installed}...{latest}` composer.lock check — comparing from the bare commit sha when the installed version is a "dev-{sha}" build, since `vdev-{sha}` is never a real tag — "assume changed" on any compare failure) so `MaintenanceController::index()` keeps working unchanged — then, only if `auto_update_enabled` is on, `auto_update_level` isn't `'dev'` (development mode, below), and the release's version-bump type (`patch`/`minor`/`major`, derived by comparing dotted version components — `GitHubWebhookService::isBumpAllowed()`; an installed dev build bypasses this gate entirely, since its "dev-{sha}" components would parse as 0.0.0 and classify every release as a major bump, permanently blocking a site whose admin deliberately switched the channel from `'dev'` back to patch/minor) is within that level, schedules `Task\InstallUpdateHandler` (`core`/`install_update`, `reference: 'scheduled_install'` so a newer release arriving before the slot fires cancels and replaces it) for the next occurrence of the configured weekday+time (`auto_update_day`/`auto_update_time`, interpreted as wall-clock **Europe/Brussels local time** — `GitHubWebhookService::SCHEDULE_TIMEZONE`, same platform rationale as the calendar module's `IcsBuilder::TIMEZONE_ID`; shared hosting routinely runs PHP with `date.timezone` UTC, and an admin's "03:00" means 3 o'clock at night locally — converted back to the server timezone before storage, since `scheduled_actions.run_at` is naive and compared against PHP's default timezone) — pushed a full week out if that occurrence is under 5 minutes away, so the webhook's own arrival time can never coincide with an immediate install. A `push` event only acts when `auto_update_enabled` is on and `auto_update_level === 'dev'`, and the pushed branch matches `dev_update_branch`: it schedules an **immediate** install (`scheduleAfter(..., 0, ...)`, no weekly slot, no level gate) from the pushed commit's zipball (`https://api.github.com/repos/{owner}/{repo}/zipball/{sha}`), with `update_history.version_to` set to `dev-{7-char short sha}` rather than a release tag. Neither path has a human requester (`requested_by: null`, §8.16) — a webhook-triggered install never sends a push notification, only journal entries (`auto_update_scheduled`, `level: 'info'`).

Development mode is a 4th `auto_update_level` value (`'dev'`, alongside `patch`/`minor`/`major`) selected from the same "Mises à jour automatiques" radio group and gated by the same top-level `auto_update_enabled` switch — not a separate danger-zone toggle with its own confirm-keyword flow, as an earlier iteration had it. That extra friction never added real protection: configuring the GitHub webhook at all already requires repo admin rights, so the confirm-keyword step was redundant. Selecting `'dev'` swaps the "Moment d'installation" (day/time) fields for a "Branche à surveiller" text field (`dev_update_branch`), since installs happen immediately per-commit rather than on a schedule. While `'dev'` is selected, a published release is deliberately never auto-installed (`GitHubWebhookService::handleReleaseEvent()` short-circuits when `auto_update_level === 'dev'`) — development mode and the stable weekly-slot path are mutually exclusive by construction of the radio group, not merely by convention.

All 5 of these settings (`auto_update_enabled`/`auto_update_level`/`auto_update_day`/`auto_update_time`/`dev_update_branch`) are real `SettingService` rows (so `ResetSettingsHandler`/§8.18 resets them like anything else) but are filtered out of `SettingsController::index()`'s generic Configuration > Paramètres rendering via a small hardcoded exclusion list — that page's plain editable-row UI has no room for the semver explainer or webhook status block this section needs, so it's managed exclusively from the Maintenance page instead. Saving those preferences (`MaintenanceController::saveAutoUpdatePreferences()`) also reconciles any release install still pending at its weekly slot (`reference: 'scheduled_install'`): canceled — with its `update_history` row marked failed so it doesn't show "En cours" forever — when auto-update was turned off, the channel switched to `'dev'`, or a narrowed level no longer allows that release's bump type; moved to the newly-saved day/time otherwise. Without this, "Enregistrer" silently left the pending install exactly as the old preferences had scheduled it.

`POST /config/maintenance/update/check-now` (`MaintenanceController::checkForUpdatesNow()`) is an on-demand equivalent of the webhook for an admin who doesn't want to wait — since detection is otherwise purely webhook-driven with no polling fallback. It checks whichever channel `auto_update_level` currently selects: `GitHubReleaseClient::getLatestRelease()` for the stable channel (also refreshing the same settings cache the webhook would, via `setInternal()`, since these are non-editable rows), or the new `GitHubReleaseClient::getLatestCommit(branch)` (`GET /repos/{owner}/{repo}/commits/{branch}`, returning a `CommitInfo` DTO — `sha`/`message`/`htmlUrl` — mirroring `ReleaseInfo`'s shape) for the development channel. Never schedules an install itself; the page shows a confirm dialog and, if accepted, calls the existing `installUpdate()` endpoint. That endpoint now branches the same way: the stable-channel path is unchanged (re-validates from the settings cache), while the dev-channel path (`installDevBranchUpdate()`) re-fetches the branch's current head itself rather than trusting anything the client echoed back from the check-now response — the same "never trust the client's idea of the target version" principle applied to a source that has no settings cache to re-validate against — then schedules exactly the same immediate/no-slot/no-level-gate install `GitHubWebhookService::handlePushEvent()` would for that commit.

`Task\InstallUpdateHandler` (scheduled either by `MaintenanceController::installUpdate()` for a manual install — which re-validates server-side that a newer version is actually cached before scheduling, never trusting the client — or automatically by `GitHubWebhookService` above) walks `update_history.status` through `backing_up` → `downloading` → `installing` → `migrating` → `completed`, each transition persisted so the polling route (`GET /api/maintenance/update-status/{id}`, same pattern as `backup-status`) can report progress. The safety backup (step 1, `Core\Maintenance\BackupService::createDatabaseDump()` + `createFileBackup(true)`, registered as a `backups` row with `type='auto_update'`) is not a shortcut — it is the only thing an automatic rollback can restore from, so any throwable from downloading through the `VERSION` write triggers `BackupService::restoreDatabase()` + `restoreFiles()` against that exact backup, and `update_history.status` becomes `rolled_back` rather than `failed`. A throwable during the backup step itself cannot be rolled back (nothing was changed yet). The "installing" step copies every top-level entry of the extracted artifact over the live install except `storage/` (all live uploads/keys/config/temp) and `VERSION` (written separately, last, only once everything else succeeded) — nothing else needs excluding for a release artifact, since unit-specific files (`config/app.php`, `.env`) were already excluded from the artifact itself by `scripts/release.sh`. A branch install (`payload['source_type'] === 'branch'`) has one extra step first: GitHub's branch/commit zipball always wraps its contents in a single top-level `{owner}-{repo}-{sha}/` directory (unlike `scripts/release.sh`'s artifact, `zip -r artifact.zip .`, which has none), so `resolveBranchArchiveRoot()` descends into that one directory before the install copy runs — gated strictly on the explicit `source_type`, never inferred from entry count alone, so a release artifact is never mistakenly stripped even if it coincidentally had one top-level entry. **A real production incident, found and fixed**: `Core\View\TwigFactory` compiles templates to `storage/temp/twig_cache` with `auto_reload` off outside debug mode, so it never re-checks a compiled template's freshness against its `.twig` source — and Twig's cache key derives from the template *name*, not its contents, so an updated template maps to the exact same cache entry as the old one. Since `installFiles()` deliberately never touches `storage/` (live uploads/keys/config), a template-only change installed correctly to disk but the server kept executing the pre-update compiled version indefinitely, with no visible sign anything had failed. Two complementary fixes: `clearCompiledTemplateCache()` deletes `storage/temp/twig_cache` immediately after `installFiles()` on every install (release or branch), **and** — the load-bearing one — `TwigFactory` namespaces the cache directory by `VersionFile` (`storage/temp/twig_cache/{version}`, see §13). The namespacing is what actually makes this self-healing, because it needs no cooperation from whatever installer performed the update: clearing the cache from `InstallUpdateHandler` only helps once the *new* installer is the one running, so the very install that ships the fix would still have served stale templates without it. The "migrating" step reuses `Core\Database\MigrationRunner` against the newly-installed `schema/core.sql` — no separate update-specific migration logic. Per §10, that call can return early (`MigrationResult::$complete = false`) if the schema change is large; when it does, `InstallUpdateHandler` reschedules itself rather than treating the update as finished (`update_history.status` stays `'migrating'`), and the next invocation re-enters via a dedicated resume path that retries only `migrate()` — never re-running `backing_up`/`downloading`/`installing`, which aren't safe to repeat. A throwable during a resumed migration reconstructs the safety backup's file paths from `update_history.backup_id` (the resumed invocation no longer holds them locally) before rolling back the same way the initial attempt would have.

`public/cron.php` (the real crontab entry point) was fixed in an earlier iteration: it was missing `create_backup`'s handler registration entirely (background backups silently failed with "No handler registered" whenever a real cron ran them instead of the poor-man's-cron in `public/index.php`) and never constructed a `NotificationService` at all (so push notifications from any background task never fired via real cron). Both are wired identically to `public/index.php`. There is no longer a `check_update` handler to keep in sync between the two entry points, since the webhook replaced it — but `check_stable_update` (below) is a new one that must be, and is.

`Task\CheckStableUpdateHandler` (`core`/`check_stable_update`, `reference: 'daily'`) is the stable channel's webhook fallback: each run, if `auto_update_enabled` is on and `auto_update_level !== 'dev'`, it calls the new `GitHubWebhookService::checkForNewRelease()` — a live `GitHubReleaseClient::getLatestRelease()` lookup that delegates to the same private `processRelease()` the webhook's `handleReleaseEvent()` uses internally, so both paths refresh the settings cache and schedule installs identically; the only difference is where the release info comes from (a webhook payload vs. a direct API call). A failure (GitHub unreachable, rate-limited, etc.) is caught and journaled (`auto_update_check_failed`, `level: 'info'`) rather than left to crash the scheduler run. It then unconditionally self-reschedules for the next day at 01:00 plus a fresh `random_int(0, 3600)`-second jitter — spreading every installation's daily API call across an hour rather than every site on earth polling at exactly the same second — using the same "no first-class recurring task" pattern as `Task\AutoBackupHandler`/`Modules\LlmConnector\Task\RefreshModelsHandler`: re-check via `SchedulerService::find('core', 'check_stable_update', 'daily')` before scheduling, so a run that happens to overlap an already-pending future occurrence never duplicates it. `public/index.php` seeds the very first occurrence immediately at bootstrap (same one-time `if find() === null` pattern as the other self-rescheduling tasks), so a fresh install starts checking without waiting a full day for the first jithttered 01:00 slot.

The "Détection des nouvelles versions" webhook status block on the Maintenance page (config/webhook-not-configured warning included) is now shown **only** while `'dev'` is selected — the stable channel no longer depends on the webhook being configured at all, thanks to this daily fallback, so surfacing that warning outside development mode would be misleading noise. `MaintenanceController::index()`'s `webhook_warning` computation reflects this: `$autoUpdateEnabled && $level === 'dev' && !$webhookConfigured`.

### 8.18 Reset and restore (`Core\Maintenance`, "Réinitialisation")

The third and final Configuration > Maintenance section: three destructive actions, each requiring the admin to type an exact confirmation word (`REINITIALISER`/`EFFACER`/`RESTAURER`) — checked server-side in `MaintenanceController` (a JS check only gates the submit button's `disabled` state, never the actual authorization), with "Réinitialisation complète" additionally requiring an explicit "I understand" checkbox. All three run as background scheduled tasks and take their own automatic `backups` row (`type='auto_reset'`) first via `BackupService`, exactly like §8.17's update install.

Progress polling (`GET /api/maintenance/reset-status/{id}`) deliberately reuses `scheduled_actions` itself rather than a dedicated history table — `{id}` is the id `SchedulerService::scheduleAfter()` already returns, and `Core\Scheduler`'s own `pending`/`processing`/`done`/`failed`/`canceled` status is sufficient for this section's needs (unlike §8.17's `update_history`, nothing here needs InstallUpdateHandler's richer per-step status). `Core\Config\SettingRepository::resetAllToDefaults()` (backing "Paramètres par défaut") resets every setting's `setting_value` to its `default_value` column — populated at every `register()` call, including a self-heal `UPDATE` on rows that already existed, since `Task\ResetSettingsHandler` trusts this column blindly and a setting registered before this column existed must not silently reset to empty.

`Task\FullResetHandler` ("Réinitialisation complète") is the most destructive code in this codebase: after its safety backup, it truncates every table (`TRUNCATE` + `SET FOREIGN_KEY_CHECKS=0/1` on MySQL; `DELETE FROM` per table on SQLite — dual-pathed specifically so its own tests can exercise the real wipe logic without a live MySQL server), deletes `secrets.enc`, and empties `storage/` except `storage/keys/master.key` (the encryption key must survive so existing encrypted backups — including the one just taken — stay decryptable) before recreating the empty directory structure and moving the safety backup's two files back under `storage/maintenance/`. Those files end up orphaned (no `backups`/`files` row survives the truncate to reference them) — retrievable only via FTP, which is an accepted, spec-literal trade-off of "keep the file, not the bookkeeping" for an operation whose entire point is an empty database. The final `event_log` write (`'full_reset_performed'`) is deliberately the first row of the "new" installation's journal, with a `null` `user_account_id` — logging the real requester would violate `fk_el_user`, since `user_accounts` was just wiped. `Core\Maintenance\BackupServiceInterface` exists solely so `FullResetHandler` accepts an injectable fake in tests (`?BackupServiceInterface $backupService = null`, defaulting to a real `BackupService`) — every other Maintenance handler still constructs `BackupService` directly, this is not a general DI abstraction.

`Task\RestoreBackupHandler` ("Restaurer un backup") accepts two sources: an existing `backups` row (`source=server`) or a previously-downloaded backup zip re-uploaded by the admin (`source=upload`, saved to `storage/temp/`, validated by attempting to read `database.sql` from within it before anything else runs, deleted in a `finally` regardless of outcome). `BackupService::restoreFiles()` gained an optional `$password` parameter for this iteration — needed because the user-triggered `full_config`/`full_no_gallery`/`full_with_gallery` backup types (§8.15) are AES-256-encrypted zips, unlike the automatic `auto_update`/`auto_reset`/`database` types, which never are. Like `InstallUpdateHandler`, it takes its own pre-restore safety backup first and automatically rolls back to it (`restoreDatabase()` + `restoreFiles()`) if the restore itself fails at any step — including its post-restore `migrate()` call, which (§10) can itself need more than one invocation to finish; a `payload['resume_migration']` follow-up task retries only the migration, reconstructing the safety backup's paths from `payload['safety_backup_id']` for its own rollback path since it no longer holds them locally.

### 8.19 Retro module (`modules/retro`)

Post-activity "rétrospectives" boards: a chief/intendant (`retro_role_min_create_board` setting, default `intendant`) opens a board manually or lets `Task\AutoCreateRetroHandler` create one automatically at a linked calendar event's start time (opt-in per event, `calendar_events.auto_create_retro`, only when the `calendar` module is enabled — a genuine optional module-to-module dependency, §7.5) — animés then post free-text comments and vote (a fixed per-member vote budget, `retro_default_vote_budget`) without needing an account beyond the same identified-member session used everywhere else. `Task\AutoCloseHandler` closes a board past its configured duration and emails a closing digest; `Task\PurgeRateLimitHandler` clears `retro_rate_limits` rows past their window. `Service\ModerationService` is an optional `llm_connector` consumer (§7.5) with three modes (`retro_moderation_mode`: disabled/warning/enforced) — a flagged comment either posts anyway with a private warning to its author, or is rejected with an AI-suggested, more respectful rewording, degrading silently to "no moderation" when `llm_connector` is disabled or has no active provider. `Api\RetroEventLinkLookupInterface` is retro's own public API (§7.5, module-to-module direction) letting the calendar module resolve an event's linked board without depending on retro's internal classes.

### 8.20 SOS Staff d'U module (`modules/sos_staff`) and scheduler `TaskContext`/`cron.php` fixes

Keeps the unit's single "SOS" emergency phone number always forwarded to whichever Staff d'U member is on duty. `Provider\PhoneProviderInterface` (`readForwardingState()`/`setForwarding()`/`testConnection()`/`listLines()`) is a pluggable-provider abstraction; `Provider\Ovh\OvhTelephonyProvider` + `OvhApiClient` implement it against the OVH Télécom API (request signing, no new Composer dependency — same raw-`curl`-style precedent as `Modules\LlmConnector\Provider\AnthropicProvider`). `Service\OnCallService` builds/saves a month's duty grid (sparse storage — no row means "available") and computes day-to-day forwarding-target transitions, scheduling one `Task\ApplyRedirectHandler` run per actual change via `SchedulerService`; `Service\RedirectService::apply()` is the read-set-confirm-notify sequence, journaling every outcome and alerting the resolved super-admin (`Core\Security\UserAccountRepository::findFirstSuperAdmin()`) on technical failure. `Service\CalendarSyncService` is an optional `calendar` module consumer (§7.5, reuses the module's default public "Animateurs" calendar) that mirrors duty periods as read-only events, degrading to a no-op when `calendar` is disabled.

Building this module surfaced two real gaps in the generic scheduler, fixed at the core level (not worked around): `Core\Scheduler\TaskContext` was never actually constructed in production — neither `public/index.php`'s poor man's cron nor `public/cron.php` called `SchedulerRunner::setTaskContext()`, so any module's real task handler crashed (`RuntimeException('TaskContext not set')`) the moment an overdue task reached it — and `public/cron.php` never built a `ModuleManager` either, so `SchedulerRunner::setModuleManager()` was never called there, meaning every module-registered task silently failed ("No handler registered") whenever run via a real crontab instead of a page visit. Both entry points now build the same `ModuleManager` and `TaskContext` (`TaskContext` also gained `$userAccounts`, needed for the super-admin alert above) before processing overdue tasks.

### 8.21 Public Sections page (`Core\Http\Controller\PageController::sections()`)

Each card on the public "Notre unité > Sections" page (`role_min: public`, same audience reasoning as Contact below) shows the section's staff photo (§8.10), its designated "responsable" name, its email, and a small per-section editable text block reusing `editable()` unchanged (key `"section.{desk_code}.text"`). The "responsable" name comes through `Core\Module\SectionResponsableProvider` (`getResponsable(int $sectionId, int $scoutYearId): ?MemberProfile`) — the same core-hook precedent as `FunctionFlagsProvider`/`HomeBannerProvider` (§7.4/§8.13): core defines the interface, the trombinoscope module implements it (reusing its own "lead" resolution, itself backed by `FunctionFlagsProvider`'s per-function flag), and the composition root wires the concrete instance into `PageController` only when `trombinoscope` is enabled — a section simply shows no responsable name when it isn't. The public Contact page (`PageController::contact()`) similarly shows the Staff d'U section's group photo and a name/totem roster (`SectionService::getSectionStaff()`), both routes deliberately public even though the closest analogous page (`/trombinoscope`) requires `identified`, on the reasoning that a prospective parent/member needs contact information before they've registered.

### 8.22 Member page ("Espace animés", `Core\Member\MemberPageService`)

`Core\Http\Controller\MemberController::show()` (`/members/{id}`, `role_min: identified`, further scoped by `MemberService::canAccess()` — chief/admin or the member themselves) orchestrates only; every data need is built by `Core\Member\MemberPageService::buildPageData()`, a per-request core service with four nullable optional-module dependencies (§7.5 pattern): `Modules\MassMail\Api\MassMailQueryInterface`, `Modules\Gallery\Api\GalleryAlbumProvider`, `Modules\Calendar\Api\CalendarEventLookupInterface` (reused as-is — no new interface — for "next upcoming event"), and `Core\Module\SectionResponsableProvider` (§7.4, same trombinoscope-backed hook as the public Sections page, §8.21). Each corresponding page block degrades to "not displayed" when its dependency is null.

The page's own section is resolved from the member's main function's Desk code (`SectionService::findByDeskCode()` — `MemberFunctionInfo` carries only a Desk code, not a numeric id). The section's responsable is shown via a dedicated `full_name` Twig filter (first + surname, deliberately never `display_name`/totem) together with a real postal address — `SectionResponsableProvider` implementations are built on `SectionService::hydrateMemberProfile()`, which never loads addresses, so `MemberPageService` re-resolves the responsable's full profile via `MemberService::findProfileByMemberAndYear()` specifically for this need. "Référent {section}" badge holders are Staff d'U members, not members of the target section, so they can't be found through `SectionService::getSectionStaff($sectionId)` — `MemberBadgeRepository::findMemberYearIdsForBadgeAndYear()` looks them up directly by badge id.

**Photo, replaceable by the member outside configuration mode**: `member_photo()` (TwigFactory) takes an explicit `bool $editable` parameter — `config_mode` remains the trigger at every other call site, this page is the only one that also passes `is_self`. The real authorization boundary is server-side, in `UploadController::isUploadAuthorized()`: the `member_photo` context is allowed either through configuration mode (unchanged) or when the requesting account is linked to the member the upload key names (`MemberService::isLinkedToMember()`, blind-index email match) — no chief/admin bypass, with the single deliberate exception of an active temporary member override (§8.42), which that method now also answers true for. `/upload`'s route `role_min` was loosened from `superadmin` to `identified` to let this through; every other context (`editable_image`, `section_photo`, the new `age_branch_logo`) keeps its own explicit check in that same method, so the loosened route floor changes nothing for them. The upload always lands on the *current* scout year even when the displayed photo came from `MemberPhotoService`'s own earlier-year fallback, because the key `member_photo()` builds for the editable overlay uses `effective_scout_year_id`, never the year the fallback actually resolved.

**Branch card** (right column): the member's age branch's federation logo + explanation link, configurable per branch from Configuration > Config Desk (`age_branches.logo_file_id`/`explanation_url`, auto-migrated core-schema columns). Fallback order: uploaded (`role_min: public`, generic `/upload` flow, new `age_branch_logo` context) → shipped default under `public/assets/img/branches/`, matched via `AgeBranchRepository::defaultLogoFilename(sortOrder)` (keyed off `canonicalSortOrder()`, never a free-text label comparison — Staff d'U/Iama/unknown branches have no default) → nothing (no empty box, same principle as `section_photo()`). The explanation link itself always renders even with no logo at all.

**Private documents** (self only, no staff bypass): `core.sql`'s `member_documents` table (member id, scout year, title, `file_id`) is metadata-only — `Core\Member\MemberDocumentService`/`MemberDocumentRepository` just list rows; the actual access boundary is `files.owner_member_id` enforced by `FileAccessGuard` (§8.3). Storage/listing only this iteration — no generation, no admin upload UI yet.

**Mass-mail email detail**: `MassMailQueryInterface::getRecentEmailsForMember()` now returns each recipient's `id` alongside subject/date/section, and a new `findEmailDetailForMember(memberId, recipientId): ?array` resolves the full subject+body. The detail route itself (`GET /members/{id}/emails/{recipient_id}`) lives in the mass_mail module (`Modules\MassMail\Controller\MemberEmailController`, declared in `module.json`), not in core's `MemberController` — the content is entirely the module's own data; core only ever links to it via the recipient id `MemberPageService` already exposes. The controller takes core's `MemberService` directly (module→core dependencies need no interface indirection, unlike the reverse) to re-verify server-side that the requesting account is chief/admin or the member themselves, on top of `findEmailDetailForMember()`'s own re-check that the recipient row really belongs to this member.

### 8.23 Installable PWA — app shell only (`Core\Photo\UnitLogoProcessor`/`UnitLogoService`, `Core\Http\Controller\PwaController`, `public/sw.js`)

Lot 1: the site installs to the home screen on Android/iOS and opens standalone, offline shows a fallback page instead of the browser's own error — no push notifications, no content caching yet (those are later lots). `PwaController::manifest()` (`GET /manifest.webmanifest`, `role_min: public`) builds every field from `SettingService` — `pwa_theme_color`/`pwa_background_color` (new, editable, defaults `#0d6efd`/`#ffffff`) alongside the existing `site_name`/`short_name` — never a hardcoded unit name, per §1. `start_url` is `/?source=pwa`; `display: standalone`; the `icons` array lists only 192/512/512-maskable (each `?v={version}` for cache-busting) — the 180px apple-touch icon is a separate `<link>` in `base.html.twig`'s `<head>`, not part of the manifest.

**Unit logo feature (widened scope, same underlying service).** `Core\Photo\PwaIconService`/`PwaIconProcessor` started as Lot 1's PWA-icon-only pair; a later "one upload feeds the favicon, the PWA icons, and the footer logo" feature renamed them to `UnitLogoService`/`UnitLogoProcessor` rather than adding a second icon service alongside the first — same single-upload, single-derivation-pipeline shape, just more outputs. The upload context followed suit (`Core\Http\Controller\UploadController`'s `pwa_icon` context is now `unit_logo`; the journal action is `unit_logo_updated`), and storage moved from `storage/core/pwa/` to `storage/core/logo/` (still covered by the blanket `storage/core/` `.gitignore` entry either way — nothing new to ignore). The upload block lives in Configuration avancée's (`/setup`, `Core\Http\Controller\SetupController`) "Paramètres généraux" card — moved there from Configuration > Paramètres (`config/settings.html.twig`) once that page was judged the more natural home alongside the rest of the unit's core identity settings (site name, short name, base URL). Not a settings-table row of its own, `is_file()` is still the entire state — a preview, an "Envoyer un logo" link into the generic `/upload` flow, and a "Supprimer" button (`POST /config/settings/logo-delete`, stayed on `SettingsController` — only the *page* moved, not this endpoint) shown only once a custom logo exists, reverting to the shipped defaults. Rendered only when `is_initialized` is true: during first-run (before `secrets.enc` exists), `SetupController` has no database and therefore no `UnitLogoService` to build (its `setUnitLogoService()` setter is only ever called from the normal-boot branch of `public/index.php`, mirroring the existing `setSettingService()`/`setJournalService()` pattern) — the block simply doesn't render rather than linking into an upload flow that can't work yet.

**iOS never updates an already-installed home-screen icon — no workaround exists.** iOS copies the icon into SpringBoard at the moment a site is added to the home screen and never re-reads the manifest/`apple-touch-icon` afterward; there is no web API to refresh it. The only recourse is removing and re-adding the icon. Android/Chrome, by contrast, re-reads the manifest periodically and updates an installed app's icon on its own — no admin action needed there once the cache-invalidation fix below actually makes the new icon reachable. The upload flow's own after-the-fact messaging reflects this asymmetry: `UploadController::store()`'s success flash for the `unit_logo` context spells out the iOS caveat inline (shown once, right after a successful upload, via `base.html.twig`'s generic `get_flash()` rendering — not a permanent fixture), and the upload block additionally offers a "envoyer une notification" button (superadmin-triggered, `POST /config/settings/logo-notify-ios`, `SettingsController::notifyIosLogoUpdate()`) that broadcasts a new declared type, `core.unit_logo_updated_ios` (`Core\Notification\NotificationRegistry`), to every user account via `NotificationService::dispatch()` (never `notify()` — a broadcast still needs to respect each recipient's own channel preferences/quiet hours like any other declared type). Deliberately manual, never automatic on every upload: a logo retouched three times in a row must not notify the whole unit three times, so the button only appears once a custom logo already exists and it's the admin's call when the change is "done."

**Icons live outside `Core\File\FileRepository` entirely.** A favicon/manifest/home-screen icon is fetched with no session at all, so SECURITY §6's session/role-aware `/files/{id}` single-download-path rule doesn't apply — and storing them under `public/` (SECURITY §6's usual rule for anything session-gated) isn't the concern here either, the actual reason is keeping an admin-uploaded asset out of the codebase's own tree. `Core\Photo\UnitLogoService` has no DB row and no `files` table entry: eight fixed PNG filenames (`favicon-16/32/48.png`, `logo-64.png`, `icon-180/192/512.png`, `icon-512-maskable.png`) plus `favicon.ico` under `storage/core/logo/` are the entire derived state — "has a custom logo" is `is_file()` on a *ninth*, also-retained file: `source.<ext>`, the original upload itself (see below for why). `GET /pwa/icon-{size}.png` (`role_min: public`, unrenamed despite the storage-path move — nothing outside this service's own generated URLs ever referenced it) serves an override if present, else the shipped default under `public/assets/img/pwa/`, with `Cache-Control: public, max-age=31536000, immutable` — the version query string, not the header, is what actually invalidates a stale copy (`pwa_icon_version`, a non-editable `SettingService` row bumped on every upload, deletion, *and* re-derivation, see below — kept its original name since the DoD for the logo feature never asked to rename it). `GET /favicon.ico` (`PwaController::favicon()`) is the one exception to that cache header: browsers request it implicitly at the document root with no query string to version, so a full year of "immutable" there would let a stale icon outlive several re-uploads for any visitor relying on this legacy path alone — `Cache-Control: public, max-age=86400` instead. Every current browser prefers the versioned `<link rel="icon" type="image/png" sizes="32x32"|"16x16">` pair `base.html.twig`'s `<head>` links instead (only rendered when a logo actually resolves — `unit_logo_available`, a twig global computed once at bootstrap); `/favicon.ico` exists for the rest.

**The original upload is retained, not just its derivatives** (`storage/core/logo/source.<ext>`) — every derived size is re-generated from it, on demand, without asking the superadmin to re-upload: `UnitLogoService::rederiveFromSource()` re-runs the full `UnitLogoProcessor::process()` pipeline against the *current* `pwa_background_color` and is called by `SettingsController::update()` whenever that specific setting changes (a no-op, deliberately, when no custom logo was ever uploaded — the shipped defaults aren't derived from any live source). Without this, changing the background color would update the theme and the manifest's own `background_color` immediately but leave the maskable icon and `icon-180` baked onto whatever color was in effect at the last upload.

`Core\Photo\UnitLogoProcessor` (GD, same before-storage precedent as `SectionPhotoProcessor`, §8.10) center-crops the source to a square, then derives every size in one pass. Two different treatments, by design: favicons (16/32/48), the footer logo (64), and the plain manifest icons (192/512) are alpha-preserving resizes — expected to blend with whatever they sit on (a browser tab, a dark-mode home screen). `icon-180` and the maskable icon are flattened onto an *opaque* `pwa_background_color`-filled canvas instead — the maskable icon follows the W3C convention (logo scaled to 80% of the canvas, centered, so Android's own circular-or-other mask can crop ~20% off each edge without cutting into the logo), `icon-180` uses the same flattening at 100% (full bleed, no safe-zone margin). **A real, pre-existing bug fixed alongside this feature**: `icon-180` used to go through the same alpha-preserving path as every other size — iOS has no concept of an alpha channel on an apple-touch-icon, so any transparency in the source rendered as a solid black square on the home screen once installed, and this was true even for a unit that never uploaded a custom logo (the *shipped default* `icon-180.png` itself carried an alpha channel). Both the processor and the shipped default (`scripts/generate-pwa-defaults.php`, re-run against the existing `icon-512.png` default as source) are fixed together. `favicon.ico` is hand-packed by `UnitLogoProcessor::packIco()` — a ~30-line `pack()`-based ICONDIR/ICONDIRENTRY container wrapping the already-PNG-encoded 16/32/48 bytes directly (the modern ICO format allows embedded PNG payloads, no BMP/DIB re-encoding, no new Composer dependency); every current browser prefers the `<link rel="icon">` PNGs above, so `/favicon.ico` only matters as the legacy fallback for the rest. `UploadController`'s `unit_logo` context (superadmin-only, its own explicit branch in `isUploadAuthorized()`) short-circuits before the generic upload pipeline — it never touches `UploadHandler`/`FileRepository`, calling `UnitLogoService::storeUploadedLogo()` directly instead.

Footer logo: `base.html.twig`'s `{% block footer %}` renders `/pwa/icon-64.png?v={{ pwa_icon_version }}` at 24px next to `{{ site_name }}`, `alt=""` (decorative — the unit name text sits right next to it, a redundant alt would just be screen-reader noise), gated on the same `unit_logo_available` global as the favicon `<link>`s — nothing rendered, no broken image, no empty box, when neither an upload nor a shipped default resolves (same "nothing if absent" principle as `section_photo()`, §8.10).

`public/sw.js` is hand-written (~200 lines, no Workbox, no build step — ARCHITECTURE's existing "only three external dependencies are justified" stance extends to this) and must stay at the web root (`/sw.js`) to control the whole site; moving it under `/assets/` would silently scope it to that subtree. It precaches an explicit whitelist only — Bootstrap (including Bootstrap Icons' font files, not just its CSS — see the real bug below), the site's own CSS/JS, `components.css`, every icon size above (including `/favicon.ico`), `/offline` and its own script, and the shipped branch-logo images — cache-first for exactly those, network-only for everything else except two narrow exceptions: a failed navigation falls back to `/offline` (below), and `GET /files/{id}/thumb|md` (§8.39's derivative pipeline) gets a **read-only** network-first-with-cache-fallback branch that never itself writes to Cache Storage (writing stays the pre-download script's job, §8.25) — the plain, un-suffixed `/files/{id}` original stays strictly network-only, same as every other authenticated download. Versioning is entirely the query string: `base.html.twig` registers `/sw.js?v={{ app_version }}&iv={{ pwa_icon_version }}` (`Core\Maintenance\VersionFile` for the former, `Core\Photo\UnitLogoService::currentVersion()` for the latter — two entirely independent counters, a logo upload never bumps `app_version`) with `updateViaCache: 'none'`; `CACHE_NAME` derives from *both* values (`'app-shell-' + VERSION + '-icons-' + ICON_VERSION`), so either one changing alone is enough to make the browser see a byte-different worker, which installs, then purges every cache whose name starts with the `app-shell-` prefix and doesn't match the new one in `activate`, and re-precaches under it.

**A real bug, since fixed: `activate` used to empty the entire offline content cache.** The purge above used to filter on `name !== CACHE_NAME` alone — every cache with any other name, including `offline-config` and every `content-*` cache (§8.25's own lifecycle, meant to be purged only on logout or consent withdrawal), was deleted on every release *and* on every standalone unit-logo upload (which bumps `ICON_VERSION` and therefore `CACHE_NAME` on its own, with no release involved at all). The filter is now scoped to the `app-shell-` prefix specifically, so a logo upload or a release no longer silently wipes a member's offline pre-download.

**A second real bug, since fixed: the app shell's own precache list was incomplete.** `APP_SHELL_BASE_URLS` precached `bootstrap-icons.min.css` but not the `.woff`/`.woff2` font files that CSS actually references, so every icon on the site — including the entire nav menu, which is icon-driven — rendered as an empty box offline. `components.css` (Staffs, trombinoscope, calendar, member page, départs) and the handful of scripts the offline surfaces themselves depend on (`breadcrumb.js`, `chip-picker.js`, `notification-badge.js`, `offline-cache.js`, `offline-nav.js`, `offline-photos.js`, `offline-page.js`) were missing the same way. The list stays deliberately small — no admin-only or module-config script belongs in it — and a dedicated test (`Tests\Core\Offline\AppShellManifestTest`) now fails the build the moment a listed path stops existing on disk.

**Icon cache-busting: a real, since-fixed bug.** Every icon URL (`ICON_URLS` — the 8 PNG sizes above, deliberately excluding `/favicon.ico`, which browsers request bare with no query string to ever version) is precached WITH its current `?v=` baked into the `Request` (`VERSIONED_ICON_URLS = ICON_URLS.map(url => url + '?v=' + ICON_VERSION)`) and matched in the `fetch` handler by *exact* URL — no `ignoreSearch`. Previously every icon URL was precached bare and matched with `caches.match(request, { ignoreSearch: true })`, which made `ignoreSearch` do exactly what its name says: `/pwa/icon-192.png?v=7` resolved to the one precached `/pwa/icon-192.png` entry regardless of what `7` was, so `pwa_icon_version` bumping had zero effect on what was actually served — a re-uploaded logo silently kept showing the old icon (favicon, installed-app icon, footer logo) until a visitor manually cleared their cache, no matter how many times `pwa_icon_version` incremented, since the cache name itself never changed either (see above). `ignoreSearch` stays in effect for the rest of the app shell (`APP_SHELL_BASE_URLS`: Bootstrap, the site's own CSS/JS, `/favicon.ico`, `/offline`) — none of those legitimately carries a query string in real traffic, so it's harmless there and a reasonable safety net.

`offline.html.twig` deliberately does not extend `base.html.twig` — it's precached once and can be served back much later with zero network, so nothing session/DB-derived (`menus`, `current_user_*`, `config_mode`) may ever be baked into it; it's a fully standalone document linking only already-precached CSS (Bootstrap, Bootstrap Icons, `app.css`). **A real bug, since fixed: its "Réessayer" button never worked.** The page used an inline `onclick="window.location.reload()"`, which SECURITY §9's CSP (`script-src 'self' 'nonce-…'`, no `unsafe-inline`) silently blocks — there is no nonce to attach either, since the page is precached once and served back with no server render to issue one. Rewritten with a plain precached script (`public/assets/js/offline-page.js`, itself part of `APP_SHELL_BASE_URLS` above) and three real actions: Réessayer (reload), Retour (`history.back()`), and a link to the home page. The page also gained a Bootstrap Icons stylesheet link — its own `bi-wifi-off` icon didn't render before either, for the same missing-font-file reason as the bug above.

CSP (SECURITY §9) gained `manifest-src 'self'; worker-src 'self';`. The app-shell cache is declared in `Core\Cookie\CookieRegistry` (`necessary`, no consent gate — that arrives with actual content caching in a later lot) even though it's Cache Storage, not an HTTP cookie, so the cookie preferences page/banner stay a complete accounting of the site's local storage footprint.

### 8.24 Notification centre and Web Push, Lot 2 (`Core\Notification`)

A type registry (parallel to `Core\Cookie\CookieRegistry`) — core types in `Core\Notification\NotificationRegistry::getCoreTypes()`, module types declared under `module.json`'s `notifications` section (id prefixed `"{module_id}."`, validated by `Core\Module\ModuleManifest::validateNotification()`) and aggregated into the same registry by `Core\Module\ModuleManager::loadModule()` → `NotificationService::registerModuleTypes()`. Each type declares a `role_min` and a `channels` object (`in_app`/`push`/`email`, each `on`/`off`/`default_on`/`default_off` — `on`/`off` are locked, ignoring any member override entirely). See `docs/module-development.md`'s Notifications section for the module-author-facing contract.

`NotificationService::dispatch($typeId, $recipients, $payload, $actorUserAccountId)` is the send pipeline every declared type goes through: re-checks each recipient's *current* role against the type's `role_min` (never trusting the role at whatever moment the caller built the list — degrades to "always allowed" only when constructed without the optional `RoleResolver`/`ScoutYearService`, a documented narrow-unit-test escape hatch, never the real composition root), always creates the in-app `notifications` row even when the recipient's `push` channel is off, and never pushes to `$actorUserAccountId` (the row still appears in their own centre). Push is never sent synchronously — recipients are grouped by their quiet-hours-adjusted target send time into one `core/send_notifications` scheduled task per distinct time (not per recipient), processed by `Task\SendNotificationsHandler` under a 20-second budget that reschedules any remainder immediately. The older, simpler `notify($userAccountId, $title, $body, $url)` (single recipient, immediate, no role/channel/quiet-hours resolution, writes under an internal undeclared `core.system` type id) is kept unchanged for a handful of pre-Lot-2 Maintenance task handlers (reset/restore/update) that were never part of this lot's scope — new callers use `dispatch()`.

**Quiet hours and discretion mode**: per-account override (`user_accounts.quiet_hours_start`/`_end`, both-or-neither) else global `SettingService` defaults (22:00–07:00); `resolvePushRunAt()` returns "now" outside the window or the window's own end instant otherwise (handles overnight wrap). Discretion mode (`user_accounts.notification_discretion`) substitutes a generic push title/empty body at push-composition time only — the stored `notifications` row and the in-app centre always show the real text.

**Web Push**: reuses `minishlink/web-push` (kept over hand-rolling RFC 8291/VAPID crypto — see the dependency table in §1) — `WebPush::queueNotification()`/`flush($batchSize)` gives the spec's "batches of ~20" without hand-rolled `curl_multi`. `MessageSentReport::isSubscriptionExpired()` (404/410) prunes dead `push_subscriptions` rows; both `endpoint` and the subscription keys are `BLOB`-encrypted at rest, looked up via a blind index (`endpoint_blind_index`) same as every other encrypted-lookup field in this codebase.

**Migration safety**: `notifications.type_id` (new `NOT NULL`) and `push_subscriptions.endpoint_blind_index` (new `NOT NULL`) can't be backfilled from Iteration 1's plaintext rows, so `public/index.php` runs a one-time `TRUNCATE` of both tables (gated by a `notifications_v2_migrated` setting checked via raw PDO, before `SettingService` exists at that point in bootstrap) immediately before the schema migration — accepted as safe since both tables are purely ephemeral operational state, never a legal record.

**Service worker consolidation (a real pre-existing bug, found and fixed while building this)**: Lot 1's `public/sw.js` (§8.23) and an earlier, separate `public/sw-push.js` (registered independently by `push-notifications.js`) both resolved to the same default scope and silently fought for control of every page — whichever registered last won, meaning either push or the offline app-shell cache was non-functional depending on script execution order. Fixed by merging push/notificationclick/`navigator.setAppBadge()` handling into the single `sw.js` and deleting `sw-push.js`; `push-notifications.js` now just awaits `navigator.serviceWorker.ready` instead of registering its own worker.

**Surfaces**: the nav notification indicator (`partials/notification_dropdown.html.twig`, §8.29 — server-rendered `unread_notifications_count`/`latest_notification` Twig globals, the badge refreshed live by `notification-badge.js` via 60s polling plus an immediate refresh on the service worker's `postMessage({type: 'push-received'})`), the app-icon badge (`navigator.setAppBadge()`, called only from the service worker's own `push` handler — the only place that can update it while the installed app is closed), the notification centre (`/notifications`, grouped by day), a preferences page (`/notifications/preferences`, per-type channel toggles — the push column starts disabled until `Notification.permission === 'granted'`, and this page never itself calls `requestPermission()`, only "Mon compte" does), and a superadmin config page (`/config/notifications` — device count, VAPID rotation which disconnects every existing subscription, a test-send button, and a "no real cron detected" warning driven by a new `cron_last_run` setting updated only by `public/cron.php` itself, distinct from the pre-existing `scheduler_last_run` which `index.php`'s poor-man's-cron updates on every web hit and is therefore not a reliable signal of real crontab configuration).

**Retention**: `Task\PurgeNotificationsHandler` (daily, self-rescheduling) deletes only *read* notifications older than a configurable `notifications_retention_days` (default 90) — unread notifications are never auto-purged regardless of age.

**Module-resolved audiences (`modules/groups`, the first type whose audience is not a role).** Every earlier module type broadcasts — the calendar's and the gallery's pass `UserAccountRepository::findAllIds()` and let `dispatch()`'s `role_min` re-check narrow it. That works only because "every identified member" *is* their audience. A discussion group's is its membership, which no role expresses, so `Modules\Groups\Service\GroupRecipientResolver` resolves it itself and passes only those recipients: `role_min` stays a floor that `dispatch()` re-checks, never the audience (handing it every account id for a private group's post would notify the whole site). It reads membership group-first — the reverse of `GroupAccessService`'s account-first read, sharing the same explicit-rows-plus-linked-sections rule and the same year resolution, so the two can never disagree about who is in an archived group — resolves each member to an account through the blind index that already backs login (`member_years.email_blind_index` via `findMostRecentEmailBlindIndexForMember()`, plus any currently-`valid` `member_emails` row; a `pending`/`inactive` secondary resolves neither a login nor a notification), and **deduplicates by `userAccountId`** so a parent with two children in the same section is told once. Everything is read at dispatch time, never captured at post time, which is what makes a member who left the section in between drop out with nothing to invalidate. `Core\Member\SectionMembershipRepository::findMemberIdsForSections()` is the one core addition this needed — the reverse of the pre-existing `hasAnyPeriod()`, for callers starting from a set of sections rather than from one member. Site admins, who moderate every group without holding a row in any of them, are resolved through `RoleResolver` over all accounts rather than a stored flag (there is no column to select on); that is O(accounts) and therefore used only by the report notification, which is a rare event.

**Module-side debounce.** A notification a member can trigger with one tap needs one, or a post with twelve reactions becomes twelve entries and twelve buzzes for its author. `groups` keeps the timing in two small tables of its own (`discussion_group_{post,reply}_reaction_notices`, one row per item, `ON DELETE CASCADE` so a deleted post takes its row with it and there is no purge task to write) against a configurable `groups_reaction_notification_window_minutes`. It records **timing, never notifications** — core's `notifications` table stays the only record of what was sent, and a module must not read it.

**Magic link, same lot**: the login page's confirmation poll now also re-checks immediately on `visibilitychange` (`auth.js`) rather than relying solely on its 3s `setInterval`, which a backgrounded tab (especially an installed PWA) can have throttled or fully suspended by the browser/OS while the user is away confirming in their mail client. `Core\Security\SessionManager` also moved from a session-only cookie (`cookie_lifetime: 0`, wiped on every browser/app close on many mobile platforms) to a 30-day cookie with a matching `gc_maxlifetime`, so an installed app no longer demands a fresh magic link every few days.

**Early session lock release**: `public/index.php` calls `session_write_close()` right after `SecretManager`/`EncryptionService` are built — before the DB connection and schema migration — rather than at the very end of the request. PHP's default file-based session handler holds an exclusive lock on the session file for as long as the session stays open; a slow request (a schema migration on first run after a real change, at minimum) previously held that lock for its full duration, and every other request from the same browser (another tab, a background fetch, the next click) would queue at `session_start()` for that entire time — a real production incident on MariaDB-backed hosting, traced to `SchemaComparator` never reaching a "nothing to do" steady state (see MariaDB-specific type/default normalization in `Core\Database\ColumnDefinition`/`SchemaComparator`) compounding with this lock into requests that looked completely stuck. After the early close, `session_status()` reports `PHP_SESSION_NONE` for the rest of the request, but `$_SESSION` itself stays populated and readable in memory — only *persisting a write* needs the session reopened. `Core\Security\SessionStore` is the single place that touches `$_SESSION` for writes/removals (`get()`/`set()`/`remove()`/`ensureWritable()`), reopening internally on every write so no call site has to remember the guard — application code should never write to `$_SESSION` directly. This replaced an earlier pattern of repeating `if (session_status() !== PHP_SESSION_ACTIVE) { session_start(); }` at each of ~15 call sites across `AuthSession`/`CsrfGuard`/`FlashMessage`/`WebAuthnService`/`ConfigurationMode`/`ScoutYearSession`/`SetupController`, several of which were missed on the first pass (`CsrfGuard::validateToken()`/`FlashMessage::get()` were still gating their *reads* on `PHP_SESSION_ACTIVE`, which — now that the session is closed by the time dispatch reaches them on every real request — made CSRF validation and flash messages fail unconditionally; `WebAuthnService`/`SetupController` had writes with no guard at all, silently dropped instead of persisted).

### 8.25 Offline content caching, Lot 3/4 (`Core\Offline`, `public/sw.js`)

Extends Lot 1's app-shell-only service worker to a whitelisted set of content pages, network-first with cache fallback.

**Whitelist aggregation (Lot 4 — a module-driven aggregator, same shape as cookies/notifications).** `Core\Offline\OfflineWhitelist` no longer hardcodes anything beyond core pages (`/`, `/contact`, `/sections`, `/rgpd`, `/account`, `/notifications`, `/members/`, `/chefs/staffs` — core routes, never a module's, so naming them here isn't the thing the "no module path in `Core\Offline`" rule is about). A module declares its own offline-cacheable page(s) under a `module.json` `offline` section (`Core\Module\ModuleManifest::validateOfflineEntry()`), and `Core\Module\ModuleManager::loadModule()` registers them into the same `OfflineWhitelist` instance (`registerModuleEntries()`) alongside cookies/notifications — a disabled module simply never registers its entry, dropping it from the aggregate on its own, with nothing to clean up. Current module entries: `/calendar` (calendar), `/trombinoscope` (trombinoscope), `/chiefs/stats` (member_stats), `/previsions` (registration). See `docs/module-development.md` for the module-author-facing contract.

Each entry carries `path`, `label` (French), `match` (`exact` by default, or `child`), and `role_min`. `match: 'child'` means the path plus **exactly one** additional segment — this is what makes `/members/12` cacheable while `/members/12/emails/5` (mass-mail content) stays out, with no exclusion list to maintain: `OfflineWhitelist`'s private `matches()` helper (also reimplemented, necessarily, in `offline-nav.js`/`public/sw.js` — there is no shared runtime between PHP and the browser, so this is a second implementation of a generic *algorithm*, never a second copy of the *data*) checks the remainder after the entry's own path has zero or more than one path separator.

`Core\Offline\OfflineWhitelist::getEntriesForRole(Role $role)` — never `getAllEntries()` — is what feeds both `#offline-config-data` (`base.html.twig`) and `Core\Offline\OfflineManifestService` (below): a logged-out visitor is never handed `/previsions` or `/chiefs/stats`, and the client never tries to cache a page it will only ever get a 403 for. This global is built in `public/index.php` deliberately *after* `$moduleManager->loadEnabledModules()` has run (same ordering constraint as `$menus = $menuBuilder->build()`, right next to it) — every enabled module must have had its chance to register before the role-filtered list is computed. `isPathWhitelisted(string $path)` (role-agnostic — the RBAC guard has already run by the time this is checked) is the server-side counterpart used for ETag eligibility (below).

Consumed on several ends: `public/assets/js/offline-nav.js` greys out unavailable links and drives the generic unavailability dialog (below), `public/assets/js/offline-cache.js` relays the same data to the service worker via `postMessage({type: 'offline-config', ...})` on every page load, and `Core\Offline\OfflineManifestService`/`GET /api/offline/manifest` (below) turns it into the actual list of URLs the pre-download script fetches.

**Generic unavailability dialog (Lot 4).** Before this, `.offline-link-disabled` carried `pointer-events: none` (`public/assets/css/app.css`), so a click never even reached a handler, and anything reached another way (a form, a bare `fetch()`) landed on the generic `/offline` fallback page with no way back except reloading. Three layers now, all generic, no per-page wiring:

1. Delegated **capture**-phase listeners on `document` in `offline-nav.js` — one for `click` on internal `<a href="/…">` (recomputed fresh against the whitelist on every click, never relying on the `.offline-link-disabled` class already being applied, so a link inserted into the DOM after the last state refresh is still covered), one for `submit` on **any** `<form>` (no whitelist check — there is no "safe" form action, so every submission is blocked while offline, unconditionally).
2. A single `window.fetch` wrapper, installed once by the same script — the hole layers 1 leaves: marking a notification read, `list-editor.js` persisting a reorder, chip pickers, and every future module doing a POST with no `<form>` in sight all go through `fetch()` directly. Short-circuits **non-GET** requests while offline (rejecting with the same `TypeError` a real network failure would produce) and opens the dialog; GET requests pass through completely untouched — the notification badge poll and the pre-download script both rely on failing silently, not on being intercepted here.
3. The service worker's fallback to `/offline` (unchanged) remains the net for what never reaches the page at all: a typed URL, the back button, a tab left open since yesterday.

One modal in `base.html.twig` (`#offline-dialog`), two French messages depending on which layer fired ("cette page n'est pas disponible hors ligne" / "cette action nécessite une connexion"). Dismissing it is the only way out — never a navigation, never a redirect — so a partially-filled form survives untouched. `.offline-link-disabled` itself is now grey-only (opacity + `cursor: not-allowed` + `aria-disabled`) — no `pointer-events: none`, no forced `tabindex="-1"`, so a disabled link stays reachable and operable by keyboard/assistive tech and can announce its own state; the greyed-out offcanvas/mobile menu falls out of this for free, since it's the same DOM the desktop nav uses. Known, accepted limitation: this rests on `navigator.onLine`, which reports "online" on a captive Wi-Fi with no real internet — the service worker's `/offline` fallback (layer 3) is what actually catches that case. Form submission is deliberately never rewritten as `fetch()` to detect real network loss — that would change redirect/flash-message handling for every form on the site for a single edge case already covered another way.

**Pre-download manifest (Lot 4 — `Core\Offline\OfflineManifestService`, `GET /api/offline/manifest`).** Supersedes the old, narrower `GET /api/offline/photo-manifest` (staff photos only): returns everything the caller's role entitles them to hold offline — every whitelisted page URL (with `/members/` expanded to the caller's own linked members, one page URL per member, via `Core\Member\MemberService::getLinkedMembers()`), and every image URL those pages actually render, as the **exact variant URL** the page itself uses (`/files/{id}/thumb` for member/staff photos via `member_photo()`, `/files/{id}/md` for section photos/the home hero/branch logos via `section_photo()`/`editable_image()`/the member page's branch card — see §8.39). Same URL as the page, or the cache misses — this exact mismatch (the pre-download fetching `/api/offline/photo/{id}` while every page rendered `/files/{id}`) is precisely the bug §8.39 closed for images; this service is what makes sure a *page* and its manifest entry never drift apart the same way. `role_min: public` on the route itself — the returned content is already self-limiting by role (a guest gets only public pages/images; member-specific entries need an email `AuthSession::getEmail()` doesn't have for a guest), so floating the route above that would add nothing, same reasoning as `/calendar`'s own `role_min: public`. The one MODULE page with images, `/trombinoscope`, is resolved through `Core\Module\StaffDirectoryProvider` exactly as the old route was — never by the service naming the module.

**Pre-download script (Lot 4 — `public/assets/js/offline-prefetch.js`, renamed from `offline-photos.js`).** Runs on **every launch** of the installed app (`display-mode: standalone`), with functional consent, never anonymously (`accountScope === 'guest'` bails out immediately) — no longer gated behind a one-time `localStorage` marker the way the old photo-only version was, since re-validating on every launch is the entire point now. Fetches the manifest above, then:
- **Images**: skips any URL already in the cache — a derivative URL is immutable for a given file id (`Core\Photo\ImageVariantService`: a re-upload always creates a new file id), so an unchanged photo costs zero bytes on a repeat launch. Cached image entries no longer in the manifest (a member no longer linked, a photo removed) are deleted via `cache.keys()`/`cache.delete()`, so the cache doesn't grow unbounded across launches.
- **Pages**: re-validates with `If-None-Match` built from the cached response's own `ETag` (below). A `304` means the content is unchanged — the script re-`put`s the **same cached body** with a refreshed `Date` header rather than re-downloading, since otherwise the staleness threshold and the "Version hors ligne du …" banner (unchanged, both still keyed off that `Date` header) would fire on a copy that was just confirmed current a moment ago.
- Every entry is best-effort (its own `.catch()`) — one failed image or page must never abort the rest of the run.

Writes go straight to the same `content-{accountScope}-{version}` cache `public/sw.js`'s own fetch handler reads from — this script remains the sole writer for image derivatives (the service worker's own `/files/{id}/{variant}` branch is read-only, §8.39), and since it only ever runs in standalone mode, its writes are automatically consistent with the write policy below without needing a separate check.

**ETag revalidation (Lot 4 — `Core\Http\FrontController`).** Every 200 GET HTML response on a whitelisted path (`OfflineWhitelist::isPathWhitelisted()`) gets an `ETag` header — an MD5 of the rendered body — and an incoming `If-None-Match` matching it gets a bare `304` back instead of the full page. Deliberately narrow: never in configuration mode (that overlay markup is session-specific and must never be revalidated away), never on POST, never on a non-whitelisted path — nothing here makes `/files/{id}` or any authenticated-but-not-whitelisted route cacheable. `FrontController` takes `OfflineWhitelist` as an **optional** trailing constructor parameter (`= null`) specifically so this stays backward-compatible with the many existing `new FrontController($router, $twig, $config)` call sites across the test suite — only `public/index.php`'s real composition root passes the live instance.

**Write policy — installed app only (Lot 4).** Personal data (Mon compte, member pages) is cacheable now that the whitelist covers them, so the service worker **writes** to the content cache, on an ordinary page navigation, only when the delivering page reported `standalone: true` in the same config blob (`offline-cache.js` computes it via `matchMedia('(display-mode: standalone)')`/`navigator.standalone`, folded into the same `postMessage` payload as everything else — never a second message). **Reads stay unconditional**: a single visit from a normal browser tab must never blind the installed app's already-cached copy until its next page load — only the *write* on that tab's own navigation is suppressed, `caches.match()` on a cache-miss fallback is untouched either way. The pre-download script's own writes need no separate check, since the script itself only ever runs in standalone mode (above).

**Activation**: gated entirely on `functional` cookie consent (`Core\Cookie\CookieRegistry`'s `content-{accountScope}-{version}` entry) — no separate on/off setting. The service worker persists the delivered config (staleness days, consent flag, whitelist, account scope, app version, standalone flag) in its own small Cache Storage entry (`offline-config`, one synthetic `Response` holding JSON) rather than a plain JS variable, since the browser can terminate and restart the worker between the `postMessage` that delivers it and the next `fetch` event that needs it — no new browser API, just the same Cache API already used for the app shell.

**Cache naming and scope**: `content-{accountScope}-{version}`, where `accountScope` is the signed-in `user_accounts.id` or `'guest'`. A different member logging in on the same device gets a different cache name outright; `Task\PurgeNotificationsHandler`-style residue avoidance goes further — logout (`offline-cache.js`, hooking every `form[action="/logout"]`) and withdrawing functional consent (the `/cookies` preferences form and the consent banner's "reject all" button, both in `cookie-consent.js`/`offline-cache.js`) send an explicit purge, deleting every `content-*` cache outright rather than just letting the old scope go unused. Withdrawal specifically sends a full `offline-config` update with `consent: false`, not just a bare purge message — a bare purge alone would empty the caches but leave the worker's *stored* config still saying consent was granted, so it would start writing to the cache again on the very next whitelisted page visited in the same session.

**Staleness**: `offline_cache_staleness_days` (`SettingService`, default **30** — raised from 7 now that a page can be cheaply revalidated via ETag instead of always fully re-downloaded, `core`-level not module-level) — read into the same config blob, never hardcoded in `sw.js`. On a cache-fallback hit, the worker compares `Date.now()` against the cached `Response`'s own `Date` header (the timestamp the page was actually fetched or last confirmed current — see the pre-download script's refresh-on-304 behavior above — not when it's being served); past the threshold it serves the generic `/offline` page (Lot 1) instead of a plausible-but-wrong schedule. Blocking behaviour itself is unchanged. The same `Date` header is also read to build the "Version hors ligne du {day} {month}, {H} h {MM}" banner injected via a `<body>`-tag string replace on cache-hit responses — a real sentence at the top of the page, not a badge, and injected by the worker (not server-rendered) since the identical HTML is served whether the request succeeds live or is replayed from cache, and only the worker knows at serve time which one this is.

**A redirected response is never cached** (`response.redirected` check before `cache.put()`): an identified-only whitelisted page (`/notifications`, `/trombinoscope`, or now `/account`/`/members/{id}`) hit with a stale/expired session bounces to `/login`, and `fetch()` follows that redirect transparently — caching the result under the *original* whitelisted URL would silently serve the login page back as if it were the real content the next time it's read from cache while offline.

**Staff photos, retired bespoke route**: the trombinoscope's offline pre-download used to need its own narrow, explicitly-documented exception to "every download goes through `FileAccessGuard` via `/files/{id}`" (`GET /api/offline/photo/{member_id}`, `Core\Photo\StaffThumbnailProcessor` deriving a square ~160px WebP on demand) precisely because `/files/{id}` had no cacheable, already-small rendition of a photo to point the pre-download at. §8.39's `GET /files/{id}/thumb` is that rendition — generated once at upload, not on demand — so the bespoke route and processor were retired entirely in the prompt that introduced §8.39, and this lot folds the surviving manifest route (`/api/offline/photo-manifest`) into the wider `/api/offline/manifest` above, deleting the narrower one. Every URL the manifest lists still goes through the exact same `FileAccessGuard` check as any other request to that route once `offline-prefetch.js` actually fetches it — the manifest only ever lists candidates, it grants no access of its own.

### 8.26 Scout year transition (`Core\ScoutYear`, Espace chefs d'U)

Annual transition from one scout year to the next through a guided, phased workflow (`Core\Http\Controller\ScoutYearController`, `/admin/scout-year`, `role_min: admin`; the workflow itself lives in `Core\ScoutYear\ScoutYearTransitionService`). Three year types exist simultaneously: **public year** (the year visible to identified members and public visitors), **staff year** (optional override for chiefs/intendants, letting staff prepare the next year while members see the current year), and **preview year** (session-only override for admins to view any year).

`Core\ScoutYear\ScoutYearResolver::getEffectiveYear()` determines which year a request sees, in precedence order: preview year (if set in session via `ScoutYearSession::setPreview()`) → staff year (if role is chief/intendant and `ScoutYearAdminService::getStaffYearId()` returns non-null) → public year (fallback). The public year is stored in `SettingService` (`current_scout_year_id`), the staff year likewise (`staff_scout_year_id`), and preview is purely session state — never persisted.

**Transition workflow** (Espace chefs d'U > Année scoute page): the season's whole checklist, not only the four site-level switches. `ScoutYearTransitionService::buildWorkflow()` returns it — three phases (`preparation`, `desk`, `site`) and fourteen steps at full module coverage — recomputed on every request and never cached. The four site-level ones are unchanged: preview the target year session-only (other users unaffected), import Desk CSV for it (verified by member count > 0), activate it for chiefs/intendants via `ScoutYearAdminService::activateStaffYear()` (identified members and public still see the current year), then transition the entire site via `activatePublicYear()` (staff year automatically cleared). The other ten cover the work around them: the registration module's Départs/Passage/confirmation pages, the encoding done inside Desk itself (new staff, members, fees), and the site content a new year needs (éphémérides, badges, trombinoscope, staff photos).

**The order is advice, not a gate.** Only two conditions stop anything, both real: a public year cannot be activated without a staff year, and the registration module's veto (§8.38). Every other control stays enabled at all times — a fourteen-step workflow that locked each step behind the previous one would be unusable the first time a unit did something in a different order.

**"Done" has exactly two sources.** Either the site can observe it (`sessionPreviewId === target`, `countMembers(target) > 0`, staff/public year settings, every configured section photographed for the target year via `SectionPhotoRepository::countSectionsWithPhotoForYear()`, zero unassigned passages, at least one calendar event inside the target year's date range), or a human ticked it off (`scout_year_transition_steps`, `ScoutYearTransitionStepRepository` — row presence *is* the state, unticking deletes, everything keyed by target scout year so next year's run starts blank with no reset step). A step with a signal keeps its checkbox as an override, so a unit whose signal will never fire is never stuck. The four site-level switches are auto-only and have no checkbox at all: `POST /admin/scout-year/step` refuses their keys server-side (`isManualStep()`), so a forged request cannot make the page claim the public year moved when it did not. It also refuses any step whose module is disabled.

**Optional-module steps disappear rather than grey out** (ARCHITECTURE.md §7.5): `registration` owns `departures`/`passage`/`confirm_registrations`, `calendar` owns `ephemerides`, `trombinoscope` owns its namesake. The service takes `ModuleManager::getEnabledModuleIds()` as plain data plus two nullable providers — `Modules\Registration\Api\ScoutYearPreparationProvider` (how many passages, how many still without a destination) and `Modules\Calendar\Api\ScoutYearEventCountProvider` (events inside a date range). Because two different modules now feed this one page, `ScoutYearController` is registered **once, after every module block** in `public/index.php` rather than re-registered inside each — registering it per module would have made the page's contents depend on which module happened to be wired last.

**The Desk-encoding date is a signpost, nothing more.** `scout_year_desk_encoding_date` (MM-JJ, default `08-15`, editable) is placed in the target year's own start calendar year and labels the two dated phases plus which one the calendar is currently in. It disables nothing, activates nothing, triggers nothing; a malformed value falls back to the default rather than taking the page down. **The transition is manual-only, year-round** (itération 3): the final step is never date-gated, and nothing switches the public year on its own. This is deliberate, not an oversight — the "registration" module (itération 7, §8.38) vetoes it while registration requests are still open, and an automatic date-driven switch would have bypassed that veto outright (a date calculation can't be told "not yet"), so the two were incompatible by design and manual won. `ScoutYearAdminService::activatePublicYear()` is still the sole write path to the public-year setting, so that one veto check point is never bypassable by construction. Each step is journaled (`scout_year_staff_activated`, `scout_year_public_activated`, etc., level `security`; the manual ticks as `scout_year_step_marked`/`scout_year_step_unmarked`, level `info`) — a blocked activation instead journals `scout_year_public_activation_blocked` (§8.38).

`ScoutYearTransitionService` is the specification for `tests/e2e/specs/scout-year-transition.spec.js`, which replays the whole workflow in a real browser and blocks CI and `scripts/release.sh`'s E2E gate; the service, the template and the test each carry a cross-reference to the other two.

Without an automatic catch-up, a unit that forgets to run the transition would stay on a stale public year indefinitely with no visible sign. The Année scoute page surfaces this with a **non-blocking warning** (`ScoutYearController::index()`'s `public_year_ended`, true once the public year's `end_date` has passed) inviting the admin to run the workflow — never blocking, never itself changing anything.

This still leaves a genuinely separate concern working exactly as before: a **fresh install with no public year configured yet** (`current_scout_year_id` unset) needs a plausible starting year to boot with. `ScoutYearResolver::getCurrentPublicYear()`'s fallback to `ScoutYearService::getCurrentYear()` (auto-creating the date-computed year on demand) handles this on its own and was never part of the automatic-switch mechanism that got removed — the two were always independent code paths in this codebase, not two responsibilities of one method that needed splitting apart.

**Member search** (`Core\Member\Controller\MemberSearchController`, `/admin/members`, same Espace chefs d'U menu) searches members of the effective scout year only — name/email/phone via `MemberSearchService::search()`, with optional detail view showing full personal data and effective age (birth year + scout year offset). The offset adjustment (`POST /members/{id}/scout-year-offset`, `role_min: chief`) is the one chief-level override for age-vs-section mismatch (`member_years.scout_year_offset`, −1/0/+1) — journaled as `scout_year_offset_updated`.

**Departure marking from the detail card too, not only from the registration module's "Départs" page**: `POST /members/{id}/departure` (`role_min: admin`, `Core\Http\Controller\MemberController::updateDeparture()`) reuses the exact same `Core\Member\DepartureService` the registration module's "Départs" page (ARCHITECTURE.md §8.37) already writes through — the same `member_years.leaving`/`leaving_comment_encrypted` fact, never a second copy. The point of exposing it here too is reach, not a different feature: Départs only ever lists the *animés* of a section the acting account actually staffs, while this admin-only member-search page can look up *any* member — staff included — so a chief d'unité can mark someone as leaving even when they're not reachable through Départs at all. Because `Core\Member\DepartureService` is a plain core fact about a `member_year` (its own docblock: "not inscriptions-specific"), it's now constructed once at core level in `public/index.php` (previously only instantiated inside the registration module's own conditional block, since that page was its only consumer) — `MemberController`/`MemberSearchController` both take it as a constructor dependency unconditionally, so the control still works with the registration module disabled.

**"Animé" role filter — chief/admin/intendant excluded, not just chief/admin**: `Core\Member\SectionService::getSectionAnimes()`, `Modules\Registration\Service\PassageService::getAnimeMemberYears()`, and `ForecastService::countDeparturesForYear()` each independently filter `member_functions.role` down to non-staff — all three originally excluded only `chief`/`admin`, missing `intendant` (`Core\Http\Controller\FunctionsController::ROLE_DEFINITIONS`'s five function roles: `public`/`identified`/`intendant`/`chief`/`admin`), so a member tagged with the Intendant function was counted as an animé on Départs, Passage, and the Prévisions projection alike. All three now exclude `intendant` too — deliberately three separate copies of the same three-value list rather than a shared constant (no natural shared home across `Core\Member` and two different `Modules\Registration` services), each cross-referencing the other two in its own docblock so the next person extending this list updates all three together.

### 8.27 Member email management (`Core\Member`, self-service only)

Members manage their own secondary email addresses (`Core\Http\Controller\MemberEmailAddressController`, routes under `/members/{id}/emails/*`, `role_min: identified` but further gated by `MemberEmailAddressController::requireOwnMemberId()` on every action — no chief/admin bypass, except for an active temporary member override (§8.42), which `MemberService::canAccess()` honours and which therefore lets an admin manage that member's addresses on their behalf). `Core\Member\MemberEmailRepository` stores addresses in `member_emails` (`BLOB`-encrypted via `EncryptionService`, blind-indexed for lookup), with three states: **pending** (added but not yet confirmed — verification email sent), **active** (confirmed and usable for login), **deactivated** (previously active but deactivated by the member — can be reactivated without re-verification).

**Adding an email**: `POST /members/{id}/emails` sends a verification email via `MailService` with a unique single-use link (15-minute expiry, `MemberEmailToken` table, token hashed). `GET /members/emails/confirm/{id}` (`role_min: public`, unauthenticated — same pattern as password reset) validates the token and activates the address. **Resend**: re-sends verification for pending addresses. **Reactivate**: restores a deactivated email to active without re-verification. **Delete**: removes pending or deactivated emails (active emails must be deactivated first to prevent accidental deletion). All mutations journaled (`member_email_added`, `member_email_confirmed`, `member_email_deactivated`, level `info`, never the email text itself — only the member id).

`Core\Security\RoleResolver::resolveForEmail()` already checked all active `member_emails` rows alongside `member_years.email` for role calculation — this feature simply exposed the self-service UI for a table that was already consulted at login.

### 8.28 Section documents (`Core\Member\SectionDocumentService`, Staffs page)

Chiefs attach PDF documents to sections per scout year (`Core\Http\Controller\SectionDocumentController`, routes under `/chefs/staffs/documents/*`, `role_min: chief`) — displayed on the Staffs page and each member's own page (filtered by the member's scout year and section). `Core\Member\SectionDocumentRepository` stores metadata (`section_documents`: section_id, scout_year_id, title, file_id, sort_order); the actual PDF is a `files` row with `role_min: 'identified'` uploaded via `UploadHandler` (MIME validation, only `application/pdf` allowed).

**Operations**: `POST /chefs/staffs/documents` (add — upload + title + section/year selection, optional Ghostscript compression if available on server, warning displayed for large files when compression unavailable), `POST /chefs/staffs/documents/reorder` (drag-and-drop or move up/down to change `sort_order`), `POST /chefs/staffs/documents/{id}` (update — change title or replace PDF file), `POST /chefs/staffs/documents/delete` (delete — removes both the `section_documents` row and the underlying file). All mutations journaled (`section_document_added`/`updated`/`deleted`, level `info`).

Documents are scoped by section and scout year — each year has its own set. `Core\Pdf\PdfCompressor` (wraps Ghostscript `gs` if present, fallback no-op when absent) reduces file size via `PdfCompressor::compress($sourcePath, $targetPath)` before storage; `PdfCompressor::isAvailable()` self-tests the binary once per request and caches the result. The Staffs page lists documents per section with download links (`/files/{id}`), and `Core\Member\MemberPageService::buildPageData()` includes them in the member page's section card (via `SectionDocumentService::findBySection AndYear()`).

### 8.29 Account identity vs. notifications — one destination each, everywhere (`partials/account_avatar.html.twig`, `partials/notification_dropdown.html.twig`)

**Every avatar and every display of the current user's name, in all three nav surfaces (mobile header, mobile offcanvas user card, desktop bar), links to `/account` and nothing else.** This was previously inconsistent — the mobile header's avatar already went to `/account`, but the offcanvas card's avatar and the desktop bar's avatar both linked to `/notifications` instead (an earlier, narrower fix covered only the mobile header, see git history for that lot) — the two concerns (identity vs. notifications) were conflated in the same clickable element. `partials/account_avatar.html.twig` renders only the initials circle itself (parameterized by `size`/`font_size`), never a badge and never a link — the call site always wraps it in `<a href="/account">` alongside the display name, so a tap/click on either the picture or the name goes to the same place.

**Notification indication** is now a fully separate element, `partials/notification_dropdown.html.twig`: a bell icon carrying the `.notification-badge` unread-count pill (same class `notification-badge.js` already updates everywhere via `querySelectorAll`, 60s poll + immediate refresh on the service worker's `postMessage`), opening a Bootstrap dropdown (native `data-bs-toggle="dropdown"`, no extra JS — `bootstrap.bundle.min.js` is already loaded) that shows: the unread count, the single most recent *unread* notification (`Core\Notification\NotificationRepository::findLatestUnread()` — deliberately unread-only, not just "most recent overall", since the newest notification can already be read while an older one still isn't) as a clickable row using the same "row is its own tiny POST form" mark-read pattern as `/notifications` itself (a plain `<a>` can't carry CSRF protection for that side effect), and a "Voir toutes les notifications" link into the full centre — rendered unconditionally, after the unread-count/empty-state branch rather than inside it, so a visitor with nothing unread can still reach the full centre from here exactly like one with unread notifications can. Empty state ("Aucune notification") when nothing is unread. One Twig partial, included identically at all three call sites — never duplicated markup. `latest_notification` (a `?NotificationRecord`, only fetched when `unread_notifications_count > 0`) is a `public/index.php` Twig global alongside the pre-existing `unread_notifications_count`.

**`/notifications`' own read/unread row indicator** (`core/View/templates/notifications/index.html.twig`): a small leading circle, filled (`bg-primary`) for an unread row and empty for a read one — both states render the *exact same* `<span>` (same classes, same inline `width`/`height`/`margin-top`/`flex-shrink`), only the `bg-primary` class differing, rather than two structurally different elements (a `.badge` for unread, a bare unstyled `<span>` for read) that used to end up with different effective box sizes — a plain `<span>` is `display: inline` by default and silently ignores an explicit `width`, while Bootstrap's `.badge` is `inline-block` and honors it, so the two rows' text started at different horizontal positions depending on read state. Structural identity, not just matching numbers, is what guarantees this can't regress the same way again.

**Breadcrumb bar** (`partials/breadcrumb_bar.html.twig`, included in `base.html.twig` right after the header): always visible on mobile viewports (below the site's `lg` breakpoint, 992px — the same one `partials/nav.html.twig` and `public/assets/js/breadcrumb.js` already use), and on desktop only when the site runs as an installed PWA. Visibility is 100% CSS (`public/assets/css/app.css`'s `.breadcrumb-bar` rule: `display: none` by default, `display: flex` under `@media (max-width: 991.98px)` **or** `@media (display-mode: standalone)`) — no server-side flag, no JS detection, never a security boundary (SECURITY §3, same principle as menu visibility). The first segment (a home icon linking to `/`) is always hard-coded, never sourced from `SettingService` or any config.

Each route — core or module — can optionally declare a breadcrumb: `Core\Http\Router::addRoute()`'s 6th argument (`?array{label: string, parents: array<string>}`), or module.json's `routes[].breadcrumb` (validated by `Core\Module\ModuleManifest::validateBreadcrumb()`, same optional-key pattern as `notifications`, §8.24) — a single mechanism for both, since `Core\Module\ModuleManager::loadModule()` feeds a module's declared breadcrumb through the exact same `Router::addRoute()` call core routes use directly in `public/index.php`. A route with no `breadcrumb` key is not an error: the trail simply stops at the home icon. `Core\Http\FrontController::handle()` sets the `route_breadcrumb` Twig global right after the RBAC check succeeds (never before — a 403 page must never leak the trail of a page the visitor couldn't reach) and right before invoking the controller action, so it's available by the time the template (including the included breadcrumb partial) renders. A Controller can override the route's static `label` per-request with a `breadcrumb_current` context variable for a dynamic title (e.g. `MemberController::show()` passes the member's `getDisplayName()`).

`parents` are ancestor labels naming a *menu* (`Core\View\MenuBuilder`'s own `label`, e.g. `"Espace chefs"` — core routes get this via `MenuBuilder::labelFor()` rather than a hardcoded copy, see §7.1) — declared as plain strings, never a URL. A parent is never a link to a specific page: most menu categories have no single landing page of their own, and even the ones that do would send every visitor to the same arbitrarily-chosen page regardless of what they actually wanted. Instead, clicking a parent **opens that menu's own section** — the desktop submenu bar, or the mobile offcanvas with the matching accordion expanded — letting the visitor pick the sub-page themselves, same as using the nav directly (an earlier version of this partial tried to resolve a parent to a specific "first real page" to link to, which meant Espace chefs' only page linking back to itself, or an Espace animés visitor being sent to a specific member's page rather than the section they actually wanted — both fixed by this redesign). `partials/breadcrumb_bar.html.twig` renders a parent as a `<button data-open-menu="{menu.id}" class="breadcrumb-parent-btn">` only when its label actually matches one of the current `menus` (the same global the nav itself renders from); otherwise it stays plain text — never an invented menu id. `public/assets/js/breadcrumb.js` wires the click: at `min-width: 992px` (matching Bootstrap's own `lg` breakpoint, same one `partials/nav.html.twig` uses to switch between the mobile and desktop surfaces) it calls `window.ScoutMagicNav.showDesktopMenu(menuId)` — a function `public/assets/js/nav.js` now exposes specifically for this, rather than simulating a raw click on the `.desktop-menu-btn` (which would *toggle* an already-open menu closed instead of ensuring it's open); below that width it opens the mobile offcanvas (`bootstrap.Offcanvas`) and, once it has finished opening, expands the matching accordion section (`bootstrap.Collapse` on `#mob-{menuId}`).

**`breadcrumb_trail`: real links, deliberately different from `parents`.** A Controller can pass this context variable — `array<int, array{label: string, url: string}>` — for one or more ancestor segments between the menu-parents and the active current page, each rendered as a genuine `<a href>`. This is not a reopening of the "link to a specific page" idea `parents` deliberately dropped: a trail entry never names a menu category (where "the specific page" is ambiguous), only a specific, already-known page within the same controller's own page family — e.g. `Modules\Groups\Controller\GroupController::show()`/`gallery()` and `GroupMemberController::index()` all pass `[['label' => 'Groupes', 'url' => '/groups']]` (plus, one level deeper on the member/gallery pages, the group's own name linking back to `/groups/{id}`) so a visitor inside one group can get back to the group list, or the group itself, in one click — something the menu-opening button can't do, since "Espace animés" holds staffs/trombinoscope/member-stats too, not just groups. `breadcrumb_current` still names the trail's own final, non-link segment exactly as before.

Every GET page in "Espace chefs d'U" (`/config/general`, parent `MENU_ESPACE_ADMIN`) and the entire Configuration space (`/setup`, `/config/modules`, `/config/badges`, `/config/functions`, `/config/settings`, `/config/rgpd`, `/config/scheduled`, `/config/maintenance`, `/config/notifications`, all parent `MENU_CONFIGURATION`) now declares a breadcrumb — these previously had none at all, so the pages using them showed no trail. The gallery module's album form (`modules/gallery/module.json`'s `/gallery/create`, `/gallery` POST, `/gallery/{id}/edit`, `/gallery/{id}` POST) got the same treatment: a static `"Nouvel album"`/`"Modifier l'album"` label (parent `"Espace chefs"`), with `GalleryChiefController::formContext()` overriding it via `breadcrumb_current` to the real album title on edit (falling back to the static label via Twig's `default()` on create, same pattern as News's `editorContext()`) — the breadcrumb now covers the "go back to the album list" need the form's own `<a href="/gallery/manage">Retour</a>` button used to serve, so that button was removed from `album_form.html.twig`.

Every module page declares a `breadcrumb` (Calendar in all three variants, Finance, Gallery, Trombinoscope, Mass Mail, News, Retro, Member Stats, SOS Staff d'U, Banner config, LLM connector config), same mechanism as core — none is left without one. **News was a real gap, since fixed**: only its two list routes (`/news`, `/news/manage`) declared a `breadcrumb` — every route that actually renders an article, its embedded form, or the article editor (`/news/{id}`, `/news/{id}/create|edit`, the `POST` routes that re-render those same templates on a validation error, and the form-response pages) had none at all, so `route_breadcrumb` resolved to `null` and the whole trail collapsed to just the home icon. Fixed by declaring a `breadcrumb` on every one of those routes and, mirroring `MemberController`'s pattern, having `NewsController::show()`/`editorContext()`/`FormController::submit()` set `breadcrumb_current` to the article's real title rather than a static, uninformative label.

**`breadcrumb_current` on picker-driven pages**: a `partials/section_picker.html.twig` (Staffs, Trombinoscope) or a bespoke equivalent (Calendar's calendar-picker, Finance's account picker in `_nav.html.twig`) changes what a page shows via a query string (`?section=`, `?calendar=`, `?account_id=`) without changing the route itself — so the route's static `breadcrumb.label` alone ("Staffs", "Calendrier", "Finances") would be stale the moment a visitor switches the picker. Each of these controllers (`StaffsController`, `Modules\Trombinoscope\Controller\TrombinoscopeController`, `Modules\Calendar\Controller\CalendarChiefController`/`CalendarPublicController`, `Modules\Finance\Controller\DashboardController`) resolves the picker's current selection the same way it already does to render the page, then sets `breadcrumb_current` to `"{static label} · {selection name}"` (e.g. `"Calendrier · Louveteaux"`) rather than replacing the label outright — unlike `MemberController::show()`, where the static label ("Membre") carries no information worth keeping, the picker's own page name is still meaningful context alongside which section/calendar/account is selected.

### 8.30 Chip picker (`partials/chip_picker.html.twig`, `public/assets/js/chip-picker.js`)

Replaces the horizontal-scroll picker pattern (`overflow-x-auto` + `flex-nowrap` below `lg`, invisible off-screen items, no scroll affordance) with wrapping chips capped at 2 lines plus a "+N" overflow chip opening a Bootstrap bottom-sheet (`offcanvas-bottom` + `list-group` — no custom dropdown, AGENTS.md) for the full list. Core, content-agnostic component, same precedent as `partials/list_editor.html.twig` (§8.13): it has no notion of what an item *is*, only a normalized shape (`id`, `label`, optional `sublabel`/`color`/`badge`, `selected`) and a `mode` (`single`/`multi`). See `docs/module-development.md`'s own section for the full caller-facing contract — this entry covers the implementation.

**Truncation is entirely client-side** (`chip-picker.js`): the partial always renders every chip unconditionally (progressive enhancement — a no-JS visitor sees and can operate every item), and the script measures each chip's real `offsetTop` after render to group them into lines — never a hardcoded chip count, which would break with label length or viewport width. Only active below the `lg` breakpoint (992px, matching Bootstrap's own); at `lg` and up chips wrap fully with no cap at all, identical to this site's pre-existing desktop picker behavior (verified against the code before assuming, not guessed). Selected chips are always moved to the front of the DOM before measuring, so the current selection is structurally never in the "hidden" group; if the selection itself spans more than 2 lines (`multi` mode with many picks), the cutoff extends to cover all of it rather than hide part of a selection. Recomputed on `resize`/`orientationchange`, debounced.

**Selection paths**: `mode: single` needs no JS for the actual selection — chip and sheet row are the literal same `<a href="{{ base_url }}{{ item.id }}{{ extra_query|default('') }}">`, so there is structurally only one path, not two implementations kept in sync. `mode: multi` chips/rows are `<button>`s; a single delegated click handler (shared between the chip row and the sheet, `.chip-picker-item`) toggles `data-selected`/`aria-pressed` on both the chip and its sheet-row counterpart together and dispatches a `chip-picker:change` `CustomEvent` (`detail: { selectedIds }`) on the picker container — the component never persists a selection itself, that's entirely the caller's responsibility, listening for the event. The sheet stays open across `multi` toggles (none of its selectable rows carry `data-bs-dismiss`) — only the dedicated "Fermer" button does, so Bootstrap's own offcanvas dismiss only fires there.

**Existing callers, refactored into thin mapping layers with unchanged public include signatures** (no existing call site touched): `core/View/templates/partials/section_picker.html.twig` (sections → items, `mode: single`; `color` always forwarded from `Core\Member\SectionService::colorForSection()`, never recomputed; a section with no configured `name` gets a `badge: 'Non configurée'`, sheet-only) and `modules/calendar/views/partials/calendar_picker.html.twig` (`Service\CalendarPickerService::buildOptions()`'s options → items, `mode: single`, `extra_query` preserves the month param across picks). Both remain genuinely thin: neither owns chip/sheet/truncation markup or logic, only the domain-to-item mapping. The calendar picker was, and remains, single-select ("Mes évènements" or exactly one calendar) — there is no multi-select "show several calendars at once" feature in this codebase; `module.json`'s `cookies` array for `calendar` stays `[]`, unchanged, since this migration introduces no new persistence and no new cookie.

**Third `mode: single` caller**: `modules/finance/views/_nav.html.twig` (the espace_chefs Finances pages' page picker — the 5 finance sub-pages — and its account picker), replacing a raw `overflow-x-auto`/`flex-nowrap` button row with no scroll affordance, the exact anti-pattern this component exists to replace. The page picker maps each static page to an item whose `id` is the page's own path (`/finance`, `/finance/movements`, ...) with `base_url: ''` — `chip_picker` never assumes `id` is numeric, so a full relative URL works as directly as a query-param id does. The account picker instead follows the numeric-id/`base_url` pattern (`base_url: current_path ~ '?account_id='`), same as the calendar picker.

**First `mode: multi` caller**: the Staffs page's per-member badge picker (`core/View/templates/chefs/staffs.html.twig`) — one `chip_picker` instance per staff member (`picker_id: 'badge-picker-' ~ member.memberYearId`), replacing what used to be a plain `.badge-toggle-btn` row that grew unbounded with the number of active badges (the same "takes too much vertical space on mobile" problem the picker itself was built to solve). Since the site's badge-assignment endpoint (`POST /chefs/staffs/badge-toggle`) toggles exactly one badge per call and returns `{success, assigned}`, the page's own `chip-picker:change` listener diffs the event's full `selectedIds` against the selection it last committed to find the single id that changed, rather than trying to reconcile a whole-set request against a single-item endpoint. On a server rejection it must revert the chip/sheet-row visual state chip-picker.js already flipped optimistically — this is what `window.ChipPicker.setSelected(pickerId, id, selected)` (chip-picker.js's one exported function, added for this) exists for: it applies the same visual update `chip-picker.js`'s own click handler does, but never dispatches `chip-picker:change` itself, so correcting a rejected toggle can never loop back into the caller's own listener. Any future `mode: multi` caller with the same "one id per persistence call" shape can reuse it the same way.

`chip-picker.js` loads unconditionally in `base.html.twig` (not gated behind `is_authenticated`), since the public calendar page (`role_min: public`) uses a chip picker too.

**Notification-centre/push bodies name which calendar the event belongs to** (`Service\CalendarNotificationService::dispatchEventNotification()` for "Nouvelle activité"/"Activité modifiée", `Task\EventReminderHandler` for "Rappel d'activité") — the event's own title alone is frequently ambiguous, since several sections often reuse the exact same generic title ("Réunion normale"). The published/changed path reuses `CalendarService::labelsByCalendarId()` (the single source of truth for "what do we call this calendar", already used by the calendar picker and the event bars themselves) since it already holds a `CalendarService`; the scheduled reminder handler — no persistent DI container, same constraint as every other task handler — resolves it with its own small `resolveCalendarName()` copy, the same section-name-or-Desk-code-fallback logic `Task\AutoCreateRetroHandler::resolveCalendarName()` already has (small tolerated duplication, same precedent).

**A real bug, found and fixed while investigating a user report on `/chefs/calendar`'s event dialog**: `.modal-dialog-scrollable` relies on `.modal-header`/`.modal-body`/`.modal-footer` being direct flex children of `.modal-content` (itself `display: flex; flex-direction: column; max-height: 100%; overflow: hidden`) so `.modal-body`'s own `overflow-y: auto` has a bounded height to scroll within. Any dialog whose submit button lives in the footer needs both wrapped in one `<form>` — but a plain `<form>` has no `overflow` of its own, so per the flexbox spec its automatic minimum size is its content size, not 0: it never shrinks to fit the remaining space, `.modal-body`'s internal scroll never engages, and the footer (the save button) ends up pushed below the visible viewport with no way to reach it on mobile. Fixed everywhere this pattern occurred (`modules/calendar/views/chief.html.twig`'s event dialog, `modules/finance/views/config/categories.html.twig`'s category and rule dialogs — the only three `<form>`-wrapped `.modal-dialog-scrollable` bodies in the codebase, confirmed by auditing every `modal-dialog-scrollable` occurrence, not just the one reported) by giving the form itself `class="d-flex flex-column flex-grow-1" style="min-height:0;"`, making it a proper flex column so `.modal-body`'s scroll and the footer's fixed position both work as `.modal-dialog-scrollable` intends. The other `modal-dialog-scrollable` dialogs in the codebase (`partials/rich_text_editor.html.twig`, `modules/finance/views/movements/list.html.twig`'s two, `modules/mass_mail/views/_compose_dialog.html.twig`) never wrap `.modal-body`+`.modal-footer` in a `<form>` at all (JS-driven save via a plain button, not a native submit) and were never affected.

### 8.31 Public form protection (`Core\Security\HumanCheck`)

Generic, module-agnostic anti-bot protection for a public form submitted by a non-identified session — introduced for three integration points (magic-link request, news module public form responses, and the component's own Twig partial as the reusable surface any future module drops into its own form), no captcha, no external service, no client-side behavioral analysis. Three cumulative barriers, none visible to a human — an identified session skips all three unconditionally, an explicit requirement rather than an optimization.

1. **Honeypot** — a real `<input>` (never `type="hidden"`, which bots skip over) hidden from a human only via a CSS class (`.hc-trap`, `public/assets/css/app.css`, never an inline style — SECURITY.md §9's CSP), with `tabindex="-1"`/`aria-hidden="true"`/`autocomplete="off"` so neither keyboard navigation nor a screen reader ever reaches it. A human never fills it; a bot's naive form-filler does.
2. **Minimum delay, capped by a maximum age** — a submission received less than N seconds after the form was rendered is rejected (probable bot); one received after the configured validity window has elapsed is rejected as expired (probable replay of a long-stale page).
3. **Per-IP sliding-window rate limit** — beyond N submissions from the same IP within the configured window, reject.

**Stateless by design**: the honeypot's field name and the render timestamp travel inside the form itself (`Core\Security\HumanCheck\HumanCheckChallenge`), HMAC-signed via `EncryptionService::blindIndex()` — the same technique every blind-indexed lookup in this codebase already uses, keyed off the existing `blind_index_key` (itself derived from the master key via `secrets.enc`, §1). Nothing is stored server-side for the challenge itself: a session-bound challenge would break the moment a visitor has two tabs open, or a PWA is restored from a frozen state, which is exactly why the signature — not a session lookup — is what prevents a forged timestamp. `HumanCheckService::verify()` never touches `$_SESSION`/`$_POST` (§13): the Controller reads the request, decides whether the session is identified, and passes both in as plain parameters — "this person is identified" is always an input to the service, never something it resolves itself.

The one piece of real server-side state is the third barrier's counter: `human_check_rate_limits` (`schema/core.sql`, migrated automatically like every core table, §10 — no module version bump needed) stores only an `ip_hash` (HMAC via `blindIndex()`, same technique as the blind index on encrypted email — the IP address itself, personal data, is never stored in clear) and a `form_key`. `Core\Security\HumanCheck\Task\PurgeHumanCheckRateLimitsHandler` (`core`/`purge_human_check_rate_limits`) deletes rows older than the current window and self-reschedules for the next day — same pattern as `Core\Notification\Task\PurgeNotificationsHandler`/`Core\Maintenance\Task\AutoBackupHandler` (`Core\Scheduler` has no first-class recurring-task concept) — registered directly in **both** `public/index.php` and `public/cron.php` (§8.17/§8.20 document two real production bugs from registering a handler in only one of the two).

Four `SettingService` keys (core, no module — `human_check_min_delay_seconds` default 3, `human_check_form_validity_seconds` default 14400, `human_check_rate_limit_window_minutes` default 10, `human_check_rate_limit_max_attempts` default 5), each with a French `description`.

A rejection never reveals which barrier tripped — same generic French message regardless of `HumanCheckResult::$reason` (an internal string, for the journal only) — and never loses the visitor's input: both call sites re-render the same form (a fresh `HumanCheckChallenge`, the previously-entered values still there) rather than a dead-end error page. Every rejection journals a single `human_check_failed` entry (`level: security`, context `{'form': $formKey}` only — no IP, no honeypot content, nothing that could identify the submitter; `event_log.ip_address` still gets populated the same way it does for every journal entry, §11, this is only about not *also* duplicating it into `context` the way a few other `log()` call sites do).

`partials/human_check_fields.html.twig` is the entire integration surface for a new caller: `{% include 'partials/human_check_fields.html.twig' with { human_check: human_check } %}` inside the `<form>`, where `human_check` is whatever `HumanCheckService::generateChallenge($formKey)` returned (or `null` for an identified session — the partial then renders nothing). One `verify()` call in the Controller on submit, same generic rejection handling either way — no interface, no per-module wiring, since this is core calling core, not a module boundary (§7.4/§7.5 don't apply here).

**Magic-link request (`POST /login/magic-link`, `Core\Http\Controller\AuthController`)**: only the honeypot and minimum-delay barriers apply (`verify(..., enforceRateLimit: false)`) — `AuthService::requestMagicLink()` already rate-limits by email blind index (SECURITY.md §8, `MAX_REQUESTS_PER_HOUR`), a differently-scoped counter for the same abuse pattern; stacking a second, IP-scoped counter on top would produce inconsistent thresholds and unexplained lockouts (e.g. a school's shared IP hitting the per-IP ceiling while individual emails are each still well under their own limit). The honeypot and delay checks are still worth applying independently: they reject a naive bot before it ever reaches `AuthService`, at zero cost to a legitimate slow human.

**News module public form responses (`POST /news/{id}/form/submit`, `Modules\News\Controller\FormController`)**: all three barriers apply — the module has no rate limiting of its own for anonymous responses. `Modules\News\Controller\NewsController::show()` generates the challenge for the article page's render; a rejection re-renders `@news/detail.html.twig` (same path as an existing `NewsException` validation failure) with a fresh challenge, refactored into one shared `rerenderFormWithError()` helper.

### 8.32 Departure marking (`Core\Member\DepartureService`)

A chief or animateur can flag a member_year as "won't be back next scout year" while Desk still lists them active this year — feeds place/headcount projections. Shipped ahead of its first screen; the registration module's "Départs" page (§8.37) is the actual consumer, added later. `DepartureRepository::updateComment()` (added alongside that page) updates only the comment column, independently of `markLeaving()`/`unmarkLeaving()` — see §8.37 for why that split exists.

Three columns on `member_years` (`leaving` boolean, `leaving_marked_at`, `leaving_comment_encrypted`), migrated automatically like any core table (§10, no module version bump — this isn't a module's `schema.sql`). Scoped to the marked row's own scout year on purpose: a new Desk import creates a fresh `member_years` row for the next year with `leaving` defaulting to false, so the marker resets naturally — no purge task, and re-importing the *same* year never wipes it, since `MemberYearRepository::upsert()`'s explicit column list never touches these three.

`leaving_comment_encrypted` is a free-text reason — often sensitive (a conflict with a leader, a family situation, a child's difficulties, sometimes health) — so it is `BLOB` + encrypted exactly like `handicap_encrypted` on the same table, encrypted/decrypted only in `DepartureRepository`, never in the Service, never in a journal entry or error message. `DepartureService::markLeaving()`/`unmarkLeaving()` each journal a single `member_leaving_marked`/`member_leaving_unmarked` entry (`level: info`, context `{'member_id': ...}` only — the *persistent* member id, resolved internally by the Repository so no caller has to thread it through separately, never the comment).

### 8.33 Sections a chief/animateur staffs (`Core\Member\SectionStaffAuthorizationService`)

Answers "which sections is this account a chief/animateur of, for the effective scout year" — a new authorization boundary this codebase didn't have before: RBAC here is otherwise purely hierarchical (`chief` sees whatever `chief` sees; "chief of *this* section" doesn't exist anywhere else). This is not a departure from §2 — it's exactly the case that section describes: the RBAC guard still filters route access up front, and a Controller narrows further onto a specific resource using this service, the same way `MemberService::canAccess()` narrows onto one member. First consumer: the "Départs" page (a future iteration); more will follow, which is why the logic lives here rather than being copied into a controller.

Resolution mirrors `MemberService::canAccess()`: the account's email blind-indexes to its linked `member_years` for the effective scout year, then `member_functions.section_id` for any function whose role is `chief` or `admin` gives the staffed sections. `admin`/`superadmin` (account-level role) get every section unconditionally — the service owns this rule, not the caller. **The same trap `SectionService::getSectionStaff()` already guards against applies here just as directly**: a section's animés carry the *same* `section_id` on their own `member_functions` row as that section's staff, so the role filter (`chief`/`admin` only) is what keeps an animé from being reported as "staff of their own section." The service answers only "which sections" — never "is this allowed" — the decision stays with the caller, which is what keeps it reusable. First (and, as of §8.37, only) consumer: the registration module's "Départs" page.

### 8.34 Address comparison normalization and fee estimation (`Core\Member\AddressNormalizer`, `FeeEstimationService`)

Two members living at the same address suggest a household fee category (one person → normal, two → couple, three or more → family) — always a *suggestion*, never applied automatically: a shared house, two families at one number, shared custody all produce false positives no address normalization can fix, so the service returns both the suggested category and the raw household size it was computed from, for the caller to explain its reasoning.

`AddressNormalizer::normalize()` reduces street+number+box+postal code to a comparison-only string — never displayed, never meant to be readable, its only job is that two different encodings of the same real address produce the same string. Reuses `Core\Member\Service\MemberSearchService::fold()` for lowercasing/accent-stripping (nothing new to invent there) and adds what's missing: **tokenizing on runs of non-alphanumeric characters, then dropping tokens that exactly match a street-type word/abbreviation (rue, r, avenue, av, chaussée, ch, boulevard, bd, place, pl, clos, drève, …) or a French article (de, du, des, la)**. Tokenizing before filtering — rather than a substring replace of "rue"/"du"/etc. against the concatenated blob, the approach this reimplements — is the fix for a real production bug: a substring replace corrupts any word that merely *contains* a stop word as a substring ("Rue Duquesnoy" losing its "du", "Bois du Duc" losing two occurrences instead of one). Word-boundary tokenization only ever drops a token that *is* one of these words. The postal code is never filtered — purely numeric, it can never match an alphabetic stop word, and it carries most of the discriminating power between two genuinely different streets.

Display-side normalization is a different class entirely: `Core\Service\TextNormalizerService::normalizeAddress()` (the `|normalize_address` Twig filter), applied to `Core\Member\MemberAddress::format()`'s already-composed, human-readable line (street/number/box, then complement, then postal/city — that composition order is `format()`'s own job, never something this normalizer decides). Its one non-cosmetic behavior: when the FIRST word of the input starts with a digit — meaning a house number was typed at the front of the street field instead of into its own field ("12 Rue de la Paix" as raw Desk/import data) — `moveLeadingNumberAfterStreet()` relocates it to just after the street name, so the output always reads "street, then number" regardless of which order the underlying data happened to arrive in. It looks for the comma `format()` places between the street/number/box segment and the postal/city segment first (the common case) and inserts the number right before it; falling back to inserting before the next numeric token (a bare "12 Rue X 1000 Ville" with no comma) or, if neither exists, appending it at the very end (a street with nothing else attached).

The comparison value is never stored in clear: `member_addresses.address_normalized_blind_index` (`CHAR(64)`) is an HMAC blind index (`EncryptionService::blindIndex()`, same technique as every other blind index in this codebase) computed from the normalized string, exact-match only. `Core\Import\DeskImportService` computes it at every address write, alongside the existing encrypted fields. `Core\Member\FeeEstimationRepository::countHouseholdMembers()` counts distinct `member_years` (active, for the given scout year, **excluding anyone marked leaving**, §8.32) sharing that blind index — `Core\Member\HouseholdFeeCategory::fromHouseholdSize()` then maps the count to a category. As of registration module iteration 5 (§8.36), `FeeEstimationService` also takes a nullable `?Modules\Registration\Api\HouseholdRegistrationCountProvider $registrationCount = null` (§7.5's "module publishes an `Api` interface, core depends on it optionally" pattern, wired in the composition root only when the module is enabled) and sums in that request's `accepted`/`encoded` registration requests sharing the same address blind index — a caller estimating for a request's own fiche passes that request's own id as `estimate()`'s 6th, `?int $excludeRegistrationRequestId` parameter so a request never counts itself. Degrades to counting existing members only when the module is disabled or `$registrationCount` is null.

**Retroactive backfill, removed at iteration 3**: `schema/core.sql`'s migration is DDL-only (`MigrationRunner` never backfills data), so every `member_addresses` row written before `address_normalized_blind_index` existed had it `NULL` — without a one-time catch-up, `FeeEstimationService` would have silently reported "one person" for every household on any already-installed unit, a result indistinguishable from normal behavior. `Core\Member\AddressBlindIndexBackfill::run()` did the ~250-row catch-up in one single pass, guarded by the `address_blind_index_backfilled` `SettingService` flag, called once from `public/index.php`. Same lifecycle as `schema/drops.sql` (§10): applied everywhere, then retired — the class, its call site, and the setting flag are gone as of iteration 3, while the column itself and its population at Desk-import time (unaffected by this removal) remain.

### 8.35 Registration module — "socle et inscription publique" (`modules/registration`)

Iteration 4 of the "future inscriptions module" §8.34 already anticipated: a public registration page, a form, two automatic emails, and a family-facing tracking page. Deliberately stopped at `status = 'pending'` — staff review/acceptance, Desk reconciliation, and retention/purge were all later iterations; §8.36 below covers the iteration that added them.

**Slot math (`Service\SlotMath`, pure/no-DB, covered by `SlotMathTest`)**: the module's unit of measure is a "slot" — branch × year-in-branch, never a birth year or a section directly. Age brackets (per animé branch: entry age reached at year-in-branch 1, and how many years the branch spans) are **not** module-owned configuration: `Repository\AgeBracketRepository` derives them at read time from the real Desk-imported `age_branches` table matched against `Core\Member\MemberYearService::BRANCHES` — the same federation-fixed constants `member_stats` already uses for an *existing* member's effective-age computation, via the shared `MemberYearService::branchForSortOrder()` lookup (`intdiv(sort_order, 10) - 1` indexes straight into `BRANCHES`). An earlier version of this module kept a separate, admin-editable `registration_age_brackets` table duplicating these same four numbers — removed once the duplication was pointed out (two independently-editable copies of the same federation facts risked silently drifting apart, and the ages aren't specific to registration in the first place). `SlotMath::referenceCalendarYear()` resolves which of a scout year's two calendar years is used for the translation, from a configurable reference day/month (`registration_reference_date` setting, default 31 December) — September-or-later keeps the scout year's start year, earlier rolls to the next one. `Service\SlotService` wraps this against real data: `birthYearsByBranch()` for the public page's "born in..." listing, and `waitlistTiersByBirthYear()` for the optional availability display (`registration_waitlist_enabled`), which nets a slot's configured capacity (`registration_slot_capacities`) against two numbers — the *projected* headcount (existing `member_years`, active, excluding anyone marked leaving §8.32, decrypted and run through `MemberYearService::getEffectiveAge()` to find who currently sits one rank below each slot and will "feed" into it next year) and the count of *accepted* requests already targeting that slot (derived from each request's decrypted birth date via `SlotMath::slotForBirthDate()`, never a stored slot column) — then buckets the remaining estimate into available/limited/heavy via two configurable ratio thresholds. Deliberately `accepted`, not `pending`, as of iteration 5 (§8.36): a still-undecided request might yet be refused, so counting it toward "how full" would mislead both the public display and the admin capacity-verification table, which reuses this exact same counting method (`Service\SlotService::capacityBreakdownForYear()`) so the two can never silently diverge.

**Target year and the in-year code**: a submission normally targets the *next* scout year (`ScoutYearService::ensureYear(ScoutYearService::nextLabel(...))`, auto-created if needed, same precedent as the scout year transition's own auto-creation §8.26). `registration_year_codes` (one plaintext code per scout year — "ce n'est pas une barrière de sécurité", the chief reads it aloud over the phone; `RegistrationYearCodeRepository::ALPHABET` excludes visually confusable characters for exactly that reason) lets a family submit against the *current* year instead, via a collapsed field on the form — `is_active = false` (or no row at all) is the only "in-year registration is closed" mechanism needed, and regenerating a code overwrites it in place so the previous value stops matching immediately.

**The in-year code is its own open/close mechanism, independent of `registration_form_open`, unlocked per browser session**: while the form is genuinely open, an optional inline code field (collapsed behind a toggle, unchanged from earlier iterations) can redirect a single submission to the *current* public year instead of the default *next* year (`Service\RegistrationService::resolveTargetYear(?string $submittedCode)`). While the form is *closed*, that inline field doesn't exist — the closed page shows only the "not open" message and a standalone code-entry form (`POST /inscriptions/code`, `Controller\PublicRegistrationController::verifyCode()`), never the registration form itself. A valid code (`RegistrationService::isYearCodeValid()`, checked against the current public year only) calls `Service\RegistrationYearCodeSession::unlock()`, which stores the unlocked scout year id in `$_SESSION` (`Core\Security\SessionStore`, the same primitive `Core\ScoutYear\ScoutYearSession` uses for its own per-session preview override) — from then on, for that browser session only, the full form renders and targets the current public year, without the code having to be re-entered on a later page load or resubmitted with the actual registration. This is a deliberate session-only scope, not a global toggle: unlike `registration_form_open`, one visitor entering a valid code never opens the form for anyone else. `Controller\PublicRegistrationController::resolveAvailability()` is the single place both `index()`/`buildPageContext()` and `submit()` ask "is the form reachable, and which year does it target" — computed once so the two paths can't drift apart. A submission that's neither open nor session-unlocked re-renders the closed state with a friendly French error (422) instead of a blind 404 — a 404 was harmless when the form was truly unreachable through the UI, but is now a confusing dead end for a client that reached `submit()` some other way (e.g. a stale open tab whose session unlock later expired).

**Per-birth-year waitlist indication (`Service\SlotService::birthYearSlotsForPublic()`)**: the public page's "nés en..." grid and its birth-date-selection preview both need, per birth year, which (branch, year-in-branch) it falls into and its waitlist tier — but must never leak the raw capacity/projected/accepted counts behind that tier (`capacityBreakdownForYear()`'s numbers, staff-only, shown on `/config/inscriptions`'s "Vérification des capacités" table). `birthYearSlotsForPublic()` reuses `birthYearsByBranch()`'s own bracket iteration and `waitlistTiersByBirthYear()`'s own tier computation rather than a third copy of either, and returns only `{birth_year, branch_label, year_in_branch, tier}` per slot. Each branch's birth years render one per line (`<ul>`, not a comma-joined string) with a short badge next to each one ("Disponible" / "Limitée" / "Complet", intentionally terser than the tier names used internally) when `registration_waitlist_enabled` is on — this replaced an earlier separate "Disponibilité des places" summary section entirely (three lists of years grouped by tier, redundant with the per-year info once that existed); the birth-date `<input type="date">`'s `change` handler (`public.html.twig`'s `{% block scripts %}`) looks the entered year up in the same `birth_year_slots` data client-side and shows both the year-in-branch and the same short tier label ("Branche prévue : Louveteaux — 2ᵉ année. Limitée."). The card's own title switches between "Année scoute {label}" (waitlist off — nothing to show beyond which years feed which branch) and "Disponibilités {label}" (waitlist on, with a one-line explanation of what the three badges mean right underneath) — the heading itself communicates whether there's availability information on the page at all, rather than a visitor discovering that only by noticing the badges are absent. `registration_waitlist_enabled` itself now defaults to `1` (was `0`) — showing this information is the expected default, not an opt-in a chief has to discover in Configuration > Paramètres first; `SettingRepository::upsert()` only self-heals a setting's `default_value` column on an existing row, never its live `setting_value` (deliberately, so a chief's own choice is never silently overwritten on upgrade — see its docblock), so this default change only takes effect for installations that register the setting for the first time; an already-running site keeps whatever it already had until a chief flips it themselves.

**Submission and identity data**: every identity field on `registration_requests` (parent and child name, address, phone, email, gender, birth date, remarks) is a `BLOB` encrypted via `Core\Security\EncryptionService`, encrypted/decrypted exclusively inside `Repository\RegistrationRequestRepository` (SECURITY.md §5) — never in `Service\RegistrationService`, the controller, or a journal entry, which only ever logs the request's own id. Three blind indexes exist: on email (tracking-page linkage, §14-style), on normalized last name + first name + birth date (Desk reconciliation, §8.36), and on the normalized address (household fee count, §8.34/§8.36) — **none of the three is ever used to block or refuse a submission**, matching every other blind index in this codebase. The name+DOB one is computed by `RegistrationRequestRepository::normalizeForNameDobBlindIndex()`, itself built on `Core\Service\TextNormalizerService::normalizeName()` (the same deterministic French/Belgian-particle-aware title-casing used for display elsewhere) plus a final `mb_strtolower()` pass for case-insensitive matching — module spec-mandated, not an ad hoc fold function, precisely because §8.36's reconciliation must compute the exact same index for a freshly-decrypted Desk member as this repository computed at submission time. `desired_section_id` is never trusted from the request body directly: the controller re-derives the birth-date-implied branch via `SlotMath::slotForBirthDate()` and silently drops the submitted section to "no preference" unless it actually belongs to that branch. When the submitting session is identified, declared sibling links (`registration_request_siblings`) reference a real `members` row, exactly like `Core\Member\MemberService::getLinkedMembers()`'s own membership model — never a bare account.

**Two automatic emails, one anti-robot gate**: `Service\RegistrationService::submit()` sends a parent receipt (never an acceptance — "Ceci n'est pas encore une acceptation") carrying the tracking link, and, only if `registration_unit_alert_email` is configured, a unit alert containing **the child's first name only** — never the family's contact details — plus the target slot and a link to the request. Both render an editable default body via `Core\View\EditableContentService` with `{{placeholder}}` substitution (never Twig on user-controlled data), and both fail silently into the journal on `MailException` (never blocking the submission itself). `Controller\PublicRegistrationController::submit()` gates on `Core\Security\HumanCheck` (§8.31) exactly like the news module's public form, with the same "never lose the parent's entered data on rejection" sticky-value re-render.

**Tracking page (`Controller\TrackingController`)**: two access paths onto the same underlying request, matching the module spec's "vue minimale par token" vs "vue complète si identifié et rattaché". The public token URL (`/inscriptions/suivi/{id}/{token}`) verifies possession of a `password_hash()`-hashed, non-expiring token (`Service\TrackingService::findByToken()`, same technique as `Core\Member\MemberEmailService`'s own confirmation tokens) and shows only status/child-first-name/received-date. The identified path (`/inscriptions/suivi/demande/{id}`) never persists a session-to-request link — `Service\TrackingService::isLinkedByEmail()` re-derives it on every call from the identified session's own email, blind-indexed against the request's primary address and any **confirmed** secondary one, the same "never persist the link, always re-derive it" approach `MemberService::getLinkedMembers()` already uses for members — and shows the full request plus secondary-email management.

**Secondary emails — module-local, not a generalization of `member_emails`**: mirrors `Core\Member\MemberEmailService`'s shape, states, and `bin2hex(random_bytes(32))` + `password_hash()` token technique exactly, but as its own table (`registration_secondary_emails`) rather than a polymorphic owner on `member_emails` — nothing else in this codebase uses a `(subject_type, subject_id)` owner, every table here is FK'd to one single concrete concept, and a registration request explicitly is not a member. Unlike a member's Desk-sourced address, a request's *origin* email is never a row in this table at all (it lives on `registration_requests` itself), so there is no "cannot delete" case to special-case — every row `Service\SecondaryEmailService` touches really is removable. **A confirmed secondary address grants the full tracking view with no staff involvement at all** — a deliberate self-service exposure, not a staff-mediated control (documented explicitly in the RGPD content, §8.35's own RGPD rule 26).

**Espace animés menu hook**: `Core\Module\MenuEntryProvider` (§7.4) — `Service\RegistrationMenuHookService` contributes one dynamic entry per pending request linked to the identified visitor's email, alongside the core-built per-member entries, in the same `MenuBuilder::GROUP_DYNAMIC` group. `module.json` declares `/inscriptions/suivi/demande/{id}` (the entry's own target) *before* `/inscriptions/suivi/{id}/{token}` — the reverse order once let the token route's all-wildcard tail silently swallow every click on this exact menu entry (§7.1's route-shadowing rule).

**Sibling checkbox names and the birth-date branch preview (public form)**: `Controller\PublicRegistrationController::buildPageContext()`'s `sibling_candidates` list renders through `|normalize_name` in the template, same as every other member name display in the app (Desk-imported names are frequently ALL CAPS in storage). The birth-date field's "Branche prévue : ..." hint is computed entirely client-side from `birth_years_by_branch` — the exact same server-computed data already rendered in the "nés en..." table above the form, re-embedded as an inline JS array rather than a second AJAX round trip or a duplicated copy of the age-bracket math — so the preview can never drift from what the table above it already shows for the same target year.

**Scheduled open/close — recurring, year-less MM-JJ, not a one-shot datetime**: `registration_scheduled_open_at`/`registration_scheduled_close_at` hold a bare `MM-JJ` (e.g. `09-30`, `08-31` — same convention as `registration_reference_date`/`SlotService::referenceMonthDay()`), deliberately never a year, so a chief configures the recurring transition once and it fires every scout year without re-entry. Polled hourly by `Task\OpenRegistrationHandler`/`Task\CloseRegistrationHandler` rather than reacted to at save time (no per-setting side-effect hook exists on the generic settings-update path). Each handler fires only when today's `m-d` exactly matches the configured value — never "catching up" a date that already passed earlier this year, exactly like a real crontab — guarded against firing twice the same day by a companion `*_applied_on` setting (`registration_scheduled_open_applied_on`/`_close_applied_on`, a real `AAAA-MM-JJ`, "managed automatically" in its own label) rather than clearing the schedule after firing, since the schedule itself must persist across years. Self-reschedules hourly — same "no first-class recurring task" precedent as `Modules\Retro\Task\PurgeRateLimitHandler`. A chief can also flip `registration_form_open` immediately at any time via `Controller\RegistrationConfigController::toggleOpen()` (`POST /config/inscriptions/toggle-open`) — a manual toggle never touches the applied-on markers, so it never interferes with next year's automatic transition (a chief can e.g. manually close the form the same day it auto-opened, and the auto-open handler won't silently reopen it later that day). Both the manual toggle and the recurring MM-JJ schedule (`saveSchedule()`, `POST /config/inscriptions/schedule`, its own `preg_match`/`checkdate` MM-DD validation since module.json-declared settings carry no validation regex) live directly on `/config/inscriptions` — the page a chief managing Inscriptions actually reaches (`role_min: admin`), rather than only on the generic `/config/settings` page (`role_min: superadmin`).

**No unit-specific value in code**: slot capacities, the reference date, the open/close schedule, and both waitlist thresholds are all `SettingService`/`registration_slot_capacities` values, editable from `Controller\RegistrationConfigController` (capacities/year code/open-close) and the generic settings page (everything else) — never a hardcoded capacity number. Age brackets are the one exception to "editable somewhere": they're federation-fixed and centralized (`MemberYearService::BRANCHES`, above), not unit-specific data at all, so there's nothing about them to configure on this screen or anywhere else.

### 8.36 Registration module — staff-side request management (iteration 5)

Everything §8.35 deliberately stopped short of: a request's full life cycle from `pending` through a final state, and staff tooling to drive it.

**State machine (`Service\RequestStatusService`)**: three progression states (`pending` → `accepted` → `encoded`) plus two exits (`refused`, `withdrawn`), `RegistrationRequest::FINAL_STATUSES = ['encoded', 'refused', 'withdrawn']`. `ALLOWED_TRANSITIONS` is a private matrix enforced centrally — `accept()`/`refuse()`/`withdraw()`/`revertToPending()` all funnel through one private `transition()` that throws `RegistrationException` on an inconsistent move (e.g. accepting an already-`encoded` request) rather than silently applying it. `encoded` has no manual transitions at all: it is reached exclusively via `Service\MigrationService::migrate()` (below), never a bare `updateStatus()` call. Entering any final state sets `final_at` (retention's own anchor, never `received_at`); `revertToPending()` is the one transition that clears it back to `NULL`.

**The decoupling rule (`RequestStatusService::visibleStatus()`)**: a pure function, the parent-facing half of the module's own explicit design rule — the tracking page must never reveal an acceptance or a refusal before the corresponding email has actually been sent. `visibleStatus()` returns `pending` in place of `accepted`/`encoded` while `accepted_email_sent_at IS NULL`, and in place of `refused` while `refused_email_sent_at IS NULL`; every other status passes through unchanged. `Controller\TrackingController`'s templates call this, never `$request->status` directly. Staff-facing surfaces (the fiche, the management list) show the real internal status *and* the email-sent columns side by side instead — the gate is for parents only, never a staff-facing mystery.

**Acceptance/refusal emails (`Service\RequestEmailService`)**: always sent explicitly via a fiche button, never automatically at the status change itself — unlike iteration 4's receipt/unit-alert emails, `registration_email_accepted_body`/`registration_email_refused_body` ship with **no default body**. `isAcceptedBodyReady()`/`isRefusedBodyReady()` (non-empty after `strip_tags()`) gate both the send button (`Controller\RegistrationRequestController` disables it server-side too, not just in the template) and `sendAccepted()`/`sendRefused()` themselves, which throw `RegistrationException` if called anyway. Unlike iteration 4's best-effort submission emails, a `MailException` here is **re-thrown**, not journaled-and-swallowed: a staff-triggered send must surface its own failure rather than silently claim success while leaving `*_email_sent_at` unset — which also means retrying is always safe and always available. Each send rotates the tracking token (`RegistrationRequestRepository::rotateTrackingToken()` — the original, shown once at submission, is long gone by now) before building the link, exactly like a fresh grant.

**Reconciliation at Desk import (`Service\ReconciliationService implements Api\ReconciliationTrigger`)**: wired nullable into `Core\Http\Controller\ImportController` (§7.5 pattern, `?ReconciliationTrigger $registrationReconciliation = null`, invoked as `$this->registrationReconciliation?->reconcileForYear($scoutYearId)` right after a successful import) — `public/index.php` re-registers `ImportController` a second time inside the registration module's own conditional block with the real service, since the module's services don't exist yet at the controller's first (forward-referenced, `?? null`) registration earlier in the file; same "re-register with the real provider" pattern as `MemberController`'s own re-registration. Matching is **blind-index only**: `findAcceptedIdsAndBlindIndexForYear()` reads only `id`+`name_dob_blind_index` for that year's `accepted` requests (no decryption at all), while the *only* decryption this pass performs is the freshly-imported `member_years` rows for that scout year (unavoidable — their blind index doesn't exist yet) to recompute the same index via the shared `RegistrationRequestRepository::normalizeForNameDobBlindIndex()`. Both sides are then grouped into in-memory `blindIndex => [ids]` maps and joined by a plain PHP loop — **zero SQL/decrypt loop over `registration_requests`**, and import performance is unaffected by how many requests are pending. Exactly one request and one member sharing a blind index migrate automatically; **zero matches leaves the request as-is** (surfaces in the management page's "non rapprochées" encart); **more than one match on either side is refused outright** (real homonym/twin case) and journaled as `registration_reconciliation_ambiguous` with `request_ids`/`member_ids` arrays only — never a name, matching SECURITY.md §11.

**Migration — one code path, not two (`Service\MigrationService::migrate()`)**: called identically by `ReconciliationService` (automatic) and `Controller\RegistrationRequestController::link()` (manual, by Desk "numéro de tiers" = `members.desk_id`, looked up via `Core\Import\MemberRepository::findByDeskId()`) — module spec: "un seul chemin de code, pas deux". Not a bare status flip: confirmed (`isValid()`) secondary emails migrate to `member_emails` (`MemberEmail::SOURCE_MANUAL`/`STATUS_VALID`, idempotency-checked via `findByMemberAndEmail()` first) so a parent never loses tracking access they configured, then `RegistrationRequestRepository::linkToMemberAndEncode()` sets `linked_member_id`/`status = 'encoded'`/`final_at` — both writes inside one `$pdo->beginTransaction()`/commit/rollback block, so a partial failure never leaves the status flipped without the emails having moved. Identity data itself never migrates (Desk stays authoritative). Idempotent by construction: a no-op if the request is already `encoded` to that exact member; `idx_rr_linked_member` (`UNIQUE`, nullable-safe) is the DB-level backstop for "one member, one request" behind an application-level pre-check (`findByLinkedMemberId()`) that produces a friendlier error. Once `encoded`, the request disappears from Espace des animés immediately (`RegistrationMenuHookService::isVisible()` hardcodes `false` for `STATUS_ENCODED` — the real member page takes over) but the fiche itself stays staff-consultable for the whole retention period below.

**The fiche (`Controller\RegistrationRequestController`, `@registration/request_detail.html.twig`)**: fields ordered exactly as Desk's own encoding order (Nom, Prénom, Section, Genre, Date de naissance, Téléphone 1/2, Email, Tarif, Adresse). At "Section", two distinct lines: "section souhaitée" (the parent's own pick, read-only, straight from `desired_section_id`) and "section prévue" (`intended_section_id`, staff-decided, editable, **restricted to the request's own slot branch** — `saveIntendedSection()` re-derives the birth-date-implied branch via `SlotMath::slotForBirthDate()` exactly like the public form's own `resolveDesiredSectionId()`, and silently drops an out-of-branch submission — and **never rendered on any tracking template**, verified directly by `RegistrationRequestControllerTest::testIntendedSectionNeverAppearsOnTrackingSurface()`). At "Tarif", `Core\Member\FeeEstimationService::estimate()`'s suggestion (household size shown in clear) next to a real, Desk-imported `fee_categories` dropdown (`Core\Import\FeeCategoryRepository::findAll()`, new in this iteration) — always overridable, never applied automatically. Internal notes (`internal_notes_encrypted`): encrypted at rest, never shown to a parent, and — the module's own stricter rule for this one field — **never journaled**, not even a diff; `saveNotes()` logs nothing at all. Everything else parent-submitted is strictly read-only; there is no code path that writes back to an identity field. Declared siblings (`RegistrationRequestController::siblingDetails()`) show by name and by their PROJECTED section for the request's own target scout year, not a bare count — each sibling's real birth date and `scout_year_offset` (their current member_year row, resolved against the current public year, same precedent as the Passage page's own new-registrations sibling lookup above) is run through `MemberYearService::getEffectiveAge()` with the request's target year as the reference, exactly the "never recompute an age by hand" rule everywhere else in this module. "Adresse postale" is composed street-then-number (`{{ r.street }} {{ r.number }}`, matching `Core\Member\MemberAddress::format()`'s own convention), same on the family-facing tracking page (`@registration/tracking_full.html.twig`) — previously both put the number first, the opposite of every other address display in the app.

**Retention (`SettingService` + `Task\PurgeRegistrationRequestsHandler`)**: two settings, both counted from `final_at` (entry into a final state), never `received_at` — `registration_espace_animes_retention_months` (default 3, read by `RegistrationMenuHookService::isVisible()` for `refused`/`withdrawn` requests; `encoded` is unconditional/immediate as above) and `registration_purge_retention_years` (default 2, read by the purge handler). `PurgeRegistrationRequestsHandler` follows the exact `Task\OpenRegistrationHandler`/`CloseRegistrationHandler` self-rescheduling pattern (§8.35) — daily interval, `findFinalIdsOlderThan($cutoff)` (ids only, a row about to be hard-deleted is never worth decrypting) then `deleteById()` per id, one summary journal entry (`count`+`cutoff`, skipped entirely on an empty run), then `scheduleAfter(...)` — bootstrapped once from `public/index.php` (`if find(...) === null then schedule(now)`), no `public/cron.php` change needed (module-scoped handlers auto-resolve via `ModuleManager::getTaskHandler()`, same as §8.35's open/close pair). A non-final request (`pending`/`accepted`) is never purged, regardless of age.

**Management page (`Controller\RegistrationConfigController`, extended from iteration 4's brackets/capacities/year-code screen)**: a year selector (target year default — `ScoutYearService::nextLabel()` of the public year — plus the current year and every past year still in the database; a requested year outside that range silently falls back to the target year, so nothing beyond target+0 is ever reachable and a past year is consultation-only, its bulk actions hidden server-side too, not just visually); a capacity-verification table (`Service\SlotService::capacityBreakdownForYear()`, deliberately reusing `waitlistTiersByBirthYear()`'s own accepted-count/threshold logic so the admin table and the public tier can never silently diverge); the request list (`findAllForYear()`, in-PHP status/text filtering — an encrypted column can't be `LIKE`-searched in SQL, so filtering happens after the bounded per-year decryption the list already needed for display, never a broader unbounded scan); the "non rapprochées" encart (`findUnreconciledAcceptedForYear()`); and the "non clôturées" encart with two bulk actions (`bulkRefuse()`/`bulkWithdraw()`, `findNonFinalForYear()` as the target set) — both require CSRF, both are behind a `data-confirm` dialog that announces the exact count being acted on before submission (CSP has no `unsafe-inline`, so the confirm listener is a nonce-carrying delegated `<script>` block, same pattern as `core/View/templates/members/show.html.twig`), and both refuse outright (flash error, no-op) for a past year. An editable free-text notice block uses the generic `partials/rich_text_field.html.twig`/`rich-text-field.js` pair (`POST /api/rich-text-content`, `Core\Http\Controller\EditableContentController::updateField()` — no per-module save endpoint needed), the same mechanism `modules/banner` already uses for its own per-item rich text, applied here to a single fixed key instead of a list.

**RBAC**: every iteration-5 route (`/config/inscriptions/demandes/*`, the two bulk-action routes) is `role_min: admin`, `menu: espace_admin`, matching the whole config surface iteration 4 already established — no new role tier introduced.

### 8.37 Registration module — Départs, Passage, mailing list (iteration 6)

Départs (`espace_chefs`) and Passage (`espace_admin`, moved up from `espace_chefs` once it became clear a page showing the whole unit at once has no business at the per-section chief floor) prepare next year, plus an optional contribution to `mass_mail`.

**Départs (`Controller\DeparturesController`)**: `role_min: chief`, but the page itself is scoped further, per-section, using `Core\Member\SectionStaffAuthorizationService::getStaffedSections()` (§8.33) — never a parallel cloisonnement check. `admin`/`superadmin` get every section (the service's own rule); a plain animateur/chief sees only their own. Lists `Core\Member\SectionService::getSectionAnimes()` (new sibling to `getSectionStaff()`, same `f.role IN/NOT IN ('chief', 'admin')` split, same "an animé carries the same `section_id` as their section's staff" trap) — never staff. Marking uses `Core\Member\DepartureService::markLeaving()`/`unmarkLeaving()` (§8.32) as-is; the free-text comment goes through a NEW, separate `DepartureRepository::updateComment()` that touches only `leaving_comment_encrypted`. That split exists specifically so the page's auto-save (no save button — every checkbox change and every comment blur POSTs independently, module spec) never lets one field's save silently clobber the other's when two animateurs edit the same section around the same time: the checkbox always fires `{leaving: bool}` alone, the comment field always fires `{comment: string}` alone, and `Controller\DeparturesController::update()` applies only whichever key is actually present in the JSON body. Every write re-derives the section server-side (loops the account's own `getStaffedSections()`, checks the target `member_year_id` is really among that section's `getSectionAnimes()`) rather than trusting which page/section the request claims to come from — the module spec's own "cloisonnement re-checked on every write, not just at display" requirement. `hydrateMemberProfile()` (§ core `SectionService`) previously left `scoutYearOffset` at its default `0` — a latent gap nothing had needed until now; fixed in place, since "année de parcours" must go through `MemberYearService::getEffectiveAge()` with the member's real offset, never recomputed by hand (module spec's own explicit pitfall).

**Passage (`Controller\PassageController`, `Service\PassageService`)**: `role_min: admin` (§4.4's Espace chefs d'U, not §4.3's Espace chefs — a plain per-section chief/animateur is rejected), NOT section-scoped (module spec: splitting arrivals across sections needs the whole unit at once). Anchored on the **public year + 1**, always — computed the exact same way `RegistrationConfigController`'s own target year already is (`ScoutYearService::nextLabel()` + `ensureYear()`), never via `ScoutYearResolver::getEffectiveYear()`. This is a **deliberate, explicit exception** to the rule that governs every other page on the site (an admin's session preview or an active staff year must not move the target) — written directly into `PassageController`'s own class docblock so it reads as an intentional design decision, not a bug someone "fixes" later. Two independent blocks:
- **New registrations**: `accepted`-but-not-`encoded` requests for the target year (`RegistrationRequestRepository::findAcceptedForYear()`, already scoped to `status = 'accepted'` — `encoded` is a different value entirely, no extra filter needed), with each declared sibling (`registration_request_siblings`) resolved against the **current public year** (a sibling is a real, already-enrolled member — resolving them against the *target* year would find nothing, since that year's Desk import hasn't happened yet) to show their own current section. The "section prévue" field edited here is `registration_requests.intended_section_id` — **the exact same column** the fiche (§8.36) reads and writes; `PassageController::saveIntendedSection()` re-implements the fiche's own branch-scoping check locally (small, ~15-line duplication, same precedent as `slotLabel()` already being duplicated across controllers in this module) rather than sharing a helper, but there is only ever one column being written, so the two surfaces can never disagree on what "section prévue" currently is — verified directly by a test that sets it through one path and reads it back through the other.
- **Branch changes**: existing members at the **last rank of their current branch** (`EffectiveAge::yearInBranch === totalYearsInBranch`, computed against the **current public year**, never the target year — these are members who exist *today*), excluding anyone marked `leaving` (§8.32) and excluding Pionniers (`AgeBranchRepository::canonicalSortOrder() >= 40` — the federation's last animés branch, "un pionnier de dernière année ne passe nulle part", module spec). Grouped by current section. Each row's "même adresse" column (module spec: **never** called "fratrie" in code, comments, or the UI — a shared `member_addresses.address_normalized_blind_index` means roommates, two families at one number, or shared custody just as often as siblings) is resolved by a plain self-join on that blind index against other active, non-leaving `member_years` for the same year — entirely distinct from the new-registrations block's own sibling-link lookup above; the two must never be conflated in code, since they answer genuinely different questions. The destination section picker is limited to sections whose `age_branch_id` belongs to the arrival branch (current branch's canonical sort order + 10) — computed fresh, never trusted from the request.

**Destination storage (`registration_section_transfers`, `Repository\SectionTransferRepository`)**: keyed on the permanent `member_id` (not a `member_year_id`) + the target scout year, storage confined to the module — module spec: this is planning data, not a fact about the member, and must never be written to `member_years`, since Desk stays the sole source of truth once that year is actually activated and re-imported. SELECT-then-branch UPDATE/INSERT and a PHP-computed `updated_at`, same portability rules as the rest of this module (no `ON DUPLICATE KEY UPDATE`, no SQL `NOW()`).

**Mailing list (`Api\ExternalMailingListProvider`, `Service\ExternalMailingListService`)**: the registration module **owns** this Api interface and `mass_mail` **optionally consumes** it — the same shape as `Modules\Finance\Service\ReceiptExtractionService` consuming `llm_connector` (ARCHITECTURE.md §7.5), not the "core hook" shape of `Core\Module\MenuEntryProvider`. The distinction matters here: registration is the one that *has* the capability (turning its own accepted/encoded requests into a resolvable recipient list), `mass_mail`'s own compose page merely wants to *use* it — so the interface lives in registration's `Api` namespace, and `mass_mail`'s `Service\MailingListService` takes a nullable `?ExternalMailingListProvider $externalListProvider = null` constructor dependency, wired in `public/index.php` only when the registration module is enabled (both `MailingListService` and `MassMailService` — which holds its own internal reference to the *old* `MailingListService` instance built earlier in the file — are rebuilt together and `MassMailController`/`ConfigController` re-registered, same "re-register with the real provider" pattern already used for `ImportController`). Content is deliberately **`encoded` only**, not `accepted`: `mass_mail_recipients.member_id` is a `NOT NULL` foreign key to a real `members` row, which an `accepted`-but-not-yet-`encoded` request simply doesn't have — reading the module spec's "les demandes acceptées et encodées dans Desk" as one path (every `encoded` request necessarily passed through `accepted` first) rather than a union of two inclusion rules is the only reading that's actually implementable, and it matches the spec's own "point à vérifier" about deduplication against Desk-derived section lists, which only makes sense for members that already exist in Desk. The list is named `"Inscriptions {target year label}"` (never `"Nouvelles inscriptions"` — module spec: one list per year, never recycled) and is **never re-scoped by `mass_mail`'s own multi-year selector**: `MailingListService::resolveMembersForYears()` special-cases `LIST_TYPE_EXTERNAL` to call the provider exactly once and tag every recipient with `Api\ExternalMailingListProvider::targetScoutYearId()` (the provider's own fixed target year) instead of looping over whichever of previous/current/next happens to be checked in the compose dialog — without this, a recipient's `mass_mail_recipients.scout_year_id` could end up pointing at a year where their `member_years` profile doesn't actually exist, breaking the tracking page's own profile lookup for that row. `mass_mail_emails.list_type`'s `ENUM` gained a fifth value, `'external'` (schema.sql bump, mass_mail module.json 1.4.0 → 1.5.0); `list_id`/`list_section_id` both stay `NULL` for it, same as `default_active_members`/`default_chiefs`. No change was needed to `MassMailAccessService::canUseList()` or the compose page's own JS (`isListAllowed()`/`populateListSelect()`) — both already default to "chef d'unité only" for any list type they don't explicitly recognize, which is exactly the right behavior for a unit-wide list with no natural section owner.

**Cross-campaign duplicate delivery — investigated, not fixed**: the module spec asks whether `mass_mail` already deduplicates by address at send time. It does, but only **within one email's own recipient resolution** (`resolveMembersForYears()`'s `$seenMemberIds`/`$seenAddresses`, for that email's own multi-year merge) — there is not, and was already not before this iteration, any deduplication **across two separate emails**. A chief who sends one email to "Inscriptions 2026-2027" and later a second, unrelated email to "Section - Louveteaux" (which now includes the same, freshly-imported child) will reach that family twice — but this is true today of any two of `mass_mail`'s existing lists (e.g. "Membres actifs" and any section list already overlap on every member), so the external list introduces no new failure mode. Building real cross-campaign deduplication (suppressing an intentionally distinct second email because an unrelated first one already reached the same address) would be a substantial, unscoped feature in its own right, not a small provision — left as-is, documented here rather than silently ignored.

### 8.38 Registration module — Prévisions and the year-transition veto (iteration 7)

The module's final iteration: a read-only headcount projection, and the first veto a module ever opposes to a core operation.

**Veto mechanism (`Api\ScoutYearTransitionVetoProvider`, `Service\ScoutYearTransitionVetoService`)**: the reverse direction from §7.4's core hooks and the same shape as §7.5's `HouseholdRegistrationCountProvider`/`ExternalMailingListProvider` — the module publishes a one-method interface (`countBlockingRequests(): int`) in its own `Api` namespace; `Core\ScoutYear\ScoutYearAdminService` takes it as a **nullable** constructor dependency (default `null`), wired to the real implementation only in `public/index.php`'s registration block. Core never references a single concrete class of the module — only this interface — and with the module absent or disabled, `countBlockingRegistrationRequests()` simply returns `0` and every transition behaves exactly as it did before this iteration existed.

The refusal itself lives in `ScoutYearAdminService::activatePublicYear()` — the method that actually flips the setting — not in the controller: it throws `Core\ScoutYear\ScoutYearTransitionVetoedException` (carrying the blocking count) before touching `SettingService` at all when the veto reports anything open. This is deliberate placement, not a style choice: it means the refusal holds even if some future code path called `activatePublicYear()` directly, bypassing `ScoutYearController` entirely — "vérifié côté serveur, pas seulement à l'affichage" (module spec) as a property of the service, not of any one caller. `ScoutYearController::activatePublic()` catches the exception, journals `scout_year_public_activation_blocked` (`security` level, `blocking_request_count` only — no personal data, matching every other event this controller already logs) instead of `scout_year_public_activated`, and flashes an actionable message pointing at `/config/inscriptions` and the iteration 5 bulk actions ("tout refuser", "tout retirer").

**Second Api, same shape (`Api\ScoutYearPreparationProvider`, `Service\ScoutYearPreparationService`)**: `countPassages()` / `countUnassignedPassages()`, read by `Core\ScoutYear\ScoutYearTransitionService` (§8.26) to tell whether the Passage page still has work waiting, and — by its mere presence — to decide whether the workflow shows this module's three preparation steps at all. Unlike the veto next door it is not a pass-through to one query: "who changes branch next year" is a rule `PassageService` already owns, so the service asks `getBranchChanges()` the exact same question the page asks rather than re-deriving it in SQL, and memoises the answer (that call decrypts every animé of the year and resolves every household, and the two counts are two questions about one result). It resolves its own target year — public + 1, like every other surface in this module — precisely so core never has to hold a second copy of that rule.

The count is **"toutes années cibles confondues"** (module spec) — `Repository\RegistrationRequestRepository::countNonFinalAllYears()` deliberately has no `scout_year_id` filter at all, unlike every other query in that repository. A `pending`/`accepted` request that targeted a year already in the past still blocks: this is what makes it impossible to accumulate a forgotten backlog by switching years around it, at the cost of a chief occasionally having to close out a stale request from a prior season before the current one can transition — an intentional trade the module spec explicitly asks for.

Step 3 (activate the staff year) shows the same count as a **non-blocking** warning (`ScoutYearController::index()` computes it once, unconditionally, and passes `blocking_request_count` to the template for both steps) — it arrives much earlier in the season and staff need the runway to work through it, so it must never gate anything. Step 4's own alert is the hard stop; the "activez d'abord une année pour le staff" hint that used to appear whenever `can_activate_public` was false was narrowed to only fire when the staff year is genuinely unset (`not staff_year`), so it no longer misfires with a stale message when the real blocker is open requests instead.

Itération 3 already removed the only automatic path a year could switch through (§8.26); this iteration doesn't need to re-verify that separately, since `activatePublicYear()` is still the sole write path to `SETTING_PUBLIC_YEAR` (`ScoutYearAdminService`'s own only two methods, both explicit/manual), and the veto sits inside that one path.

**Prévisions (`Controller\ForecastController`, `Service\ForecastService`)**: `role_min: chief`, `espace_chefs`, **not** section-scoped (same reasoning as Passage — judging a section's trajectory needs the whole unit at once), anchored on the **public year + 1** exactly like Passage and the mailing list (§8.37) — the controller resolves years the identical way `PassageController::resolveYears()` does. Purely a read: no route writes anything, so nothing here ever reaches the journal.

Four sources combine into one projected headcount without double counting:
1. **Certain** — animés already re-imported into Desk for the target year (`PassageService::getAnimeMemberYears($targetYearId)`, promoted from a private method the same query already existed as for Passage's branch-change detection — one query, two callers, never a second near-copy of the SQL). Real data; empty until an import for that year has happened. Because that method already filters `leaving = 0` and only returns rows that genuinely exist for that scout year, "apport 1" and "moins apport 2 (marked leaving)" both fall out of the same query for free — nothing extra needed.
2. **Hypothesis** — current-year animés who are neither marked leaving nor at the last rank of their branch, projected one scout year forward by calling `MemberYearService::getEffectiveAge()` again with the **target** year's reference year instead of hand-incrementing `yearInBranch` — the module spec's own explicit pitfall, avoided by construction rather than by discipline.
3. **Hypothesis** — branch changes (`PassageService::getBranchChanges()`), placed in their destination section when one is chosen, or "non attribués" (origin: passage) when not.
4. **Hypothesis** — accepted-but-not-encoded registrations (`PassageService::getNewRegistrations()`, extended to also return the raw `slot` array alongside its existing `slot_label` string, so the year-in-branch used for grouping is never a second, independent computation of what `SlotMath` already worked out once), placed in `intended_section_id` — the exact same "section prévue" column Passage's own top block already writes — or "non attribués" (origin: inscription) when unset.

The double-counting risk the module spec calls out by name — a request that reached `encoded` and was then reimported existing both as a request and as a member — cannot occur structurally: `getNewRegistrations()` only ever returns `status = 'accepted'` rows, and a request becomes `'encoded'` at the exact moment it gets a real `linked_member_id` (`RequestStatusService`/`MigrationService`, §8.36); the two states are mutually exclusive, so bucket 4 can never contain anyone bucket 1 also contains. Buckets 2 and 3 get one more defensive layer on top of that: any `member_id` already present among the target year's real `member_years` rows is excluded from both, so a genuinely **partial** Desk import — some children re-imported already, others still only planned — never double-counts someone who made it in early, and always trusts whatever section Desk now shows for them over an earlier passage/destination decision. A dedicated test (`ForecastServiceTest::testEncodedAndReimportedRequestCountedOnce`) locks this in.

"Non attribués" (unplaced passages/registrations) are pushed into the same internal projection list as everyone else — `section_id: null` — so they still land in the unit total and the birth-year pyramid (module spec: both must include them), while `buildViewModel()`'s per-section loop simply skips a `null` section id, keeping them out of every real section's own numbers. The page surfaces them as their own card (total, split by the two origins, a direct link to `/passage`) rather than a fake section row — module spec: this card is meant to visibly empty out as staff work through Passage, making it a natural "prévisions are trustworthy now" signal.

**Two invariants this page owes the reader, both regression-tested** — a review of the page found it silently violating all of them, each in a way that quietly made people disappear from a projection whose whole purpose is to account for everyone:

- *`sum(sections) + unassigned === projected_total`.* `buildViewModel()` is now the single place that decides where a row lands, so a row can neither be counted twice nor fall between two counters. Previously the "non attribué" tallies were incremented at push time while the section loop separately `continue`d past anything it couldn't resolve, and the two disagreed in exactly one case: **`ForecastService` built its section map from `getAllWithBranches()` (visible only) while `PassageService` offers destinations and "sections prévues" from `getAllWithBranches(true)`**. A hidden-but-active section is an ordinary, assignable destination, so a passage into one hit the `continue` — commented "shouldn't happen — always a real, active section", which conflated *active* with *visible* — and vanished: in the unit total, in no section, and not "non attribué" either. The map is now built with `includeHidden: true` (a hidden section nobody is projected into is dropped again at the end, so nothing empty is added to the page), and a section id that genuinely cannot be resolved (deleted, or since deactivated) lands in its own `from_unknown_section` bucket rather than being dropped.
- *Everyone in `current_total` who is absent next year appears in exactly one of `departures_count` or `aging_out_count`.* `current_total` used to be computed from `getAnimeMemberYears()`, which carries `leaving = 0`, and then additionally dropped anyone outside the four branches — so an announced departure was subtracted from **both** sides of `projected − current` and cancelled itself out, and a unit losing a member to a declared departure displayed "Variation: 0". It is now a plain count of today's real animés (`countCurrentAnimes()`: active, non-staff, sectioned, leavers and out-of-branch members included). The other half of the variation, members leaving by **age** rather than by a flag — last-year Pionniers above all, who pass through neither bucket 2 nor bucket 3 — is now counted as `aging_out_count` and shown on the page as its own "Fin de parcours" card, so the variation is fully explained by the figures printed beside it.

**Members a year ahead or behind (`member_years.scout_year_offset`)** get their own attention here, since a forecast is exactly where an off-by-one year shows up. Bucket 2's gate now asks where a member lands **next** year, not where they sit today: it previously required the *current* effective age to be in a known branch, which dropped a member held back below Baladins' entry age even though they reach 1st year next year — precisely the person a forecast exists to predict. Bucket 3's year-in-branch was hardcoded to `1` ("always the bottom rank of the arrival branch"); it is now derived per member from `getEffectiveAge()` against the target reference year, honouring their own offset, like every other age question in this module. See also §8.1's note on the import carrying the offset forward — without that fix, the *certain* bucket ranked advanced members by a stale age the moment Desk re-imported them.

Certain vs. hypothesis is tracked per section (`certain_total`/`hypothesis_total`) and shown next to every section's number, never only once at the top of the page — module spec: "une projection présentée comme un fait finit citée en réunion comme un fait." Only bucket 1 ever counts as certain; a **chosen** passage destination or section prévue is still just staff's own plan, not yet a Desk fact, so buckets 2–4 are hypothesis regardless of whether a decision has already been made for them.

**Not reusing `member_stats`**: the three visualizations this page needs (a stacked, segmented bar per section by year-in-branch; a single divided bar for gender balance; a two-sided population pyramid by birth year) are structurally different from anything `member_stats` renders (one flat proportional bar per branch-year row, plus separate detail cards) — not a smaller/larger version of the same chart, a genuinely different shape each time. `member_stats` publishes no `Api` interface, and its one candidate for a "reusable render component" (a colored, proportional flex bar with the count printed inside) is a generic two-line CSS technique already reused verbatim by several unrelated parts of the site, not a component specific to that module — there was nothing to actually extract into core beyond what Bootstrap utility classes already provide for free. This lands on the third of the module spec's three explicit branches ("rien de réutilisable → implémenter dans le module, en assumant le doublon visuel") — a deliberate choice, recorded here rather than left implicit, not a shortcut. What genuinely is shared, and never recomputed independently, is `SectionService::colorForSection()` for every section color on the page (§8.8) and `PassageService`'s three public methods for every underlying number. `ForecastService`'s constructor takes no dependency on anything under `Modules\MemberStats`, verified by a reflection-based test — the page renders identically whether that module is installed, enabled, or absent entirely.

**Remaining capacity per year of the journey**: a later addition, placed directly above the "Non attribués" card — one proportional bar row per (branch, year-in-branch) slot, deliberately drawn with the exact same generic bar-row markup the paragraph above already identifies as a reusable-by-copy CSS technique (fixed label left, proportional colored bar with the count inside, fixed detail right), this time explicitly requested to match `member_stats`' own look. The numbers themselves are never a second computation: `ForecastController::index()` calls the same `SlotService::capacityBreakdownForYear()` the Inscriptions config page's "Vérification des capacités" table already reads (§8.35), and `ForecastService::groupCapacityByBranch()` only reshapes that flat row list into per-branch groups — capacity, projected, accepted and the availability tier all stay identical between the two pages. Each row's color is the branch's own representative-section color, resolved the same way `MemberStatsService::resolveBranchColor()` already does (first section by `desk_code` when a branch has several, `SectionService::colorForSection()`, falling back to `MemberYearService::colorForBranchSortOrder()` for a branch with none) — duplicated in miniature rather than extracted, since that method is private to a module `ForecastService` has no dependency on. A negative `remaining` (over capacity) is shown as-is, never clamped to zero — only the bar's own width is floored at zero, since a bar can't be drawn shorter than empty.

### 8.39 Image variant pipeline (`Core\Photo\ImageVariantService`/`ImageVariantProcessor`, `GET /files/{id}/{variant}`)

Until this iteration, a `member_photo`/`section_photo`/`editable_image`/`age_branch_logo` upload was stored at whatever size the phone produced and every page rendered the original through `/files/{id}` — the original could be several megabytes, which made the offline pre-download (§8.25) impractical and every page slower than it needed to be. Two fixed derivatives are now generated once, at upload time, and every one of these four core photo contexts renders exactly one of them instead of the original.

**Client-side downscale, before the upload even reaches the server** (`public/assets/js/upload.js`): for the same four contexts plus `unit_logo` (§8.23 — has its own storage pipeline but shares the same upload page), the selected file is drawn onto a canvas, downscaled so its longest edge is at most 2400px, and re-encoded to WebP at quality 0.85 — skipped entirely when the source is already small enough (under a size/dimension budget) so an already-reasonable photo isn't needlessly re-degraded. Alpha is preserved throughout (canvas defaults to transparent, `drawImage()` copies the source's alpha channel unchanged). A canvas/encode failure falls back to the original file rather than blocking the upload. `Core\Http\Controller\UploadController`'s server-side cap is raised from 5MB to 10MB accordingly — the client-side step is expected to keep real-world uploads well under either figure, but the server floor still has to accommodate whatever a browser without canvas support, or a non-browser client, sends unprocessed.

**Server-side derivatives** (`Core\Photo\ImageVariantService`/`ImageVariantProcessor`, GD-based, same before-storage-pipeline precedent as `SectionPhotoProcessor`): exactly two variants exist, no more —

| Variant | Geometry | Quality | Rendered by |
|---|---|---|---|
| `thumb` | 192×192, centre-cropped square, WebP | ~q70 | `member_photo()` |
| `md` | 1024px longest edge (aspect preserved), WebP | ~q75 | `section_photo()`, `editable_image()`, `age_branch_logo` |

192 isn't arbitrary: `.member-photo` is 96px and `.member-photo-header` is 64px (`public/assets/css/components.css`), so 192 covers the 96px avatar at exactly 2×. Same "no `files` row, no new DB column, `is_file()` is the entire state" shape as `UnitLogoService` (§8.23) — a derivative is a sibling of the stored original on disk, in the same storage subdirectory, named `{original-basename}.{variant}.webp`. Generated exactly once, right after `UploadController` calls `UploadHandler::handle()` — never regenerated, never generated on demand. Because the original has already been through EXIF-orientation-correction and re-encoding by that point (`UploadHandler::stripExifAndSave()`, or the dedicated `SectionPhotoProcessor`/`LandscapeImageProcessor` for those two contexts), `ImageVariantProcessor` itself does no orientation handling of its own — it only decodes, crops/resizes, and re-encodes as WebP, with alpha preserved end to end.

**Serving** (`GET /files/{id}/{variant}`, `Core\Http\Controller\FileController::variant()`): resolves the file through the exact same `FileAccessGuard::check($id)` call `serve()` uses — same `role_min` floor, same owner-scoping, same `file_access_denied`/`owner_scoped_file_accessed` journal entries — then reads the sibling derivative from disk. This is a rendition of the same file, not a second access path (§6's single-download-path rule stays true). `{variant}` is validated against the fixed two-name vocabulary *before* it is ever used to build a filesystem path — anything else, including a path-traversal attempt, is a plain 404 that never touches the filesystem. A missing derivative (an original uploaded before this pipeline existed, or before a re-upload regenerates it) is also 404 — never a fallback to the original, and rendering degrades instead: `member_photo()` falls back to its existing initials placeholder, `section_photo()`/`editable_image()` render nothing at all, same "nothing if absent" principle as §8.10. `Cache-Control` is `max-age=31536000, immutable` (`public` or `private`, mirroring the file's own `role_min` exactly as `serve()` already does) — a derivative URL is immutable for a given file id, since a new upload always creates a new file id (and a re-derivation would be a new upload too, per the "no on-demand regeneration" rule above).

**One real, pre-existing bug fixed alongside this pipeline**: `UploadController` stored `section_photo` files at `role_min: 'intendant'`, but `section_photo()` is rendered on the *public* Contact and Sections pages (§8.21) — `FileAccessGuard` silently denied every one of those to a non-identified visitor, so both pages showed no staff photo at all to anyone not logged in. `section_photo`'s stored `role_min` is now `'public'`, matching what §8.21 already assumed.

**Retired**: the offline trombinoscope pre-download used to need its own narrow exception to the single-download-path rule (`GET /api/offline/photo/{member_id}`, `Core\Photo\StaffThumbnailProcessor`, generating an on-demand ~160px WebP square) precisely because `/files/{id}` had no cacheable, already-small rendition to point the pre-download at. `GET /files/{id}/thumb` now *is* that rendition, so the exception is gone entirely — `Core\Http\Controller\OfflineController::photo()` and `StaffThumbnailProcessor` are deleted, and `GET /api/offline/photo-manifest` (kept, still `role_min: identified`, still gated on `StaffDirectoryProvider`) now lists plain `/files/{id}/thumb` URLs. This is a net reduction of security surface: one fewer bespoke route bypassing `FileAccessGuard`'s normal single-path posture. See §8.25 and §6 for what this changes there.

### 8.40 Groups module (`modules/groups`)

Private discussion groups for a unit: a per-section group where a section's members talk, plus invitation groups a chief opens for anything else. Every table is prefixed `discussion_group` — `groups` is a reserved word on MySQL 8.0 (the window-function frame clause), so `CREATE TABLE groups` is a syntax error that would only surface at install time on a real server, never in the SQLite-backed suite.

**Two membership sources, resolved per request, never materialised.** A member belongs to a group either through an explicit `discussion_group_members` row (invited by a chief; the row also carries the `is_moderator` flag) or by having a `member_section_periods` period in one of the group's `discussion_group_sections` for the group's year. `Service\GroupAccessService` reads that account-first (which of *my* linked members is in this group), `Service\GroupRecipientResolver` reads the same rule group-first (who is in this group) — the two share the year resolution so they can never disagree about an archived group. Nothing is ever copied into a membership table, which is what makes a Desk import that moves a member between sections take effect on the next page load with nothing to invalidate. `discussion_groups.scout_year_id` is deliberately nullable, against AGENTS.md's "every member-related table carries `scout_year_id`": a section group always has one (which is what keeps a past-year group readable by exactly whoever was there), an invitation group has one only if the chief wanted it.

**One name for one human (`Service\MemberIdentityService`).** Everywhere this module names somebody — a message, a comment, "qui a réagi", "vu par", the members page — it writes the **account first, then in parentheses every membership that account carries for the year in question**: `Marie Dupont (Akéla, Baloo)`. The account is the human who actually typed it; the memberships are what that human has. It used to read the other way round (`Akéla (Marie Dupont)`), which put a child's totem in front of a message a parent had written, and made the same person read differently here than on the members page, where only the totem appeared.

The join between the two halves is the **email blind index**, the same one login already uses (`UserAccountRepository::findEmailBlindIndexesByIds()` / `MemberYearRepository::findMemberIdsByEmailBlindIndexes()`) — no address is ever decrypted to resolve a name. Resolution is batched per page (`forAccounts()`/`forMembers()` take id lists, never one id) and memoised per request under an `accountId:scoutYearId` key, so a feed of twenty messages by the same author costs one lookup, and an archived group still names the people who were in it *that* year rather than whoever holds the address now. Two fallbacks, in order: an account with no first/last name is named by its memberships instead of by an empty string, and a member with no account at all keeps their own display name — most animés have none, and inventing a human name in front of them would be worse than their totem. `Service\PostAuthorResolver`, `ReplyPresenter`, `ReactorListService`, `SeenByService`, `GroupFeedService`, `AuthorOptionsService`, `MentionService` and `GroupMemberController` all go through it, and `views/partials/identity.html.twig` is the single place that draws it wherever there is room for markup, so those surfaces cannot start disagreeing. `ReactorListService`/`SeenByService` additionally dedupe **on the rendered label**: a parent whose two children both reacted is one human and therefore one line. **No surface is exempt** — including the three where the *membership*, not the author, is what the reader is acting on. Those take the account-first shape narrowed to one membership (`MemberIdentityService::accountLabelForMembers()`, "Marie Dupont (Akéla)"): `forMembers()`'s full identity is right for an author and useless here, since three options reading "Marie Dupont (Akéla, Baloo, Chil)" are three identical options. It returns an **empty string** rather than a fallback of its own when no named account stands behind a membership, so each caller keeps the fallback that suits it — the totem for the author selector, the full name for a search box.

- **"Publier en tant que"** (`AuthorOptionsService`): "Marie Dupont (Akéla)" / "Marie Dupont (Baloo)". The human name repeating down the list is the point rather than noise — it is the signature each option would put on the message.
- **The invite-candidate search** (`GroupMemberController::searchLabel()`): the account when there is one, the membership's own full name and totem when there is not, which is the normal case here (a candidate is by definition not in the group yet, and most animés never have an account). Matching still runs against the membership, so a moderator typing a totem or a surname finds the row either way; only the label changes.
- **The "@" mention** (`MentionService`) is the one that changed shape rather than just wording, because what is displayed and what is written into the message can no longer be the same string. `suggest()` returns both: `label` — the account and its memberships — is what the row **shows**, so two people can be told apart and so typing a totem still finds the parent behind it; `mention` — the account's name alone — is what gets **written** into the body, because "@Marie Dupont (Akéla, Baloo)" mid-sentence is not something anybody would type or read back. `resolve()` reads that short form out of the stored body and returns **every membership that human holds in the group**, so mentioning a parent of three no longer means knowing which of three totems to type; `GroupNotificationService::mentioned()` already collapsed an account linked to several mentioned members into one notification. `MAX_PER_MESSAGE` now counts **people, not memberships**, so one parent of three does not spend three of a message's ten. Two accounts sharing a name in one group resolve together — the same collision two identical totems always had, erring towards notifying both. Which membership signed a given item stays *stored* — `author_member_id` still decides read state, "vu par" and the rate limit — rather than displayed.

**Text a member typed, rendered (`Core\View\TextLinker`, the `autolink` Twig filter).** A URL in a message or a comment is a link. The order is the property, not an implementation detail: the text is **escaped first**, and anchors are built around the already-escaped spans, so nothing a member wrote reaches the page as markup and the only tags in the output are the ones the linker built. Only `http`/`https` ever become an `href` — `javascript:` and `data:` are left as characters, which is the difference between a linkifier and an XSS vector. Every link carries `target="_blank"` and `rel="nofollow ugc noopener noreferrer"`: user-generated content pointing at the open web. Trailing sentence punctuation stays outside the anchor (the same set `PostLinkService` trims, so a link and the preview card it gets are never one character apart), a long URL is elided **in the middle** for display while the `href` keeps all of it, and the filter owns newlines too — it **replaces** `|nl2br` on user content rather than composing with it, because whether `nl2br` re-escapes already-safe markup depends on how the value reached it and getting that wrong stops escaping the text around the links. The first URL of a post is a separate matter: `PostLinkService` still lifts it out of the body into its own preview card, so it is never rendered twice.

**A thread opens on its END.** A post shows the **last** `ReplyService::PAGE_SIZE` comments, not the first (`ReplyRepository::findLastForPosts()` — ranked newest-first inside the window function, ordered oldest-first outside it, so the SELECT takes the tail and the display still reads as a conversation). Paging runs **backwards** from there: `replies_prev_before_id` is the id of the oldest comment on screen, and `GET /groups/{id}/posts/{postId}/replies?before=…` returns the page immediately older (`findPageBefore()` selects newest-first so the LIMIT takes the rows nearest the cursor, then reverses). A cursor is required — the feed renders the tail itself, so a request without one is a 400, not a request for the first page. `partials/reply_page.html.twig` renders its button **above** the cards it returns, which is what lets `groups.js` keep using the same replace-the-wrapper-in-place pagination as the feed with no special casing for direction. Reversing this fixed a thread of forty comments opening three weeks in the past, with seven clicks between the reader and what somebody wrote that morning.

**404, never 403.** Every route naming a group answers 404 to a non-member — a 403 would confirm the group exists, and these groups have no directory, no public group and no join request. The same rule covers a post from another group, a reaction endpoint (which would otherwise be an id-enumeration oracle across every group on the site), a report, and a notification's deep link.

**Delegated album (§7.5, gallery).** `gallery` is a hard `requires` dependency. A group's media live in a real gallery album obtained through `Modules\Gallery\Api\DelegatedAlbumManager`, created lazily on the first media post, never surfaced in the gallery's own listing. Authorization is entirely this module's: `File\GroupFileOwnershipChecker` (`owner_type` `discussion_group`, §8.3's registry) gates `/files/{id}`, and `Gallery\GroupDelegatedAlbumAccessChecker` registers the same rule into gallery's separate delegated-album registry. Link previews reuse the same module's `Api\LinkPreviewFetcher`, so `Service\OgScraperService` stays the only outbound HTTP client in the codebase (SECURITY.md §17).

**Moderation, in the query.** Members report; reaching `groups_report_hide_threshold` hides an item from everyone but the group's moderators — and the hiding is a `WHERE` clause in `PostRepository`/`ReplyRepository`, not a CSS class, so a hidden row never reaches the template, the reply counts, the group gallery or a notification payload. Hiding is the maximum automatic consequence; a moderator restores (persisted in `moderation_cleared`, so the next report cannot undo their decision) or deletes. `Service\ModerationService` is an optional `llm_connector` consumer with its own system prompt — deliberately not retro's, whose prompt is written for an anonymous retrospective board — failing open on every technical path (SECURITY.md §18).

**Lifecycle: four self-rescheduling daily tasks, no core hook.** `Task\EnsureSectionGroupsHandler` creates one group per visible, active section per year (Staff d'U included — it is a real section, unlike in `Core\Badge\BadgeService`, which skips it because a "Référent Staff d'U" badge would be meaningless). The work is `Service\SectionGroupSyncService`, which is idempotent and therefore also runs on the group list's own page load — the self-healing pattern of `BadgeService::syncSectionReferentBadges()`. **There is deliberately no hook from the Desk import**: core would then carry a reference to a module (backwards, and dead weight when it is disabled), and a half-failed import would leave the groups half-created with nothing to notice it; asking "which sections have no group yet" is cheap, self-heals after any failure, and also picks up a section made visible long afterwards. A group created this way has `created_by_member_id` NULL and therefore no moderator row — naming an arbitrary member would be a lie that also handed them the flag — so site admins moderate it until a chief grants it.

`Task\CloseInactiveGroupsHandler` closes a group idle for `groups_inactivity_close_months`; closed means read-only and **fully visible**, not hidden. Because `last_activity_at` defaults to the creation instant, a group that never held anything is measured from its creation date, which is what stops every freshly created section group being closed on the next nightly run. `Task\PurgePostsHandler` deletes a post `groups_post_retention_months` after its *last activity* (pinned posts excluded in the SQL, at any age) and `Task\PurgeClosedGroupsHandler` deletes a group `groups_closed_purge_months` after closure, album included. Both delete **files before rows**, so a crash mid-purge leaves a row the next run finds again rather than bytes orphaned in a bucket with nothing pointing at them; both process one bounded batch per run. **A group of the effective year or a later one is never purged** — otherwise the ensure task would recreate a section group the same night, forever; that rule is also why this module needs no tombstone table. None of the three durations is configurable per group: an override would let a moderator opt out of the retention bound.

**Moderation escalation, and the one thing a moderator may not do.** A moderator may delete their own content — that is just deleting your own message — but may **never restore an item they authored**: in a space where minors write, the person a report is about must not be the person who decides the report was wrong. `Controller\ReportController` checks BOTH identities the item carries (the account that typed it and the member it was signed as), so a parent who posted as their child cannot restore it by arguing the author was the child; the refusal is universal, site admins included, since an admin restoring their own reported content is the same conflict. When the reported item's author holds the group's moderator flag, the report notification escalates to every site admin as well (`Api`-shaped `moderatorsAndSiteAdminsFor()`, kept separate from `moderatorsFor()` so a future "admins opt out of routine group moderation" setting could never narrow the escalated audience with it), and the escalation is journaled under its own event type. The item's author is excluded from that notification whether or not they moderate — telling them their own content was reported would tell them a report exists, which is exactly what a reporter is promised will not happen.

**Closing, reopening, leaving.** A moderator closes a group by hand (`POST /groups/{id}/close`) or waits for the inactivity task. **Reopening** (`POST /groups/{id}/reopen`) resets `last_activity_at` to now — without that, the task that just closed it would close it again on its next nightly run, and the purge clock would still be running against a group somebody just said they still wanted. A past-year group is refused: prompt 3's read-only-archive rule is not relaxed, and the header says so rather than leaving a moderator hunting for a missing button. **Leaving** (`POST /groups/{id}/leave`) deletes the caller's explicit `discussion_group_members` row; a derived section membership is refused server-side with its own French explanation rather than silently deleting nothing, because that membership follows the Desk import and the only way out of it is to leave the section. The group's **last explicit moderator** may not leave — counted inside the same transaction as the delete, or two moderators leaving in the same instant would both see "there are two of us" and both succeed. Site admins do not count towards that check: a group must keep a moderator of its own. A departing member's posts and replies stay exactly where they are; author anonymisation is a project-wide concern and deliberately not this module's to invent.

**Creation quota.** `groups_max_created_per_member` (default 5) caps how many **open, non-section** groups one member may have created, counted on the `created_by_member_id` column prompt 3 already introduced — there is exactly one notion of who created a group. Section groups are excluded (the scheduled task creates them, not a person) and closed groups stop counting (the cap is about live clutter, not about how much somebody ever created). Site admins are **not** exempt: an admin's clutter is exactly as cluttering as anyone else's.

Task handlers get their stack from `Task\GroupsTaskFactory` (`SchedulerRunner` builds every handler with a bare `new`), and the gallery half from `Modules\Gallery\Api\DelegatedAlbumManagerFactory::fromTaskContext()` — assembly on gallery's own side of the §7.5 boundary, so a consuming module never reaches into gallery's internal constructors.

### 8.41 Month grids — two of them, on purpose (`Core\View\MonthGrid`)

Two month-grid builders live side by side in this namespace, and the split is deliberate. Both produce 7 columns (Monday first), one row per week, spanning the Monday on/before the 1st to the Sunday on/after the last day of the month, so both always render as whole weeks (4–6 rows). They diverge on the question they answer.

| | `MonthGridBuilder` + `GridEvent` | `DayStateGridBuilder` + `DayState` |
|---|---|---|
| Question | "What is happening on these days?" | "Can I take these days?" |
| Model | Many date-ranged items **laid over** the grid | Exactly one state **on the cell itself** |
| Algorithm | Greedy interval row-packing into continuous multi-day bars, capped at a row limit with a `+N` overflow | None — one lookup per day, no overlap, nothing to pack |
| Partial | `partials/month_grid.html.twig` | `partials/month_day_grid.html.twig` |

`DayStateGridBuilder` was added rather than folded into `MonthGridBuilder` for two reasons. The mechanical one: merging them would produce one class with two disjoint code paths sharing only the calendar arithmetic. The load-bearing one: availability is confidentiality-sensitive in a way an event calendar is not, and putting it in the same class would leave the packing algorithm one refactor away from that path. The calendar module keeps using `MonthGridBuilder` untouched, with no regression risk from anything on the availability side.

**`DayState::STATE_OCCUPIED` deliberately cannot express *why*.** Every distinct private reason a day is taken — booked, held, manually blocked — maps onto that one state with the same label and colour, so a public visitor cannot tell them apart. `DayState::STATE_UNSELECTABLE` is kept strictly apart from it for the opposite reason: a day that is merely in the past, inside a minimum-notice window, or beyond a booking horizon is *free*, and painting it as "taken" actively misinforms a visitor into giving up on it. `DayState::STATE_DEPARTING` ("occupied in the morning, free from midday") is a first-class state rather than a later flag, because in a half-open availability model the last day of a range is pickable as the first day of the next one.

**Colour is never the sole carrier of meaning.** `DayState::$accessibleLabel` is a required constructor argument, not an optional extra — there is no way to construct a state that has a colour and no text equivalent — and the partial always renders it both as visually-hidden text and as the native tooltip. `DayStateGridBuilder::build()` likewise requires an explicit `$default` state for unmapped days, so a caller cannot leave a cell with no label by omission.

Both are generic core components: neither knows anything about calendars, rentals, or any other domain concept, and a caller maps its own objects onto `GridEvent`/`DayState`.

### 8.42 Temporary member addition (`Core\Member\TemporaryMemberSession`)

An admin (chef d'unité) searching for someone on `/admin/members` can add that member to **their own** list of animés for the lifetime of the session, from a button on the detail card (`admin/members/_detail_card.html.twig`). The point is to see the site as that member sees it, and to act on their behalf — a support tool, for the case where "it doesn't work for me" needs reproducing from the inside rather than guessing from a roster.

**Session-only, one member at a time.** `TemporaryMemberSession` stores a bare `member_years.id` under one session key. Nothing is written to the database, the value carries no personal data, and `set()` replaces whatever was there — deliberately the same shape and the same guarantees as `Core\ScoutYear\ScoutYearSession`, which it is modeled on. It is cleared on logout, from the banner's own "Retirer" control, and whenever configuration mode is deactivated.

**One injection point, not fifteen call sites.** `MemberService::getLinkedMembers()` is where the override enters, so every surface that derives from it inherits the behavior without a patch of its own: the Espace animés menu, the header identity, the offline manifest (which then opts back out, below), `StaffsController`, `FileAccessGuard`'s owner-scoping, and the gallery, groups, news, retro, calendar, mass_mail and registration modules. Patching those individually was the alternative, and it would have guaranteed drift.

`MemberService` is a Service, so it never reads `$_SESSION` itself. It asks `TemporaryMemberProviderInterface`, and the one session-aware implementation (`SessionTemporaryMemberProvider`) is wired in `public/index.php`'s composition root. The constructor parameter is **optional and trailing** for the same reason `FrontController`'s `OfflineWhitelist` is: roughly thirty other constructions — scheduled tasks, module factories, the whole test suite — pass three arguments and get the plain email-only behavior.

The provider takes an **email** rather than exposing a bare getter, and answers null for anything but the account that set the override. Several callers pass an email that is not the session's own (`GalleryAccessService::getManagedSectionIds()`, `BoardService::resolvePrincipalSectionId()`), and a temporary member must never leak into a third party's computed list. The role is re-checked on every call too, not just at activation: a session demoted mid-flight (a Desk import) stops resolving the override immediately, same posture as `ConfigurationMode::isActive()`.

**Year scoping is filtering, not purging.** A `member_years` row belongs to exactly one scout year, and `getLinkedMembers()` only injects when the row's year matches the one asked for. Previewing another year therefore hides the temporary member and switching back restores it, with no purge-on-year-change hook to keep in sync.

**The banner is the safety rail.** A temporary member takes over the header identity outright rather than going through `getHighestRoleMember()` — an animé carries no function at all, so the highest-role rule would keep showing the admin's own member and the override would be invisible exactly where it most needs to be legible. What stops that from reading as "you are logged in as this person" is the dedicated banner in `base.html.twig`: *Vous agissez au nom de X (session uniquement)*, with its own Retirer control. Deliberately **not** the configuration-mode banner, whose text ("les textes et images du site sont éditables") is about something else entirely and would bury the one fact that matters here. Activation still turns configuration mode on, and deactivating configuration mode still drops the override — the coupling is real, the wording is not shared.

**The RBAC role does not change.** The admin keeps their own role, menus and route access; only the *content* seen through `getLinkedMembers()` follows the member. This is a narrower thing than impersonation: "what this member can see" without "what this member can do to the router". It also means there is no way to lock oneself out of the removal control.

**Three deliberate widenings.** Each is a boundary this codebase had previously written down as having no chief/admin bypass, and each is now reachable while an override is active — see SECURITY.md § Temporary member addition for the accepted risk:

- `MemberService::isLinkedToMember()` answers true for the temporary member, which is what makes the member page's own photo upload (`UploadController::isUploadAuthorized()`, §8.22) reachable.
- `FileAccessGuard`'s `$linkedMemberIds` (§8.3) includes it, so the member's owner-scoped private documents are readable.
- `MemberService::canAccess()` honours it. That one matters mostly where the method is called with `'identified'` rather than the caller's real role — `MemberController::show()`'s `$isSelf` probe, which decides whether the member page renders its owner-only half at all, and `MemberEmailAddressController::requireOwnMemberId()`, which gates managing that member's secondary email addresses. Without it the other two widenings would be reachable by API but invisible in the UI.

**The offline manifest opts out.** `OfflineManifestService::excludeTemporaryMember()` drops it again, and is the one place that does. Everything else the feature touches is a live server-side decision that disappears the moment the override does; the manifest is the only consumer whose output is written to the visitor's own device and outlives the session. Caching another member's page and photo into an admin's browser, where they would stay readable after the override was removed, is a data-retention problem the rest of the feature simply does not have.

**Journal.** `temporary_member_added` and `temporary_member_removed`, both at level `security`, carrying the acting admin's `user_account_id` and the `member_year_id` — never a name, an email, or anything else identifying the member.

### 8.43 Rental module (`modules/rental`)

Renting out the unit's own assets — halls, grounds, tents, trailers, equipment. Opt-in (`enabled_by_default: false`): not every unit rents anything out.

**No `scout_year_id`, deliberately.** AGENTS.md § Database asks every member-related table to carry one "unless the data itself genuinely isn't scout-year-scoped (e.g. `calendar_events`)". This is that same exception, for the same reason: a rental is dated on a calendar, not attached to a school year. A booking from 28 August to 2 September straddles two scout years; forcing it into one makes the other year's availability calculation wrong, and the year-transition machinery would orphan live bookings every September. Retention is therefore driven by the accounting exercise instead, never by the scout year.

**Two spaces, two different role boundaries — and only one of them is the real protection.**

| | Where | `role_min` | What actually protects it |
|---|---|---|---|
| Structural configuration of the assets | `Espace chefs d'U > Locations` (`/admin/locations`) | `admin` | The route guard |
| Day-to-day operation of one asset | the asset's own managed space, `/mes-locations` | `identified` | `Service\RentalAuthorizationService` |

The managed space's `identified` floor is not an oversight. A manager is explicitly **not** required to be a chief, so the route guard grants nearly everything and the per-asset check is what stands between a logged-in visitor and someone else's bookings. It is re-run server-side on every action; a hidden "Gérer ce bien" button, an absent menu entry and a breadcrumb are presentation, never a boundary (§12).

**Why `espace_admin` and not `configuration`.** The intended audience for asset configuration is the unit chief, i.e. `admin`. The `configuration` menu's own minimum is `superadmin`, and `ModuleManifest` rejects, fail-safe, any *module* route more permissive than its menu — so a module page cannot sit there at `admin` at all. (`Core\Maintenance` appears to do exactly that, but it is a core route, not a manifest-validated one; §3 documents it as the single exception.) `espace_admin`'s minimum *is* `admin`, so that is where an admin-level module configuration page belongs, without weakening that guard for every other module.

**Authority comes from exactly two places**: Staff d'U membership (resolved through `MemberService::isUnitChief()`, never stored as a grant, so a revoked or import-suspended row can never lock a unit chief out of their own unit's assets), and an active row in `rental_asset_managers`. **ScoutMagic badges are never an ACL here.** That table points at `members.id` — the *persistent* identity, never `member_years.id`, same choice as `files.owner_member_id` — so a manager does not silently lose their assets every September.

**Archived, never deleted.** An asset with any history is archived: it leaves public view and stops taking bookings, but stays fully readable to its managers, who still have past bookings to settle. `RentalAssetService::hasHistory()` is the single gate every history-bearing table extends as later iterations add them.

**Public confidentiality is absolute, not configurable** (module spec §6.6). A public page never renders a manager's name, phone or email; the asset's emergency phone; anything about a renter or a booking; a price actually paid; a document; an access code; an internal comment. The `is_renter_contact` flag on a grant widens the audience from "internal" to "internal + this booking's renter" — it never means "public". A non-public or archived asset is a **404** for anyone who cannot manage it, never a 403: telling an anonymous visitor "this exists but you may not see it" is itself a disclosure.

**Menu entries** come from `Core\Module\MenuEntryProvider` (§7.4): the "Locations" index and one entry per pinned public asset in "Notre unité" (public, so the hook runs for an anonymous visitor too), plus "Mes locations" in "Espace animés" for an actual manager. The index page exists as soon as **any** public asset does — not only when one is pinned — because an unpinned public asset would otherwise have no menu entry and no index to be listed on, i.e. be reachable only by someone who already knew the URL.

### 8.44 Rental pricing engine (`Modules\Rental\Pricing`)

```
quantity × unit price   (quantity raised to the floor if a minimum applies)
+ fees
= total
```

That is the whole model. **There is no rule precedence, no resolution, and no rule that cancels another** — which is what makes a quote explainable to a renter line by line, and what keeps `RentalPricingEngine::quote()` a calculation rather than a resolver. Duration tiers, progressive rates, day-of-week rates, a per-person price detached from time, base + supplement beyond a threshold, and packages stacked on the unit price are all explicitly out of scope; each of them reintroduces precedence. The schema reflects this too: there is no `priority`, `rank` or `condition` column anywhere in it.

**Four configuration blocks per asset**: the billing unit; a unit-price grid on **two axes and two only** (period × renter category); a billable minimum — a floor amount **or** a floor number of people, never both (the service refuses, because storing both would need a precedence rule between them); and an ordered list of fees, each of exactly three natures.

**`BillingUnit` decides two things, not one.** Besides the quantity formula, it alone determines whether availability is counted in **nights** (half-open: the departure day frees up for the next arrival) or in **full days** (closed: the return day is still taken). The module spec is explicit that this is derived, never configured separately — letting an operator set them independently is how a calendar ends up contradicting the invoice. Each unit also carries the French sentence explaining that consequence, which is the single source of truth for the note under the selector (rendered server-side, refreshed client-side by `public/assets/js/rental-pricing.js` reading the `<option>`'s own `data-explanation`, never a second copy of the text in JavaScript).

**A meter fee never enters a quote.** Its amount is not merely unknown before the stay, it is unknowable — it comes from a real reading taken afterwards. It is listed as informational with its unit rate, excluded from the total, and settled on the final statement.

**Two deliberate asymmetries worth not "fixing"**:
- A **billable minimum in people** raises the *base* quantity but never a per-person **fee**. A tourist tax is owed on who actually slept there, not on a commercial floor.
- A **minimum amount** tops up as its **own visible line** rather than by rewriting the base line, so a renter never sees a line whose quantity × unit price does not equal its amount, and is measured **before** fees — the floor is on what renting the asset is worth, not on the invoice total.

**Purity is load-bearing.** The engine has no database, no session and no clock; `Repository\RentalPricingRepository` assembles a `PricingSettings` value object and `Service\RentalPricingService` is the only thing that touches storage. That is what lets the public page, the configuration **simulator**, the agreed price and the contract be *provably* the same code path. The simulator exists as the main guard-rail against a wrong tariff, and it can only be one if it is the same engine — so it is computed server-side through `quoteWithSettings()`, and there is deliberately no client-side re-implementation.

**`PriceQuote` is directly snapshotable**, and carries every fact its lines depend on (period, category, minimum, billing unit) rather than referencing the live configuration. That is what keeps the three amounts the spec warns never to confuse actually distinct: the **estimated** price is recomputed on demand, the **agreed** price is this object serialised at the moment of agreement and never recomputed — changing the asset's rates afterwards must not move it, and cannot, because the snapshot is self-contained — and the **final settlement** is the agreed snapshot plus real meter readings. `PriceLine::$isManual` marks a line a manager edited by hand, which is never recalculated afterwards.

Money is in **cents, as integers, everywhere**. Never a `DECIMAL`, never a float. `RentalPricingService::parseAmountToCents()` accepts the French decimal comma an operator actually types — `(float) "2,50"` is `2.0`, a tariff silently entered at a fifth of its value with nothing to notice it by.

### 8.45 Rental availability (`Modules\Rental\Availability`)

**The half-open interval.** In a **nights** model a stay from the 17th to the 20th occupies the nights of the 17th, 18th and 19th — the 20th is free again from the morning and another rental may *start* on it. In a **full-days** model the same dates occupy the 20th too, because the asset only comes back at the end of that day. Which applies is read off `BillingUnit::isNightBased()` and never configured separately (§8.44).

The case that breaks implementations, and which the module spec singles out, is **two stays that touch**: one ending on the 20th and one starting on the 20th are compatible in a nights model and in conflict in a days model. Both directions are pinned by tests, and the rule is expressed in exactly two places — `lastOccupiedDay()` for an existing stay and `daysCoveredByStay()` for a candidate one. A divergence between those two is precisely the off-by-one that double-books a departure day.

**"Occupied" cannot say why.** A booking, a temporary hold and a manual block are one `Occupancy` object with no discriminator. A public visitor cannot tell them apart because there is nothing to tell apart — structurally, rather than by a template remembering to hide it (§6.7/§6.14).

**Unavailable is not the same as unselectable.** A day inside the minimum-notice window is *free*; it is merely too late to ask for. It gets the past's greyed-out treatment and never "occupé", because a visitor told a free day is taken concludes the asset is booked and gives up on it. That separation survives only because occupancy and constraints are computed from different inputs — a `BookingConstraints` rule can never produce an occupied cell. The day-state precedence encodes it: **selected** › **outside the bookable window** › **occupied/partial** › **departing** › **free**, with the unbookable window deliberately ranked *above* occupancy so a day nobody can book discloses nothing about whether it is taken.

**The buffer extends an occupancy after its departure only** — cleaning, a caretaker's round. Extending both ends would leave twice the configured gap between two rentals, which is not what "un battement" means. A configured buffer also suppresses the "departing" state, since with a buffer there is no free-from-midday day at all and showing one would be a lie.

**Occupancy sources are pluggable** (`OccupancyProvider`): bookings and manual blocks each arrive in their own iteration and register a provider, and `Service\RentalAvailabilityService` merges the answers. Each provider is asked **once per window**, never once per day or per booking — an implementation that queried per day would turn a calendar render into forty queries and an ICS feed into hundreds.

The calculator is pure — no database, no session, and `$today` always injected.

### 8.46 Desk-import hook for modules (`Core\Import\DeskImportListener`)

A Desk import is the moment the unit's roster becomes authoritative again: whoever left simply stops appearing in the CSV. Core already reconciles its own derived state at that point (`MemberYearRepository::deactivateAllForYear()`, `MappingResolver::deactivateAllSections()`, `UnitStaffSectionService::syncMembership()`). `DeskImportListener` opens that same moment to modules holding a reference to `members.id` — a per-object permission grant, an assignment, an ownership. Same §7.4 shape as every other core hook: core defines the interface, the module implements it, `public/index.php` wires it in only when the module is enabled.

`onDeskImportCompleted(int $scoutYearId, array $activeMemberIds)` receives **ids, not rows** — a listener needs set membership, not member data, and must not be handed personal data it has no use for (`MemberYearRepository::findActiveMemberIdsForYear()`).

**Listeners run inside the import transaction**, after `syncMembership()` and before the commit. Deliberately: a roster half-applied to core but not to a module is worse than an import that failed outright and can be retried, so a listener that throws rolls the whole import back. The corollary is that a listener must stay bounded, idempotent, and free of anything unreplayable — no mail send, no HTTP call.

**The convention is deactivate, never delete**, the one core follows itself: a member missing from an import loses access, but the row recording that they had it is kept and marked inactive, so a member absent from one import (a data-entry slip, a late registration) comes back without an admin re-granting anything. `Modules\Rental\Service\RentalDeskImportListener` is the first implementation, and journals **counts only** — a quiet mass deactivation is exactly what an admin needs to notice after a botched import, while "who manages what" must not become readable as personal data in the journal (SECURITY.md §5).


### 8.47 Usage statistics — installation identity and receiver resolution (`Core\Statistics`)

ScoutMagic installations are deployed by volunteers onto shared hosting the maintainers never see. When a bug report arrives, the single most expensive question is "what is actually running over there?" — PHP version, database engine, which modules, which layout, real cron or poor-man's cron. This section is the answer to that: an aggregated, once-a-day report an installation sends to a ScoutMagic instance acting as *receiver* (§8.49), plus the identity that makes those reports attributable across days.

**It is not anonymous, and the interface says so.** The report carries the instance's own URL, because a report you cannot tie back to a site you are supporting is close to worthless. It carries no member, no section, no email, no contact name — nothing about a natural person. The Support page states this in plain French rather than claiming anonymity it does not have.

**Two identifiers, two very different storage rules.** `Core\Statistics\InstallationIdentityService` owns both:

- The **installation id** (`settings` key `statistics_installation_id`, `editable = false`) is 16 random bytes hex-encoded. It is not a credential — it travels in clear in every payload and the receiver needs it to recognise a returning sender — so a plain settings row is the right home. It is never derived from the URL, an email, or anything else about the unit: an opaque random value cannot leak what it identifies.
- The **shared secret** (`statistics_secret`) is 32 random bytes hex-encoded and lives **only** in `secrets.enc`, exactly like `github_webhook_secret` (§8.17). Never in `settings` (a row there is readable by any superadmin on the generic Paramètres page), never in the journal, never handed to a view. `getSecret()` returns `null` — rather than throwing — while `secrets.enc` does not exist yet, so the first-run installer and the payload preview can both call it safely.

Both are generated **lazily on first use**, which means two concurrent requests can reach the "not generated yet" branch at the same moment. The id is therefore claimed with a single conditional `UPDATE ... WHERE setting_value IS NULL OR setting_value = ''` (`SettingRepository::claimIfEmpty()`) and the loser of that race re-reads and **adopts the persisted value** instead of keeping the one it just generated — an installation that changed identity between two page loads would register twice on the receiver and lose its own history.

Lifecycle consequences, both intended and both a direct reading of where each value lives: a **full reset** (§8.18) truncates `settings` and deletes `secrets.enc`, so the installation comes back with a brand-new identity and re-registers on the receiver as a new site; **restoring a backup** restores both, so the identity survives.

**"Am I the receiver?" is decided on `base_url`, never on the `Host` header.** `Core\Statistics\DestinationMatcher::isReceiver()` is the single entry point, comparing the configured `base_url` setting against the configured `statistics_destination` setting. Scheme and port are ignored, comparison is case-insensitive, and `www.` is equivalent to its absence — but no other subdomain is (`stats.scoutmagic.be` is not `scoutmagic.be`), and an empty or unparseable URL matches nothing at all, including another empty one. The rule matters because the answer decides whether the receiver-only module is visible (§8.49) and whether this installation skips sending to itself: `$_SERVER['HTTP_HOST']` is attacker-supplied on every request, so deriving it from there would let a crafted request talk an ordinary installation into behaving like the receiver. It is a pure static function precisely so both entry points (`public/index.php`, `public/cron.php`) can call it before any service is wired.

**`installed_at`** (`Core\Statistics\InstallationDateService`) is the installation's date of birth, ISO 8601 UTC. A fresh install gets it written at the end of first-time setup; every installation predating the setting gets it backfilled once at boot from `MIN(event_log.logged_at)` — the closest thing to a birth certificate the database has — falling back to "now" when the journal is empty. The write is strictly conditional-on-empty, so the two paths racing each other, a re-run setup, or a thousand boots can never move the recorded date. The setting declares itself from that service rather than inline in `public/index.php`, because `SetupController` has to write it before the composition root has ever run and duplicating the French label in two files would guarantee drift.

The five settings this section introduces (`statistics_enabled`, `statistics_destination`, `statistics_installation_id`, `support_email`, `installed_at`) are all filtered out of Configuration > Paramètres' generic rendering (`SettingsController::EXCLUDED_FROM_GENERIC_PAGE`, same mechanism and same reason as the auto-update settings in §8.17): three of them are read-only facts nobody should be invited to hand-edit, and the other two only make sense next to the explanation of what actually leaves the site.

**The payload itself** (`Core\Statistics\StatisticsPayloadBuilder`, `statistics_schema_version: 1`) is a flat set of aggregates: ScoutMagic version and whether it is a dev build, the public scout year's label, active member and section counts, every module with its manifest version and enabled state, install layout, PHP version, database engine and version, OS family and CPU architecture, HTTPS, email transport and whether it is configured, scheduler mode, auto-update settings, installation and last-upgrade dates, and free disk space. Three properties are worth more than the list:

- **Unavailable is `null`, never `0`, `false` or `""`.** "This unit has no members" and "this installation could not tell us how many members it has" are different facts, and a zero standing in for the second silently corrupts every aggregate the receiver builds. Every consumer downstream — dashboard, export, KPI cards — carries the same rule.
- **Every collector is independent.** Each metric runs inside its own `try`/`catch`; one throwing sets its own field to `null` and nothing else. `build()` never throws, because a report with holes is worth far more than no report at all — and the collectors most likely to fail (disk space behind `open_basedir`, a `php_uname` disabled by the host) are also the least important ones.
- **A few field choices are security decisions, not conveniences.** `host.cpu_architecture` is `php_uname('m')` and never the bare `php_uname()`, whose full string carries the machine's hostname. `email` reports a transport name and a boolean, never a host, port, user, password or address (`MailService::getDeliveryMode()`/`isDeliveryConfigured()` exist precisely so the builder can answer without ever seeing the credentials). No module's own configuration values are included, at all.

`installation.method` prefers the canonical value `bootstrap.php` persisted in `storage/config/install-report.json` (§9.1) over any reconstruction, and falls back to the single unambiguous filesystem tell — Layout B puts an `index.php` stub next to `public/index.php` at the project root, Layout A never does. `scheduler.mode` reads `cron_last_run`, which only `public/cron.php` ever stamps (§8.24), so a stamp under 48 h old is proof a real crontab is running and its absence is proof it is not. `storage.free_disk_bytes` is knowingly imprecise on shared hosting — it measures the underlying volume, not the account's quota — and resolves to `null` whenever `disk_free_space()` fails.

Modules are sorted by id, so two builds of an unchanged installation differ only by `generated_at`; the JSON is always `JSON_PRETTY_PRINT | JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE`, which is what makes the on-page preview readable and a diff between two days meaningful. The authentication secret is absent by construction — it is never a field, and a test asserts it appears nowhere in the serialized document.

**Sending it** (`Core\Statistics\StatisticsSender`, driven by `Core\Statistics\Task\SendStatisticsHandler` — `core`/`send_statistics`, reference `daily`) is almost entirely guards. The transmission itself is one POST to `{destination}/api/statistics` with the payload as the body and the secret as an `Authorization: Bearer` header — **never** in the body — a `User-Agent` naming ScoutMagic and its version, a 10 s connect / 20 s total timeout, and `file_get_contents()` + `stream_context_create()` behind `StatisticsTransportInterface` (same precedent as `GitHubReleaseClient`; no new dependency, and every guard testable without a socket).

**HTTPS or nothing, and a public host or nothing.** A destination that does not start with `https://` is an immediate failure with an explicit reason (`insecure_destination`), never a cleartext fallback: the bearer secret rides in a header, and a downgrade hands it to anyone on the path. A destination whose host is not a real public name — `localhost`, a bare IP literal, a single-label name, a `.local`/`.test`/`.localhost`/`.invalid`/`.internal` suffix — is `non_public_destination`, and nothing is transmitted: the same rule already applied to `base_url` in guard 3, applied to where the credential actually goes. `SupportController::saveStatistics()` refuses both at save time too, with its own French message for each (they have different fixes, and reporting a scheme problem as a DNS one sends the administrator looking in the wrong place); the sender re-checks anyway, because a setting can also arrive from a restored backup, which never passes through that form. This is deliberately the structural check and **not** `Core\Security\SsrfUrlValidator`: it has to run inside a background task on every host, with no DNS lookup and nothing reaching the network from the test suite, and the destination is a superadmin-typed value rather than something a member supplies.

The guards run in this order, each producing a journaled skip:

1. `statistics_enabled` off — skipped **silently, with no journal entry at all**. A deliberate opt-out is not an event, and recording it daily would be a year of "nothing happened" per installation.
2. `base_url`'s host is not public — `localhost`, a bare IP literal (v4 or v6), a single-label name, or a `.local`/`.test`/`.localhost`/`.invalid`/`.internal` suffix — `non_public_host`. A staging clone reporting under the production installation's identity would silently corrupt the receiver's view of it.
3. This installation **is** the receiver (`DestinationMatcher::isReceiver`) — `self_destination`.
4. Maintenance in progress (D-02: a non-terminal `update_history` row, or a `pending`/`processing` `core` task among `install_update`, `restore_backup`, `full_reset`) — `maintenance_in_progress`. A database that cannot answer the question at all counts as "yes", which is the safe direction. There is deliberately **no** global maintenance mode: `InstallUpdateHandler` is itself a scheduled task, so a global gate would block itself.
5. A report already succeeded under 24 h ago — `already_sent_today`.

**There is deliberately no development-mode guard.** An installation tracking the dev channel (`auto_update_level` `'dev'`) used to be skipped outright, producing a `dev_mode` reason; it now reports like any other. Knowing what the dev channel is actually running is worth more than keeping it out of the numbers, and a build nobody reports on is exactly the one whose bug reports arrive with no idea what was installed. Nothing is hidden by reporting either: `scoutmagic.is_dev_build` and `updates.auto_update_level` are both payload fields, and the receiver buckets a dev build separately from the release of the same number (§8.50), so a dev installation shows up *as* a dev installation rather than as a release. What keeps a developer's own working copy out of the receiver was never this guard but guard 2 — a checkout lives on `localhost`, an IP, or a `.test`/`.local` name.

Only the skips that mean something is genuinely in the way (2 to 4) are surfaced on the Support page's "État des envois"; "reporting is off" and "already reported today" are the normal state of a healthy installation, and showing either as the latest problem would read as a fault.

A success never clears the failure settings — "it failed once, and here is why" stays worth reading — so "État des envois" says which of the two came last instead: a failure older than the most recent success is greyed and marked resolved. Without that, a `non_public_host` from three weeks ago sat under the heading looking like the site's current state, and the person least likely to notice is the one who already fixed it.

**Nothing is ever retried within a run, and nothing is ever caught up.** The handler reschedules itself at +86400 s in a `finally`, **whatever the outcome** — that single detail is what guarantees both "no second attempt the same day" (a receiver that is down is not hammered) and "an installation that skipped for weeks resumes by itself the moment the reason disappears". Re-enabling reporting triggers no backfill: no report is ever generated retroactively for a period spent disabled.

**Failure reasons are redacted before they are stored.** A non-2xx answer's body is genuinely the best clue about what went wrong, so a bounded slice of it is kept — but capped at 200 characters, stripped of control characters, and **scrubbed of our own secret first**, because a receiver that echoes the bearer token back in its error message must not be able to get it written into a settings row the Support page then renders. Two properties of that sanitising are load-bearing and were not free: the control-character pass is byte-oriented rather than `/u`, because a remote error body is very often not valid UTF-8 and `preg_replace()` answers `null` on such a subject (cast to string, that silently threw away the whole reason, HTTP status included); and the result is then coerced to valid UTF-8, because `JournalService` runs the context through `json_encode()`, which answers `false` on an invalid byte sequence and would turn a recorded failure into a `TypeError` escaping the daily task. The journal records `statistics_sent` (info, HTTP status and duration only), `statistics_send_failed` (warning, redacted reason), or `statistics_send_skipped` (info, reason).

The handler is registered in **both** `public/index.php` and `public/cron.php`, with the first occurrence seeded at boot (same one-time `if find() === null` pattern as the other self-rescheduling tasks). `Tests\Core\CronEntryPointTest` now pins every core handler's presence in both files — forgetting one has already caused a silently-never-running background task in production (§8.17).

### 8.48 Support package (`Core\Support`)

A diagnostic archive an administrator generates from Configuration > Support and attaches, **by hand**, to a support request. It exists because the alternative is a long email thread asking a volunteer to run commands they have no shell for.

**The contract is one-sided: a package is always produced.** Every collector (`SupportCollectorInterface`) runs inside its own `try`/`catch` in `SupportPackageService`; one that throws, lacks a permission, finds no binary, or is meaningless on this platform contributes its own line to `collection-status.json` and changes nothing else. An archive missing three diagnostics still answers most support questions — an archive that failed to generate answers none. Outcomes are `success`, `failed` (with a reason) and `unavailable` (with a reason), and `unavailable` is a genuine third state rather than a softer failure: on chrooted shared hosting several system collectors report it on every run, forever, and that is the correct answer, not a fault to investigate.

A collector sees only `SupportCollectorContext` — add a file by content or by copying a readable path, read the connection/settings/paths, declare itself unavailable, attach a note. It never touches the `ZipArchive`, never learns where the archive ends up, and never decides whether the package is produced. Archive paths are normalised (no leading slash, no `..`, no drive prefix) because a collector composing a path out of a filesystem entry it just scanned must not be able to write outside the archive's own tree.

**Three files exist in every package**, whatever else does or does not:

1. `collection-status.json` — one entry per collector attempted: name, status, concise reason, duration, notes. Reasons and notes alike are **scrubbed of every known secret first**, then stripped of control characters and capped: a PDO error naming the database password is the canonical way a credential would otherwise walk into an archive destined for email. The secrets are passed in by the caller (`SupportPackageFactory`, which owns `SecretManager`) and used only as replacement needles. **That order is the requirement, not a detail.** The needles are every value of `secrets.enc`, database and SMTP passwords included, and a password may perfectly well contain a space — normalising whitespace before substituting turns `hunter  2` in the message into `hunter 2`, which no longer matches, and the credential rides into the archive. For the same reason the normalisation is byte-oriented rather than `/u`, and its result is coerced to valid UTF-8: a latin-1 driver error made `json_encode()` answer `false`, and the cast that followed emptied the entire status file — every other collector's outcome with it.
2. `README.txt` — French, explaining that the archive was generated locally, what it is for, what it contains, that **nothing was transmitted automatically**, that its contents must be checked before sending, the configured support address, and the full warning about PHP configuration, server logs and filesystem diagnostics.
3. `statistics.json` — byte-for-byte the payload of §8.47, at generation time, **even when reporting is disabled**. A unit declining automatic telemetry says nothing about whether they want the same facts in an archive they are attaching themselves.

**Generation is a background task** (`core`/`generate_support_package`, scheduled at +0 s by the controller, exactly like `create_backup` in §8.15): the system collectors shell out, walk the filesystem and read logs, none of which belongs inside a page load. `requested_by_user_account_id` (§8.16) names the requester so the handler can notify them (`core.support_package_ready`), and the page polls `GET /api/support/package-status/{id}` — the scheduled action's own id and status, the same shape as `backup-status`/`update-status`.

**The archive is the most sensitive artefact this codebase produces on demand**, and its storage says so: written under `storage/core/support/`, **encrypted at rest** via `Core\File\EncryptedFileStorageService`, registered as a `FileRecord` with `role_min: 'superadmin'`, served only through `/files/{id}` (which already decrypts transparently for an encrypted record). **Exactly one is ever kept** — generating replaces the previous file *and* its `FileRecord` — and `core`/`purge_support_packages` (daily, self-rescheduling) deletes it seven days after generation whether or not anyone downloaded it. Which package exists and when it was made are two `settings` rows rather than a table, since a table would hold at most one row; the generation stamp lives there rather than being read off `files.created_at` because the retention rule is this feature's own. `storage/**` is already gitignored wholesale, so the new subdirectory needed no `.gitignore` change — verified, not assumed (SECURITY.md §12).

**Nothing is ever transmitted, in any form**: no email, no upload, no pre-filled `mailto:` with an attachment. The button generates, the link downloads, and the administrator decides what happens next.

**The application collectors** (§8.48's first four beyond `statistics.json`) each answer one recurring support question:

- `database-structure.sql` — every table's `CREATE TABLE` and **not one row of data**, through `DatabaseDumper::dumpStructure()` rather than any hand-rolled dump. A schema mismatch is among the most common causes of a bug that reproduces on exactly one installation, and answering it needs the structure and nothing else; exporting rows would turn a diagnostic attachment into a data export. Where no dump can run at all (a non-MySQL driver, an unreachable server) the collector reports `unavailable`, and a test asserts the output never contains an `INSERT`.
- `configuration-parameters.xlsx` — one row per `settings` entry with the current value next to its declared default and an explicit "differs from default" flag, usually the fastest way to see what a unit changed. **Redaction keys on `setting_type = 'secret'`**, never on a list of suspicious-looking key names: a keyword list is guaranteed to miss the next secret somebody adds and to redact something harmless meanwhile, while declaring the type at registration cannot. The key and label stay visible (knowing a secret is *set* is itself diagnostic); only the value becomes `[REDACTED]`. Nothing outside `settings` is read at all, so `secrets.enc` and the encrypted credential columns (`llm_providers.api_key`, the telephony credentials) cannot leak through this file even by accident.
- `event-journal.xlsx` — the last 48 hours of `event_log`, one column per real column of the model. 48 h is the window in which "it broke this morning" is still true, and a structured sheet beats a text dump because the first thing anyone does with a journal is sort and filter it. The journal holds no personal data by construction (SECURITY.md §11) but does carry source IPs and internal ids — precisely what the README's warning is about.
- `scheduled-tasks.xlsx` — one row per **declared handler**, with the last instance that ran and the next one pending. The unit of interest is the handler, not the row: `scheduled_actions` is a queue of instances, so a task that has never run has no row at all, and "this task has never run once" is exactly the answer this sheet exists to give. There is deliberately no cadence and no enabled/disabled column (neither concept exists in this scheduler) and no full execution history.

Every textual cell in the three spreadsheets is written with an explicit string data type, so a value beginning with `=`, `+`, `-` or `@` can never be evaluated as a live formula when a maintainer opens the file (SECURITY.md §23). Free text that could quote a credential — a task's `last_error`, a collector's failure reason — goes through `SupportCollectorContext::redact()`, one implementation shared by every consumer.

Core handlers are enumerated from `Core\Scheduler\CoreTaskHandlers`, a single declarative list that `public/index.php` and `public/cron.php` both register from. That list exists as much for the entry points as for this sheet: hand-maintaining two copies is exactly how `create_backup` once ended up missing from `cron.php`, silently failing every background backup under a real crontab (§8.17), and `Tests\Core\CronEntryPointTest` now fails if either file goes back to its own copy.

**The system collectors** are all best effort, and several will report `unavailable` on every single run on chrooted shared hosting. That is the expected answer, not a fault:

- `phpinfo.html` — `phpinfo(INFO_ALL & ~INFO_VARIABLES & ~INFO_ENVIRONMENT)`. `INFO_VARIABLES` prints `$_SERVER`/`$_ENV`/`$_COOKIE`, which here means the still-valid session cookie of the superadmin who just clicked "generate". **`INFO_ENVIRONMENT` has to be excluded too, and that is the part worth spelling out**: "PHP Variables" (the superglobals) and "Environment" (what `getenv()` sees) are two separate phpinfo sections behind two separate flags, so masking only the first still ships the host's environment credentials — API tokens, proxy credentials, platform-injected database passwords — into an archive destined for email. A test asserts both are gone, against a real `phpinfo()` run rather than against the constant's name. Everything else is kept unredacted, deliberately: guessing which ini directive might be sensitive would strip something diagnostic and still miss something. That is what the warning on the Support page and in the README is for.
- `filesystem.txt` — type, permissions, owner, group, size, mtime and link target, with deliberately uneven depth: `storage/` in full (where real permission problems live), the project root at its first level, `core/`/`modules/`/`public/`/`schema/`/`config/` at depth 2, and `vendor/` **not walked at all** — only presence and top-level entry count, since a full listing there is tens of thousands of lines that answer nothing. Pure PHP, never `ls`: shelling out adds nothing and is blocked on exactly the hosts where this matters most. Symlinks are listed but never followed, so a link into `/` can't turn this into a whole-disk scan. "In full" is bounded at 5 000 entries with the truncation stated in the file and as a note: `storage/` is also where every uploaded photo and every generated variant lives, and a unit with an active gallery would otherwise spend one `lstat()` and two passwd lookups per entry building a string large enough to exhaust `memory_limit` — producing no archive at all, which is the one outcome this feature does not allow.
- `commands.txt` — availability, resolved path and version for every external command **the code actually shells out to**: `ffmpeg`/`ffprobe` (gallery video) and `gs`/`qpdf`/`pdftocairo` (`PdfCompressor`'s three backends). `mysqldump` and `mysql` are deliberately absent: both dumping and restoring are pure PHP over PDO now (§8.15.1), precisely because those binaries proved unusable on the production host, so probing them would report on something the application never calls. A host where no shell-execution function is callable says so once, up front, rather than as five identical errors.
- `webserver/` — every `.htaccess` in the install, plus a short list of server-config candidates copied only if readable. The `.htaccess` files are the point: they are the only web-server configuration always present on this project's target hosting, and they are exactly what breaks in Layout B (§9.1). There is **no platform-aware Apache/Nginx discovery**: on chrooted hosting every such path is unreadable in principle, so discovery machinery would report "unavailable" forever.
- `logs/` — one generic collector over a candidate list (`ini_get('error_log')`, `storage/logs/*`, sibling and home-level `logs/` directories), each file bounded to the last 48 hours and hard-capped per file, with truncation reported in `collection-status.json` rather than applied silently. **The per-file cap is not on its own a bound**: a shared host's `~/logs` routinely holds one rotated access and error log per domain per day, so the collection as a whole is capped too — 25 files and 8 MB, with every candidate it did not copy named in `logs/summary.txt` and a note saying how many. `logs/summary.txt` is a reserved name, since a host log file called `summary.txt` would otherwise be copied there and then overwritten by the summary itself. A line whose timestamp cannot be parsed is **kept**: log formats vary far too much to treat "no date here" as "old", and dropping a stack trace's continuation lines would mangle exactly the entries worth reading. **No process or service snapshot is ever taken.**

### 8.49 Statistics receiver module (`modules/support_dashboard`)

The other end of §8.47: one ScoutMagic installation acts as the receiver, collects every other installation's daily report, and shows them on a dashboard. The working name "GLOBAL STATISTICS" appears nowhere — the module is `support_dashboard`, "Tableau de bord support".

**`receiver_only` — a manifest field, not a deployment trick.** A module declaring `"receiver_only": true` is filtered out of `ModuleManager::discoverModules()` unless the installation *is* the receiver, which the composition root resolves once via `DestinationMatcher::isReceiver(base_url, statistics_destination)` (§8.51) and passes in as a plain boolean — `ModuleManager` has no business knowing what a statistics destination is. Filtering at that single point makes routes, menu entries, the module-registry page and the scheduler all follow automatically. The alternative — excluding the module from the release artifact — breaks on the first update that re-adds it.

**A declared scheduled task is not a queued one.** `ModuleManager` reads a manifest's `scheduled_tasks` only to teach `SchedulerRunner` which class handles which key; it never writes a row into `scheduled_actions`. Every recurring task in this codebase reschedules itself at the end of its own run, so a task whose *first* occurrence is not seeded in `public/index.php` reschedules itself never and simply does not exist. All three of this module's tasks are seeded there, in one loop, and `Tests\Modules\SupportDashboard\ModuleSchedulingTest` fails if that list ever drifts from `module.json` again — it had already drifted, and `purge_installations` (§8.50's retention) and `finalize_monthly_aggregate` (all of §8.51) had consequently never run once on any receiver.

This masking is **ergonomic, not a security boundary**, and saying so matters: the real protection is that a module which is never loaded registers no routes at all. The field is typed strictly (`"receiver_only": "false"`, a truthy string, is a load-time error) because the failure mode of getting it wrong is a module that silently does not exist anywhere, which is close to undebuggable. One accepted consequence: if `base_url` changes on an installation where the module was enabled, its `module_registry` row survives while its routes disappear. That is the intended behaviour — nothing "cleans up".

**`POST /api/statistics`** (`role_min: 'public'`) is the intake endpoint, and **the second deliberate CSRF exception in the codebase** after `POST /api/webhook/github` — same reasoning, documented in SECURITY.md §4: the caller is a machine with no session, so there is no session-bound token to carry and CSRF is not the threat. Authentication is a bearer secret, and the order of the checks is as much of the design as the checks themselves:

1. **HTTPS or refuse.** The bearer secret is in a header.
2. **Body size, on the raw string, before parsing.** 64 KB against a ~2 KB payload is a decade of headroom; a 1 MB body costs a `strlen()`, not a JSON decode.
3. **Per-IP rate limit**, 10/hour against a client that reports once a day. The counter stores the address's **blind index only**, never the address — same rule and same table shape as `human_check_rate_limits` (SECURITY.md §16), with its own daily purge task.
4. **Bearer token present**, then **structural validation**, then authentication.

**Trust on first use.** An unknown `installation_id` is a first registration: the presented secret is stored as `password_hash()` and every later report must `password_verify()` against it. That is the only model available — the sender generates its own identity with nobody to vouch for it — and it bounds the exposure precisely: an attacker can register a fake installation (noise in a dashboard, deletable) but can never take over a real one. **The secret is never stored in clear anywhere**: not in a column, not in the journal, not in a response, and a test asserts all three.

**Unknown fields are never a reason to reject.** A sender one version ahead must keep working, so an unrecognised field is kept verbatim in the stored raw JSON, warned about in the journal, and ignored for processing. The *warning* is bounded — 20 names, 64 characters each, then a count of what it left out — because those names are a stranger's text and a 64 KB body can carry thousands of them; the journal entry exists to say "somebody is ahead of us", not to mirror an arbitrary document into `event_log`. Missing optional fields are stored as `NULL` — never `0`, never `false` — and every denormalised column is replaced on each report, including with `NULL`, so a sender that stops being able to measure something stops reporting it rather than freezing its last known value. The denormalised columns exist purely so the dashboard can filter, sort and search without parsing JSON.

**A denormalised column is narrower than JSON is, and the difference is a fault line.** `INT UNSIGNED` refuses a negative counter and anything past 4 294 967 295; `DATETIME` refuses a year outside 1000–9999, which `DateTimeImmutable` parses perfectly happily. Under strict mode either one turns `{"active_members": -1}` into a `PDOException` escaping a `public` route whose entire contract is to answer a status code — so out-of-range is resolved to `NULL`, the same "not reported" a missing field gets. `instance_url` gets the same treatment for a different reason: it is the one field the dashboard turns into a link, and `javascript:…` is a perfectly valid string that Twig's HTML escaping does nothing about, so anything that is not `http://` or `https://` is stored as `NULL` (§8.50). None of these is a rejection — the URL is one optional field among twenty, and the untouched value survives in the raw JSON either way.

**One state per installation, no daily history.** Each accepted report overwrites the previous one.

A rejection is journaled as `statistics_report_rejected` (`warning`) **with the source IP and a reason category** — the one place the spec asks for the raw address, because an intake endpoint under abuse is unreadable without it — and the reason is always a fixed category, never free text and never an echo of the payload. Acceptance is `statistics_report_received` (`info`, or `warning` when unknown fields were present). The response is a bare 204 with no body: a caller learns the status code and nothing else, and an unknown installation is indistinguishable from a wrong secret. There is deliberately **no IP blocklist and no abuse-flag machinery** — out of scope.

Neither the instance URL nor the installation id is personal data (a scout unit is an association, not a natural person), and both are needed in clear to filter and search, so both are stored as plain columns — justified in SECURITY.md rather than left as an unexplained exception.

### 8.50 Support dashboard, current state (`/support-dashboard`)

The consultation half of §8.49: `role_min: 'superadmin'`, menu `configuration`, one row per installation retained by the receiver.

**No view state is ever persisted.** Filters, free search, sort and page live in the query string and nowhere else — no cookie, no local storage, no session, no per-user preference row. Two reasons, and the first is the real one: a support dashboard that silently reopens on a filter somebody set three weeks ago shows a confidently wrong picture to whoever looks next, and the person least likely to notice is the one who did not set it. The second is a pleasant side effect — a page that stores nothing on the device adds nothing to the cookie registry and needs no consent category. Arriving at `/support-dashboard` with no query string always produces the same default view: **active installations only**, most recently received first.

**Filtering, sorting, paging and every aggregate happen in PHP, over the whole retained set — never split with SQL.** One of the required filters is "does this installation have module X enabled", and the module list lives inside the stored JSON payload; expressing that in SQL means `JSON_CONTAINS`, which is MySQL-only and would leave the filter untestable. More importantly, the five indicator cards and both charts have to be recomputed **on the filtered set**: doing the filter in SQL and the aggregates in PHP is exactly how a table and its own counters end up disagreeing with each other. The population is scout units in one federation — dozens, plausibly a few hundred — so loading them all costs a few hundred kilobytes. If that ever grows by an order of magnitude, the fix is to denormalise the module list into its own table and move the *whole* pipeline into SQL, not to split it.

**An absent value stays absent, everywhere.** `NULL` means "not reported", and it is rendered "Non renseigné" — never `0`, never "Non", never "Désactivé". It is excluded from a total rather than added as zero (a total over entirely unreported values is itself `null`, not `0`), excluded from the auto-update percentage rather than counted as off, and it always sorts **last in both directions** — burying an unknown at the bottom of a descending sort would be the same lie as showing it as zero. This is a rule about the whole dashboard, not a formatting preference: the receiver's data comes from installations of differing versions, so "this sender could not measure it" is a permanent, first-class state.

**Filter values in the URL are technical keys, never the French labels the page renders.** The auto-update filter travels as `disabled`/`patch`/`minor`/`major`, and the label is produced once at the edge. A URL is not a translation artefact, and a filter keyed on displayed text breaks the day the wording is improved.

The table is responsive by tier rather than by squeezing every metric into a column: URL, version/build and last upgrade on mobile; status and last reception on tablet; active members, installation method and auto-update on desktop; active sections on very wide. Clicking a row opens a dialog whose body is **fetched and rendered server-side by Twig**, carrying every available metric plus the exact raw JSON of the last accepted report — including fields this receiver does not understand. Nothing on the page assembles markup from a remote installation's values client-side: those values are untrusted text, and Twig's autoescaping is a stronger guarantee than an escaper written in the page's own script (SECURITY.md §28).

**"Version / build" means both words.** The bucket a row falls into is the reported version plus `(dev)` when `is_dev_build` came back true — `1.0.33` and `1.0.33 (dev)` are two slices, two filter options and two export values, because a dev build is whatever the branch happened to contain that day and answering a support question as though it were the release answers it wrongly. An unreported `is_dev_build` is not thereby a release: the suffix is added only on a reported `true`.

**The instance URL is printed always and linked only when it is a link.** The value arrives from an unauthenticated stranger, and Twig's HTML escaping has nothing to say about a `javascript:` or `data:` scheme; the intake refuses those outright (§8.49), and the dashboard hydrates a separate `instance_url_href` that is null unless the scheme is `http`/`https`, so a row written before that rule existed still renders as text rather than as a link a superadmin can click. The nonce CSP would block the script either way — that is a mitigation, not a reason to store or render the value as a URL.

Exactly **five indicator cards** and exactly **two charts** (version/build distribution, auto-update mode distribution), both on the vendored Chart.js. The restraint is deliberate and is part of the specification, not an unfinished state: every other breakdown the payload would allow — by module, by installation method, by PHP version, by database engine, by OS, by HTTPS, by cron mode — is explicitly out of scope. A dashboard nobody can read at a glance answers no support question.

**Active, stale, deleted — three states, two settings.** `support_active_threshold_days` (default 14) decides *active* from *stale*: an installation is active while its last accepted report is newer than that. Stale is a display state only — the row stays, reachable through the status filter — because "we have not heard from them in three weeks" is a support fact worth seeing, not a reason to forget them. `support_retention_months` (default 6) decides when the record goes, **in its entirety**: installation id, instance URL, last payload, reception metadata and the credential hash, removed by the daily `purge_installations` task or by a superadmin acting sooner (confirmation dialog, CSRF-protected, journaled as a count and a row id — never a URL or an installation id). Both settings are read through one service method that refuses a zero, negative or blank value and falls back to the declared default: a threshold of zero would mark the whole fleet stale, and a retention of zero would empty the table on the next purge.

One consequence is accepted rather than engineered around: an installation silent past the retention window that starts reporting again is a **new registration**, because its id is no longer known and trust-on-first-use applies afresh (§8.49). That is the honest description of what the receiver knows about it.

**Finalised monthly aggregates are never rewritten by a deletion**, whether automatic or manual (§8.51). An aggregate counts the distinct installations that reported in a month that has ended; editing it because a contributor later disappeared would make the whole series mean nothing.

**The XLSX export is of the filtered set, not the page.** Same query string as the table, handed straight through, so the file is reproducible from its own URL — exporting the twenty-five rows currently on screen is how a pagination accident becomes a silently truncated deliverable. It carries **one column per defined metric**, not per visible column: the responsive table hides most metrics below `xxl` and a spreadsheet has no such constraint. Three things are deliberately absent — the raw JSON payload (the wrong home for it, and exactly where an unvetted field from a newer sender would arrive), any contact email (there is none in a report, and a column named for one would imply otherwise), and any derived "days since last report" (stale the moment the file is saved, when the timestamp and the status are both already there). Missing values are written as the same "Non renseigné" the page shows, in every column, never `0` and never `Non`. Every cell is written as an explicit string, like every other export in this codebase (SECURITY.md §23).

### 8.51 Support dashboard, monthly history (`support_monthly_aggregates`)

The receiver keeps **one state per installation** and no daily history (§8.49). That is the right trade for support work — you want to know what is running now — but it leaves one question unanswerable: is ScoutMagic being used by more units than last year, or fewer? This section answers exactly that, and nothing else.

**One number per calendar month: how many distinct installations reported at least once.** Several reports from one installation in one month are one contribution, and the uniqueness is enforced by a unique index on `(month, installation_id)` rather than by a read-then-write in PHP, which two concurrent reports would interleave past.

**Two tables, and the second one is the point.** `support_monthly_contributions` is a *working* table: it exists so distinct contributors can be counted before the month closes, and its rows for a month are **deleted at finalisation**. That delete is not housekeeping — it is what makes "a finalised aggregate contains no individual identifier" true of the data on disk rather than merely of the queries that happen to read it. `support_monthly_aggregates` holds the month, the count, and the finalisation timestamp: no installation id, no URL, nothing that names anyone.

**Finalisation is daily, and closes every month that has ended.** `support_dashboard`/`finalize_monthly_aggregate` finalises every eligible month rather than "last month", which is what makes catch-up free: a receiver left idle for a quarter closes all three on its next run, in order, with no special path and nothing to trigger by hand. The current month is never finalised — it can still gain contributors, and an aggregate is immutable once written, so closing early would freeze half a month as if it were the whole one.

**A finalised aggregate is immutable and kept indefinitely.** Nothing rewrites one: not retention, not a manual deletion, not an installation that disappears (§8.50), and there is deliberately **no user-facing recompute or regeneration** anywhere. An installation that contributed to March contributed to March; a history that gets rewritten when a contributor later vanishes is a history that means nothing, and the only honest way to guarantee that is to have no code path that can do it.

**One chart, and it is independent of everything above it.** The history section takes only its own period — 6, 12, 24 months or everything, defaulting to 12, in the query string and not persisted between visits like every other piece of view state here. It is built by a separate service method taking a separate type, so the independence is structural rather than declarative: a history that moved when somebody typed in the search box would be answering a different question than the one its axis claims, and a test pins it. No second historical chart is added — active members over time, version distribution over time, auto-update share over time and module adoption over time are all explicitly out of scope.

### 8.52 Rental bookings, the public request and the renter's tracking page (`Modules\Rental\Booking`)

**The renter never has an account, and never will.** Everything below follows from that.

**Possession of the tracking token *is* the authorisation.** `bin2hex(random_bytes(32))`, stored only as a `password_hash()`, handed to the renter once in the acknowledgement email and never rendered anywhere else. Three rules are absolute: it is verified before anything is loaded, **"no such booking" and "wrong token" answer identically** (a differing answer turns `/locations/suivi/{id}/{token}` into an oracle for which references exist), and it is never written to a log, a journal entry or a manager's email. It cannot be recovered — only regenerated, which invalidates the old one. The booking id is right there in the URL and bookings are numbered 1, 2, 3…, so the token is the *only* thing standing between a stranger and a renter's identity; the IDOR is pinned by tests in both directions.

**Every renter field is an encrypted `BLOB`**, decrypted in exactly one place (`Repository\RentalBookingRepository`) — name, email, phone, organisation, purpose, comment. The email additionally carries a blind index (`rental_renter_email`) so an exact-match lookup is possible without decrypting the table. A booking reaches the journal by **reference and id only**; a name or an address there would be a second, unprotected copy of what the table encrypts (SECURITY.md §5).

**The managers' notification carries no renter identity at all** — a reference and a link to the page that shows the detail behind a real permission check. An inbox is not a place to scatter copies of personal data, and a manager is one click away from the protected view. Each manager is mailed separately rather than through a shared `To`/`Bcc`: one manager's address must not be disclosed to the others by the header, and one bad address must not sink the batch.

**Two emails that cannot be switched off** (§6.28): the renter's acknowledgement, because it carries their only way back to their booking, and the managers' notification, because without it a request can sit unread indefinitely. Neither takes an `enabled` flag. Both are sent *after* the booking is committed and each is guarded independently — a delivery failure must never throw away a stored request.

**Every subject carries the reference first** (`[LOC-2027-0042] …`) and every outgoing message a `Message-ID` we generate and record ourselves. That is what later lets a reply be threaded back onto the right booking through `In-Reply-To`/`References` rather than guessed from the sender (§7.6). An id the MTA invented is an id we never saw, and cannot match a reply against; the local part is random and never derived from the booking, so a threaded reply cannot be forged from a guessed id.

**References come from a forward-only counter** (`rental_reference_sequences`), never from a `MAX()` over the surviving bookings. A booking deleted by mistake — or purged on schedule once retention lands — would otherwise free its number, and two different rentals would end up quoting the same reference to two different renters. The year is the year the request was *made* in, so a 2027 request for a 2028 camp stays a 2027 reference. The `UNIQUE` constraint on the column is the backstop against a genuine race.

**One hold mechanism, two meanings.** A single deadline (`hold_until`) and a single origin (`hold_origin`). An **automatic** hold is created by the request itself and is short (48 h by default, configurable, `0` disables it); when it lapses the dates are released and the request simply goes back to waiting — nobody promised anything, so nothing is refused. A **manager** option was promised with a deadline, so lapsing makes the booking `expired`. To the public the two are indistinguishable, because `Occupancy` has no discriminator to distinguish them by (§8.45).

**Availability never waits for the expiry task.** A lapsed hold is one whose deadline has passed, and the calculator reads the deadline directly — an asset is free the moment the hold expires, not the next time cron runs. `Task\ExpireRentalHoldsHandler` tidies the stored state; it is not what makes the dates available. That matters on shared hosting, where "hourly" can mean several hours late. It self-reschedules like every other recurring task (`Core\Scheduler` has no recurring-task concept), and the split between `handle()`'s unconditional `scheduleAfter()` and `bootstrap()`'s guarded one is load-bearing: `SchedulerRunner` marks a task done only *after* `handle()` returns, so a guarded reschedule inside `handle()` would find its own still-`pending` row, skip, and end the chain after one run.

**"In progress" is derived, never stored** — a confirmed booking whose dates contain today. A stored flag would need somebody to move it and would eventually disagree with the calendar.

**The submitted form is re-validated server-side, against live state.** Dates, booking rules, capacity and availability are all recomputed at submission: the calendar the visitor saw may be minutes old, another request may have taken the dates since, and a hand-crafted POST must not book four hundred people into a hall for forty. `Core\Security\HumanCheck` gates the form (never an external captcha) and is skipped for an identified session; CSRF is checked before anything else. A rejection re-renders the form with everything the visitor typed — never a dead-end error page — under one generic message that never says which barrier tripped.

**Both tick-boxes are recorded with a version *and* a hash of the exact text shown** (§6.13), so what was agreed stays provable after the wording is reworked. The version is derived from the text itself rather than being a number somebody must remember to bump: a version that only moves when a human remembers is wrong exactly when it matters. The privacy box is deliberately **not** framed as consent — the processing is necessary to the booking, and calling it consent would misrepresent the legal basis.

**The estimated price is snapshotted at submission**, as a self-contained `PriceQuote` (§8.44). It is the record of what the visitor was actually shown, and a later tariff change must not rewrite it.

**What the tracking page never shows**: internal comments, notes on a damage still being assessed, any downloadable file. What it does show is the full live price breakdown, the asset's emergency phone, and the contact details of **only** the managers flagged `is_renter_contact` — a filter applied in SQL rather than left to the template, because a template that forgot the condition would hand every manager's details to an external renter.

### 8.53 Operating a rental (`Modules\Rental\Service\RentalOperationsService`)

The managed space (§6.4, §6.5): what a manager does with a booking after it arrives. Separate from `RentalBookingService`, which is about a booking coming into existence and about feeding the availability calculator — this is the larger half of the module's rules, and keeping the two apart is what stops either from being half-applied.

**Its routes are `identified`, and that is not the protection.** A manager is explicitly not required to be a chief (§6.3), so the route guard grants almost nothing and `RentalAuthorizationService` is re-checked at the top of every action. An asset the visitor may not manage answers **404, never 403**: "this exists but is not yours" is itself a disclosure (§6.6). Bookings are numbered across the whole installation and the id is in the URL, so every booking is additionally checked to belong to the asset in the path — without that, a manager of one asset could read every booking of every other by walking the ids.

**The lifecycle lives in one table** (`Booking\BookingTransition`), not in an `if` per action. A lifecycle scattered across controller actions is one where "may a cancelled booking be confirmed?" has a different answer depending on which button was pressed. Two rules shape it: a final state is final — reopening one would silently re-take a period that may since have been let to somebody else, so the way back is a new request — and confirmation may only follow a state where somebody actually looked at the booking. Cancellation is available from every live state including `confirmed`, and computes no refund: §6.17 is explicit that there is no automatic scale.

**Confirmation re-checks availability inside the same transaction as the write**, under a row lock on the asset's bookings, followed by a compare-and-set on the status. That closes two ordinary failures on a shared hall: two managers confirming two different requests for the same week, and three bookings of five tents against a stock of twelve. The booking excludes **itself** from the check — it already holds its own dates.

**`Occupancy::$isFirm` is the one distinction that survives into availability**, and it is never a public one. A pending request holds its dates against visitors, but it is not a commitment, so it must not stop a manager confirming a competing request for the same week — arbitrating between two requests is exactly what confirming one *is*, and if a soft hold blocked it, neither could ever be accepted. Confirmed bookings, closed ones and manual blocks are commitments and do stop it. Only the confirmation path and the accept-a-date-change path pass `firmOnly: true`; every public surface sees all occupancies and cannot tell them apart.

**A hand-edited price line is never recalculated again** (§6.12). `Pricing\QuoteEditor` is pure, like the engine, and `merge()` is where the rule lives: re-quoting rebuilds the automatic lines from the live tariff and carries the manual ones across exactly as they were. A manager who negotiated 300 € for a week and then corrects the arrival date must not find their 300 € replaced by the grid's answer. Typing an amount drops that line's unit price, so a line never shows arithmetic that does not work; a discount is added as its own visible negative line rather than by shaving the base. Re-quoting is **never automatic** — it is a decision with a visible consequence, since the renter sees the new total immediately — and the total is always recomputed from the lines, never carried across.

The edited quote is stored as `agreed_price_snapshot`, a **second column** beside the estimate. The estimate stays frozen as the record of what the visitor was shown at submission; the agreed one is what the renter is actually asked to pay. `effectivePrice()` picks whichever is in force so the manager's view and the tracking page can never show different figures.

**Change requests and proposals are one table, both directions** (§6.16). They are the same object seen from two ends: somebody proposes different dates, a different head count, or an end to the booking, and somebody else decides. **Nobody decides their own** — a renter's request is decided by a manager, a manager's proposal by the renter from their tracking page — which is what makes "une demande ne modifie jamais silencieusement la réservation" structurally true rather than a rule to remember. Deciding is a compare-and-set on `status = 'pending'`, so two managers on two screens cannot both accept the same request. Contact-detail corrections are deliberately *not* a change request: correcting a phone number is not a negotiation.

**Internal comments never cross the boundary.** They are encrypted at rest even though managers write them — a comment about a booking is in practice a comment about the people making it — and the renter's tracking page **does not load the table at all**, which is stronger than a template remembering to hide it. The per-booking history is the opposite: plain text, because nothing written to it is ever about the renter. The two are protected differently because they carry different things.

**The per-booking history is not the audit journal.** `Core\Journal` answers "what happened on this site", is admin-facing, and is purged on its own retention schedule; `rental_booking_events` answers "what happened to this rental" and lives as long as the booking. A manager needs the second without being handed the first.

**A manual block over an already-booked period is accepted** (§6.18) — it must neither fail silently nor overwrite the booking, because a caretaker away during a rental is a real thing to record. The two coexist: availability adds them up and the private calendar shows both. What the manager gets instead of a refusal is a warning naming how many bookings overlap, so an accidental overlap is visible rather than hidden. Blocks are their own table rather than bookings with a special status: a block has no renter, no price, no lifecycle and no email, and forcing it into `rental_bookings` would put a nullable renter on every row.

**The milestone checklist is derived, never stored** (§6.15). Every line is computed from the booking's own state, so it can never drift from the status and no scheduled task has to keep them in step. Milestones belonging to iterations that have not landed — contract, deposit, meters, inventories, settlement — render as *not applicable* rather than unticked: an unreachable unticked box reads as outstanding work and would make the whole checklist noise.

**The private calendar pages into the past, the public one does not.** `Availability\MonthWindow` is the single place that clamping lives, with a floor that is zero for visitors (§6.7) and two years for managers, because half a manager's work is about stays that already happened. Clamping is server-side: the month is a query parameter, and a hidden arrow is not a boundary (§12).

### 8.54 Rental payments (`Modules\Rental\Service\RentalPaymentService`)

The **only** place `rental` touches money (§6.19, §6.20). Everything goes through Finance's four public interfaces (§7.5) and never near its tables — there is deliberately no foreign key from a rental row to a Finance one, because a constraint would make `rental` unusable without `finance`.

**All four dependencies are nullable, and that is the feature.** With Finance disabled — or simply not installed — every method degrades to "no receivable, no QR, nothing raised", the configuration section explains itself instead of offering an empty account picker, and the booking's payment panel says so in one sentence. A unit that settles its rentals by hand is a perfectly normal unit and must not meet a single error page. The tests cover that path as its own set, not as an afterthought.

**One receivable for the whole rental.** The deposit is a **threshold** on it — "deposit received" is `amount_received >= deposit_amount`, compared live, never a stored flag that would spend part of its life disagreeing with the bank statement — and the deposit and the balance share one structured communication. Two receivables would mean two communications, and a renter paying the balance with the deposit's reference would settle the wrong one. Raising receivables is idempotent: called again it moves the amount in place rather than minting a second communication, which would orphan every transfer already made.

**The security deposit is a different debt**: its own receivable, its own communication (so a renter transferring it cannot accidentally settle part of the rental), and **never rental revenue** — a unit holding 500 € of somebody else's money has not earned 500 €. Its **return is recorded by hand**, deliberately: Finance reconciles incoming transfers and not outgoing ones, so no bank statement can confirm it. That limitation is documented on the screen rather than papered over with a feature that would only look like it worked. The resulting status is derived from the amounts rather than picked from a dropdown, and withholding any part of it requires a written reason — the renter is entitled to know why, and six months later nobody remembers. The reason is encrypted like every other field written about a renter.

**`ExpectedReceivableInterface::updateReceivableAmount()`** is the generic extension this iteration adds to Finance (roadmap §Itération 6). Nothing in its signature names a module: the same call serves a renegotiated rental price, an amended order, or anything later. It keeps the communication — deleting and recreating would orphan the payer's transfers — and **refuses to drop below what has already come in** unless the caller passes `allowBelowReceived`. Silently producing an overpayment is how a refund nobody knows about happens: the receivable reads "paid", the surplus sits on the account, and nothing anywhere says somebody is owed money. With the flag, the caller has stated it knows.

Receivables are raised **at confirmation**, which is when the unit actually expects to be paid, and a Finance failure there is journaled rather than thrown: the confirmation has committed and the manager has been told it worked, so undoing it would be a worse lie than a rental whose payment panel plainly shows no receivable yet. A price change pushes the new total onto the existing receivable; a refusal ("this would drop below what came in") is likewise journaled, because the price change itself is legitimate and what is left is a situation a manager has to look at, not a reason to reject their edit.

### 8.55 Rental documents, contracts and invoices (`Modules\Rental\Document`)

**Three levels, each frozen the moment the next is born** (§6.25). The asset's template lives in `editable_contents`; the booking takes its **own copy** at the first generation (`rental_booking_document_texts`); the PDF is a rendering of that copy at one instant (`rental_documents` + a `files` row). The middle level is the one that earns its keep: a template reworded in March must not silently change what a renter agreed to in February, and editing one booking's copy must not touch another's.

**A generated document is never overwritten.** Regenerating produces v2 beside v1, because v1 may already have been sent, printed and signed — and a signature refers to a text, not to a file name. The version comes from a **forward-only counter** on the booking's own copy, never `MAX(version)` over the surviving documents: deleting v2 must not make the next generation v2 again, exactly the same reasoning (and the same shape) as `rental_reference_sequences` for booking references. The values a version was rendered from are frozen beside it, so "why does v1 say 467,50 € when the booking says 400,00 €?" still has an answer six months later.

**Substitution happens after sanitizing, and every value is escaped** (`Document\DocumentKeywords`). The other order would run the sanitizer over renter-supplied content and let it decide whether that content should have been markup. dompdf renders HTML, and these values come from a form an anonymous visitor filled in — a renter's name or organisation containing `<`, `&` or a quote is not exotic, it is Tuesday. The keyword list is **closed**: a template can say exactly these things and nothing else, and anything else it asks for is reported to its author **at edit time** rather than surviving into a signed contract as literal braces. An unknown keyword is left visible rather than blanked — a contract showing `{{ prix_ttc }}` is obviously wrong to whoever reads it, a silently emptied one reads as a clause that says nothing.

The editors are **plain HTML textareas, not the rich-text modal**, and that is deliberate: a contenteditable surface happily splits a run of text across elements as it is edited, so `{{ prix_total }}` can silently become `{{ pri<b>x</b>_total }}` — still readable to a human, no longer a keyword to the substituter, and only noticed once a contract goes out with braces in it.

**`is_for_renter` is an email flag, not an access right** (§6.24, §6.26). An external renter downloads nothing from this site: they have no account, and the tracking token is a capability for *their own page*, not a file credential. Their contract and invoice reach them by email and only by email; a lost email is resent by a manager, which is why resending is a first-class action. Wiring the token into file access would be a new exception to SECURITY.md §6 for the sake of saving one click, and there is a test asserting the tracking page carries no download link at all.

What does protect the files is the ordinary mechanism: `File\RentalDocumentOwnershipChecker` in `Core\File\FileAccessGuard`'s `owner_type` registry (§8.3/§7.4), resolving file → booking → asset and answering "may this person manage it?" through `RentalAuthorizationService`. The file's own `role_min` is `identified`, which alone would let any logged-in visitor at every contract in the unit; there is no role bypass, so a chief with no grant is refused like anyone else, and a file whose booking is gone is refused because there is nobody left to check against.

**Rendering reuses dompdf** through a new `Core\Pdf\DocumentPdfService` — no new PDF dependency. It is a sibling of `PosterPdfService` rather than a replacement: a poster is one page built around a QR code and deliberately truncates its title and body, which is exactly wrong for a document whose whole point is to say everything it says. The caller owns the sanitizing, which is why the service's docblock says so in as many words.

**No VAT is ever computed** (§6.27). Prices are what the renter pays. A unit letting a hall is not a VAT-registered business in the general case, and a module that computed VAT would be quietly wrong for almost every installation. What an invoice carries instead is a configurable exemption sentence, because a Belgian invoice with no VAT on it has to say why. The renter's billing identity — legal name, address, country, VAT and enterprise numbers, a buyer reference — is collected **when it becomes relevant**, not on the public request form: a visitor asking about a weekend has no reason to type a VAT number, and asking for one up front loses requests. It is encrypted at rest like the rest of their identity, and the field set is chosen with Peppol in mind without implementing it, so adding e-invoicing later is a new exporter rather than a migration.

### 8.56 The stay: meters, inventory and the final settlement (`Modules\Rental\Stay`)

**Meter readings are integers, in thousandths of a unit.** A meter index is not money, but it has money's problem: 1234.567 kWh in a float, differenced against another float and multiplied by a unit price, is how a bill ends up a cent off in a way nobody can reproduce. The subtraction is exact and the single rounding happens at the end, turning consumption into cents. Input accepts the French decimal comma like every other numeric field here — `(float) "1234,567"` is `1234.0`, a reading silently short by more than half a unit.

**A meter that reads backwards is reported, never guessed at.** An index that went down means a replaced meter, a transposed digit, or a reading taken at the wrong end; every one of those is for a human to look at, and taking an absolute value would bill a renter for a typo. The same posture covers a missing reading: the line contributes nothing and says why.

**The inventory checklist is snapshotted into the booking at confirmation** (§6.23), label and all. Editing the asset's checklist afterwards changes no existing inventory — an item renamed from "chaises" to "chaises (x40)" in June would otherwise rewrite what was checked in March, and a deleted one would erase a finding. The snapshot is guarded by a flag rather than by "are there rows?": an asset with an empty checklist snapshots legitimately into zero rows, and re-snapshotting would overwrite a completed inventory with blanks. `InventoryState::NOT_CHECKED` is a real state, distinct from `OK` — "nobody looked" and "somebody looked and it was fine" are different facts, and conflating them is how a missing set of keys becomes nobody's fault.

**The financial decision on a damage stays human**, everywhere. An incident is recorded as `PENDING` and enters nothing until a manager picks charge, withhold or waive. `PENDING` is also what keeps an assessment in progress off the renter's page (§6.26): they would read a proposed figure as a demand. Incident descriptions are encrypted — they are written about what a renter's group did — while meter comments and inventory notes stay plain, being about a device and a piece of furniture; that is the same rule, and the same responsibility on the interface, as `rental_blocks.reason`.

**The settlement never modifies the agreed price.** `Stay\SettlementCalculator` takes the agreed quote as an input and returns new lines, which the service writes to a different table — the separation is structural, not a rule to remember. The two answer different questions ("what did we agree?" and "what does it come to now?"), and letting the second overwrite the first would destroy the evidence for exactly the disputes it exists to settle. Only **per-person** lines are re-scaled to the head count that actually turned up: a group that announced forty and brought twenty-eight pays a tourist tax on twenty-eight, and the hall still costs what renting the hall costs — the same asymmetry §6.10 already draws for the billable minimum. A hand-edited line is never re-scaled, for the same reason §6.12 forbids re-quoting one.

**A settlement version is immutable once validated**, and versions come from a forward-only counter on the booking — never `MAX(version)` over the surviving rows, since a deleted v2 must not make the next settlement v2 again. Validation is a compare-and-set on `is_validated = 0`, so a second validation is refused rather than silently re-stamping a document somebody may already have acted on. Correcting a validated settlement means a new version beside it. The balance is **signed**: an overpayment is a real outcome, and flooring it at zero is how a refund nobody knows about happens.

**None of these pages is ever cached for offline use** (§6.23). The module declares no `offline` section at all, so nothing is whitelisted — and a manifest test pins that, because these are *write* pages and the offline layer caches reads. A cached inventory form would let a manager fill it in in a cellar with no signal and lose the lot on the way home. The workaround is documented on the page itself: photograph on site, type it up on return. Photo uploads go through `UploadHandler` with an images-only MIME list, which matters more here than anywhere else in the module — a phone photograph taken inside somebody's rented hall carries GPS coordinates, and `UploadHandler` strips them.

### 8.57 Publishing rental occupancy onto the calendar (`Modules\Rental\Calendar`)

**Nothing is ever written to `calendar_events`.** Occupancy is computed from the bookings on every generation (`RentalVirtualEventProvider`, the §7.6 pattern), so the booking stays the single source of truth and the two can never disagree. A copied event would survive a cancellation, a date change and the deletion of the booking itself; a computed one cannot. Turning publication off for an asset removes its occupancy from the calendar with no cleanup pass and no orphans.

**The privacy rule is not configurable, and it is applied before anything is serialised.** An ordinary reader — member, parent, anonymous visitor — gets `Local Saint-Georges — loué` and nothing else, deliberately indistinguishable in kind from a manual block (`— indisponible`), since why the unit cannot let its hall is nobody else's business (§6.7). Only a manager of *that* asset, or the Staff d'U, gets the organisation, the head count, the contact and the management link. That distinction lives in two separate builders rather than one builder with a flag, precisely so no "detailed version" object exists for a template, a JSON payload, a tooltip or an ICS line to leak — and the tests assert on what is absent from the object, not on what a template happened to render. Manager rights are re-resolved on every generation, so a revoked grant stops showing the detail on the next fetch rather than on the next token rotation.

**Per asset, two settings and no more**: which calendar to publish onto, and whether occupancy appears from confirmation or already from the hold. Publishing from the hold tells the unit's own people the hall is spoken for while a request is still being negotiated; publishing from confirmation keeps a request that may yet lapse off everyone's calendar. A lapsed hold stops being published by itself — the setting is evaluated against the booking's current state, never stamped onto it.

**A cancelled booking is published as cancelled, never omitted.** `STATUS:CANCELLED` with a bumped `SEQUENCE` is what makes a subscriber's client remove it; dropping it from the feed leaves it in their calendar forever. The one exception is a request refused before it was ever published — announcing its cancellation would announce its existence.

**The renter's own feed enriches nothing and duplicates nothing.** It is a one-event calendar served by the tracking token (`RenterFeedBuilder`), carrying dates, asset, and the contacts the unit chose to expose — never a price. It shares the booking's UID with the calendar's own rendering, so a renter who is somehow subscribed to both ends up with one event. For the unit's own people there is likewise **no second personal feed**: `PersonalFeedService` gained virtual events on the existing one, because two feeds would mean two links to subscribe to and two chances to hold the same booking twice.

**Both directions of the circularity degrade on their own** and are tested that way (`Tests\Modules\Rental\Calendar\RentalCalendarWiringTest`): with `calendar` off the registry is null, no provider is built, the per-asset publication form is not offered and the renter's ICS link is not shown; with `rental` off the registry simply has one fewer entry and every calendar feed is an ordinary, complete `VCALENDAR`.

### 8.58 Inbound mail, a read-only gateway (`Modules\InboundMail`)

**It is not a mail client, and the interface it offers has no vocabulary for becoming one.** `Client\IncomingMailboxClientInterface` declares `connect`, `disconnect`, `listFolders`, `folderState` and `fetchSince` — no `markSeen`, no `move`, no `delete`, no `createFolder`. Bodies are fetched with `FT_PEEK` and folders opened with `EXAMINE` rather than `SELECT`, so reading a message neither marks it `\Seen` nor sets `\Recent`. A unit whose treasurer works through an unread inbox must not find it quietly emptied by a background task, and the guarantee is pinned two ways: the contract has no write method, and a source-level test asserts the IMAP implementation contains none of the calls that would (`Tests\Modules\InboundMail\Client\NonIntrusiveReadTest`).

**Nothing unclaimed is ever written down, and the cursor moves past it anyway.** The sync loop offers each message to every registered consumer (`Api\MessageConsumerInterface`, the §7.6 pattern again — a mutable `Service\MessageConsumerRegistry` this module owns and each consumer's block appends to). A message nobody recognises is discarded: not stored, not queued, not notified. Keeping it "in case" would build an archive of the unit's mailbox with no screen to consult it, which is the worst possible position under the RGPD. But the cursor still advances on the UID that was seen, because otherwise one unrecognised newsletter at the top of a box is fetched, parsed and discarded on every run forever and nothing behind it is ever read.

**This module knows nothing about any consumer**, and a test asserts it: no `Modules\Rental` in its code, and no idea what a booking reference looks like. The claiming logic — reference in the subject, then thread headers, then a bounded sender match — lives in the consumer, because only the consumer can know it.

**A UID means nothing without its folder's UIDVALIDITY.** A server that renumbers a folder (restore, migration) announces it by changing that value; a cursor remembering only "last UID 4212" would then skip every message below the new 4212 and lose weeks of mail. The pair is stored, a change resets the UID to zero, and re-reading is safe because deduplication is on Message-ID within the mailbox — a message already held is recognised whatever UID it now carries. Runs are batched, so a first sync of a five-year-old mailbox does not die halfway through a request that a shared host's `max_execution_time` kills, leaving the cursor unmoved and the identical doomed attempt repeating forever.

**Configuration is superadmin and nothing else**, every route of it. A Staff d'U may *use* a configured mailbox through a consuming module's workflow but never learns the host, the account or anything that would let them reach it directly — `Mailbox::publicSummary()` is the whole of what leaves that boundary. The password lives on a separate `MailboxCredentials` object that the repository loads only when a client is about to connect, so it is structurally absent from every listing, template variable and rendered stack trace; a blank password field on save means "keep the stored one", never "clear it", since the page cannot show an operator what they would be retyping. A failure is recorded as a sentence written by `Service\MailboxErrorFormatter`, never a library's own exception text — that routinely carries the account name and the server's verbatim rejection of the credential just tried. **An invalid certificate fails the connection**, and there is no configuration path to an unencrypted session or to skipping the check.

**Everything arriving is untrusted.** HTML is sanitised once on the way in and stored sanitised — the sender's original is never written anywhere, because sanitising on render means every future template, export and API response has to remember to. **Remote images are removed rather than proxied**: a 1×1 image in a stranger's email is a read receipt, proxying still fetches it, and there is no size at which loading a remote image stops telling the sender when a manager opened their message. Attachments go through `UploadHandler` — real type sniffed from the bytes, never what the email claimed; a strict allowlist with no archives; a generated stored name; EXIF stripped; outside `public/`; `FileAccessGuard` in front. Signature logos are filtered by `Content-Disposition: inline` plus a referenced Content-ID first (cheapest and most reliable), then by a **pixel** threshold rather than a byte one — a blank 1200×800 PNG compresses to less than an ornate 100×100 banner, so weight says nothing.

**The inter-module API is scoped to one consumer and one business reference on every call** (`Api\InboundMailInterface`). There is no `findAll()`, no `findByMailbox()` and no `search()`, and that absence is the enforcement: a manager who may open a booking must not thereby gain a window onto the unit's whole mailbox. Detaching deletes rather than orphaning, since there is no unattached queue for a message to fall into. What this module cannot check is whether the *user* may reach the reference — only the consumer knows its own authorisation rules, so that check stays in the consumer's controller and the interface says so.

**Gmail connects over IMAP with an app password, deliberately.** A native connector would need Google's `gmail.readonly` scope, which is *restricted*: every unit deploying ScoutMagic would owe an annual paid security assessment, and without it their tokens expire every seven days and their sync breaks weekly. `Mailbox\ProviderType` keeps the abstraction so a native connector could be added later; it is not implemented.

**The polling task is the one module task registered by hand** rather than auto-resolved from its manifest, because it needs the consumer registry and only a composition root can build one — in `public/index.php` **and** `public/cron.php` both. A handler registered in only one of the two fails unconditionally under the other with "No handler registered" (§8.17/§8.20), so a test pins both call sites.

### 8.59 A booking's correspondence (`Modules\Rental\Mail`)

**`rental` claims its own mail; `inbound_mail` has no idea what a booking
is.** The consumer (`Mail\RentalMessageConsumer`) is registered into that
module's registry from the composition root, and everything about *which*
booking a message belongs to lives on this side of the boundary — §8.58's
module knows how to read a mailbox and nothing else.

**The matching order goes from certain to plausible and stops at the first
answer:**

1. **A reference in the subject** (`[LOC-2027-0042]`) — the module put it
   there itself, so a reply carrying it back is as close to certain as
   automatic attachment gets. Bracketed beats bare, and the subject beats
   the body, because a body is full of quoted history. **Two different
   references means no match**: a renter forwarding one booking's email
   while asking about another leaves both in the text.
2. **The thread headers** — `In-Reply-To`/`References` naming a message
   already attached. Resolved through `InboundMailInterface`, scoped to this
   consumer, because `rental` cannot look inside the other module's storage.
   The reference still wins when both point, since a thread can be hijacked
   by replying to an old email about a different booking.
3. **The sender's address, bounded by time** — the renter's own address
   *and* a message falling between the request and some weeks after the
   departure. Neither half works alone: without the address this attaches
   anything, without the window it attaches next summer's enquiry to last
   summer's stay.

**Ambiguity is answered with silence.** Two bookings matching the sender
inside the window attaches nothing at all — a manager reading the wrong file
has no way to know it is the wrong file, which makes a wrong attachment
worse than none.

**An attachment becomes a `Non classé`, internal document of the booking**,
pointing at the very file `UploadHandler` stored rather than a copy. Never
presumed to be the signed contract (that would put an unverified PDF where a
signed contract goes) and never "for the renter" (that flag queues it to be
emailed back to them). `RentalDocumentService::reclassify()` is the one-click
correction, and it refuses generated documents: a contract or invoice is what
the module produced from a template, and renaming one would break the
versioning a signed v1 depends on.

**Correcting the automatic rules is bounded by what the manager manages.**
Detaching deletes the message *and the attachments nobody re-classified* —
one already filed as a signed contract survives, an untouched `Non classé`
goes with it. Moving is offered only to bookings of that manager's own
assets, and the target list is **built from their assets** rather than
filtered from a global list, so the picker is never itself a window onto the
unit's other bookings; a hand-crafted POST naming somebody else's booking
gets the same "not accessible" as one naming a booking that does not exist.
A moved message takes its documents with it, since `FileAccessGuard` resolves
a rental file's readers through its document row.

**There is no way to attach a message by hand**, anywhere. Attaching is what
the rules do; a button that opened the mailbox would be a doorway onto
everybody's correspondence, which is the whole thing §7.11's scoped API
exists to prevent.

**Which mailboxes feed the module is a rental setting, and a manager sees a
name and a state.** Never a host, a port or an account: `listMailboxSummaries()`
is the whole of what crosses that boundary. **Empty means every mailbox** —
most units have one, and asking them to tick it before anything works would
be a configuration step whose only sensible answer is "yes" and whose
omission would look exactly like a broken sync.

**Without `inbound_mail` the booking page loses a tab and nothing else.**
`RentalCommunicationService` takes the API as a nullable dependency and
answers as though no message ever arrived, which is exactly true.

## 9. Installation / bootstrap

### 9.1 First install: bootstrap.php

FTP is used exactly once: the operator uploads a single self-contained `bootstrap/bootstrap.php` to an empty web folder and opens it in a browser. It has no Composer dependency (it must run before `vendor/` exists) and never touches `Core\Maintenance\BackupService`, `InstallUpdateHandler`, `RestoreBackupHandler`, or `FileAccessGuard` — it is their first-run twin, not a rewrite of them: same `VERSION` format (`Core\Maintenance\VersionFile`), same archive-root handling as `InstallUpdateHandler::resolveBranchArchiveRoot()` (decided from source type, never entry count), same "no new dependency" constraint.

It resolves the latest published GitHub release (hardcoded repo, never read from the request), picks one of two supported layouts, runs an 11-step POST-driven install (the browser drives a short poll loop — a single long request would time out on shared hosting), then a full acceptance gate, then writes `token.php` and deletes itself.

**Layout A — "Natural" (preferred)**: the document root sits inside a writable parent directory. The artifact's `public/` contents are merged directly into the document root; everything else (`core/`, `modules/`, `storage/`, `vendor/`, `schema/`, `config/`) goes into the parent. The result is the exact project tree in §12, with the document root simply *being* `public/`.

**Layout B — "Single-tree" (fallback)**: used whenever the parent isn't writable, doesn't physically contain the document root (chrooted/symlinked hosting), or looks like a filesystem root. The entire artifact is installed into the document root, and exactly one root `.htaccess` (never per-directory deny files — those miss module `storage/<name>/` folders created long after install, and get overwritten by every update since they'd live inside the artifact) denies `storage/|core/|modules/|config/|schema/|vendor/|tests/|scripts/` and dotfiles — gated on the request actually resolving to a real file/directory (`-f`/`-d`), since `config` also doubles as the app's own admin route namespace (`/config/maintenance`, `/config/notifications`, …); an earlier ungated version of this rule 403'd every one of those routes outright. Static assets under `public/` are rewritten across directories to be served directly (no PHP involved, so no risk); PHP execution is never rewritten across directories — instead `bootstrap.php` writes one small `index.php` stub directly in the document root (`require __DIR__ . '/public/index.php';`) and the `.htaccess` routes everything else to that same-directory file. A same-directory PHP rewrite is the one universally-supported case across Apache + PHP-FPM/FastCGI configurations; rewriting PHP execution straight across a directory boundary (an earlier version of this file did exactly that, in a two-hop chain through `public/`'s own `.htaccess`) is a well-documented trap on some hosts, where `SCRIPT_FILENAME` is computed from the request's original path rather than the rewritten target and the request fails with a raw "File not found." from PHP-FPM even though the target file genuinely exists. The `.htaccess` also forces `DirectoryIndex index.php` explicitly: some hosts (observed on OVH-style mutualized hosting) ship a placeholder page and configure their own vhost-level `DirectoryIndex` to list it ahead of `index.php`, and `mod_dir`'s directory-index resolution for the bare `/` request can win against this `.htaccess`'s own rewrite rules depending on the host's Apache module hook ordering — without the explicit override, the host's placeholder gets served instead of the site.

Either way, no code elsewhere in the codebase is aware of which layout is in use — `dirname(__DIR__)` from `public/index.php` resolves to the same project root in both cases by construction. The one narrow exception is the token-gate check in `SetupController`, which tries the two fixed candidate locations for `token.php` itself (see §9.2) — not a general path-resolution abstraction.

**Acceptance gate**: before the wizard is reachable, `bootstrap.php` runs server-side checks (`VERSION`, `vendor/autoload.php`, `schema/core.sql`, `storage/` subdirectories and permissions, no `.htaccess` shipped in the artifact, temp dir cleaned up) and has the *browser itself* fetch a set of canary files it just wrote (a positive control, `token.php` executing as PHP rather than being served as source, `storage/keys/`, a `storage/` subdirectory created moments earlier, `vendor/autoload.php`, a docroot dotfile, no `storage/` directory listing) to prove what's and isn't web-reachable — trusting the browser's report is deliberate here, the same precedent `MaintenanceController::installUpdate()` sets for accepting client-observed results server-side, and it's safe because only the operator running the install can forge the verdict and doing so grants no privilege. Any failure rolls back the entire installed tree — not just the failing piece — and no `token.php` is ever written. Full report also saved to `storage/config/install-report.json` on success.

### 9.2 Setup wizard token gate

Until `secrets.enc` exists, `/setup` (`Core\Http\Controller\SetupController`) is gated behind `token.php`, which `bootstrap.php` writes to the document root only after its acceptance gate fully passes. `SetupController` never generates a token itself: if `token.php` is missing, it refuses and displays the exact file content to create over FTP; if present, it compares a submitted value against the file's own content via `hash_equals()`, with session-based progressive lockout (there is no database yet at this point, so `Core\Security\LoginThrottler`'s DB-backed pattern doesn't apply) escalating to a hard stop after ~10 attempts. On successful completion of first-time setup, `token.php` is deleted; a persistent journal entry (and a flash message) warns the operator if deletion fails, since leaving it in place is an unnecessary — though not by itself exploitable — risk.

Collects DB credentials, unit settings (including short name ≤5 chars), email config, initial admin email. Once `secrets.enc` exists, `/setup` reverts to being a normal `superadmin` Configuration page under `RbacGuard`, unchanged — the token gate never applies again.

## 10. Database schema management

No incremental migration files. `schema/core.sql` + each module's `schema.sql` = source of truth. `MigrationRunner` compares and generates DDL — this diff never drops a column/table it finds in the database but is no longer declared (data-loss safety net), it only warns. The one narrow exception: a sibling `drops.sql` next to a schema file (e.g. `schema/drops.sql`) can declare reviewed `ALTER TABLE <table> DROP COLUMN <column>;` statements — `MigrationRunner::applyExplicitDrops()` runs each only while the column still exists, so it's idempotent and safe on every request. Still not incremental: once applied everywhere, delete the line from `drops.sql`.

`migrate()` is chunked and resumable, not one uninterruptible pass — a lesson from a real production incident: the previous all-at-once design (full backup, then introspect+diff+execute every table in one go) could take longer than the host's `max_execution_time` on a large schema change, which killed the request *before* the schema hash was saved, so the identically expensive pass repeated on every subsequent request forever (the site fell over, effectively DoS-ing itself). `migrate()` now does at most `$timeBudgetSeconds` (constructor param, default 20s) of work per call: it checkpoints after every unit of work — the one-off backup attempt, building the table queue, each table's diff, each generated DDL statement's execution — persisting a lean `MigrationProgress` (table names and SQL strings only, never full introspected structures) as JSON in the same internal `settings` mechanism the schema hash itself uses. Hitting the time budget returns `MigrationResult::$complete = false` *without* saving the hash, so the next `migrate()` call for the same schema files resumes from exactly the persisted checkpoint instead of restarting; a schema file changing again mid-attempt (a new content hash) discards the stale progress rather than trying to resume toward a target that no longer exists. A caller that treats "the operation finished" as final (`Task\InstallUpdateHandler`, `Task\RestoreBackupHandler`, `Module\ModuleManager`) must check `$complete` before doing so — none of them bump their own "done" bookkeeping (`update_history.status`, module registry version, etc.) until it's true, otherwise an incomplete migration would be permanently stranded (nothing would ever call `migrate()` for it again). The two background handlers instead reschedule themselves (`SchedulerService::scheduleAfter(..., 0, ...)`) to resume on the next scheduler tick when incomplete.

Concurrent callers are serialized with a MySQL/MariaDB advisory lock (`GET_LOCK('scoutmagic_schema_migration', 0)`, non-blocking — a caller that doesn't get it immediately just reports "not done yet" rather than doing redundant/racing work); it degrades to no mutual exclusion when `GET_LOCK()` isn't available (this class's local orchestration tests run against SQLite), which is safe there since those tests never call `migrate()` concurrently.

`migrate()` still runs against the whole live schema (no separate deploy step triggers it) so re-introspecting it just to conclude "nothing to do" would be wasted work on every page load between real schema changes — it short-circuits entirely when a SHA-256 hash of the schema file(s) + sibling `drops.sql` matches a hash cached from the last fully-completed, warning-free run (`MigrationRunner::isPending()` exposes just this cheap check, no lock, no work, for a caller that only needs to know whether a migration is outstanding at all). The cache is only written once `$complete` is true and zero statements failed, so a crash or partial failure never gets masked — the next request just resumes (or re-checks in full, if nothing had been checkpointed yet).

**Migration-in-progress page** (`public/index.php` bootstrap, right where `migrate()` used to run inline on every request): when `isPending()` is true, no page is routed normally and no migration work happens inline. A request to `POST /api/system/migration-step` runs exactly one short (5s) `migrate()` chunk and returns `{complete, progress}` as JSON; any other request instead gets a small, self-contained HTML page (inline CSS/JS, no external asset dependency, so it never depends on the rest of the app being routable) showing a progress bar (`MigrationResult::$progressFraction`, a rough four-phase — backup/diff/execute/drops — weighted estimate) whose script calls that endpoint in a fast loop until `complete: true`, then reloads. Closing the tab is safe: the next visitor (or the same one returning later) resumes from whatever `MigrationProgress` was last checkpointed, thanks to the mechanism above — this page is purely a foreground driver for the same resumable `migrate()`, not a separate migration path.

First-time setup also exposes migration directly: the setup wizard's database step runs the real migration itself (`SetupController::installDatabase()`, `POST /setup/install-database`) rather than deferring it to the final form submission, so a slow first schema creation (35+ statements from scratch) gets its own visible step instead of being bundled invisibly into "Installer" — `handleFirstTimeSetup()` still calls `migrate()` itself too, as a defensive no-op safety net, made cheap by the same cache. A fresh install's first schema creation is comfortably inside the default time budget in practice (a single `CREATE TABLE` per declared table, no per-table introspection needed since nothing exists yet), so `SetupController`'s call sites don't need to handle `$complete === false` specially.

## 13. Code conventions

- Namespace PSR-4: `Core\` → `core/`, `Modules\<ModuleName>\` → `modules/<module_name>/src/`.
- **All code, comments, variable names, table names, column names, commits, PRs: English.**
- **All UI text (labels, messages, Twig content): French.**
- Controller: reads request → calls Service → picks view. No SQL, no business logic.
- Service: never accesses `$_SESSION`/`$_POST` directly.
- Repository: only layer that touches PDO. Prepared statements only.
- View: never calls Repository or Service.
- Compiled Twig templates are cached per installed version (`storage/temp/twig_cache/{version}`, `Core\View\TwigFactory::cacheDirectory()`). Outside debug mode `auto_reload` is off and Twig keys its cache by template *name*, not contents, so a flat directory would keep serving a pre-deployment compiled class forever — the version namespace is what makes a deployment pick up changed templates on its first request, with no cache-clearing step. The one case it doesn't cover, by design: hand-editing a `.twig` file in place without changing `VERSION` (use debug mode for that).

## 14. What Devin must never do

- Call `RbacGuard` from a controller instead of letting the Router do it.
- Write a route in a `module.json` without `role_min`.
- Put business logic or SQL in a Controller or View.
- Duplicate core functionality in a module (auth, session, encryption, journal, mail, scheduler, cookie consent).
- Create an incremental migration file — update the module's `schema.sql`.
- Modify `schema/core.sql` for a module-specific need.
- Write custom CSS that duplicates a Bootstrap component.
- Introduce a frontend build tool (a bundler, a Sass compiler, a transpiler — anything that turns `public/assets/` into a build output). Node-based *test* tooling is not that, and is allowed: see §1 and §15.
- Store personal data in `VARCHAR` — use `BLOB` via `EncryptionService`.
- Write `WHERE` on an encrypted field — use blind index.
- Put personal data in logs, journal, or error messages.
- Link to a file with a direct path — use `file_url(id)`.
- Store uploaded files under `public/`.
- Write a module's own log table — use `JournalService`.
- Use French in code/comments/table names.
- Use English in UI text.
- Set a non-essential cookie without checking `CookieConsentService::isAllowed()`.
- Submit code without corresponding automated tests.

## 15. Tests

Three complementary, independently-runnable automated test stacks:

- **PHPUnit** (`tests/`, mirroring the structure of `core/` and `modules/`) — the server-side test suite: Services, Repositories (against a test database), Controllers/routes (including the RBAC boundary at every `role_min`), and the rest of the PHP application. Five suites, all of them run by a bare `vendor/bin/phpunit`: `Core`, `Modules`, `Bootstrap`, `Security` (`tests/Security/` — the source-level audits AGENTS.md § Security checklist leans on: SQL injection, encryption of personal data, file access, upload MIME trust, response headers, POST size limits) and `Integration` (`tests/Integration/` — scenarios spanning several services at once). **A directory absent from `phpunit.xml` is a suite that does not run**: `Security` and `Integration` existed for a long time without being listed, so eight files silently stopped being executed and drifted; anything added under `tests/` must be reachable from a `<testsuite>` or it is decoration.
- **Vitest + jsdom** (`tests/js/`) — isolated unit tests for first-party browser JavaScript (`public/assets/js/`), run under Node with a simulated DOM (jsdom): no PHP server, no MySQL, no real network. `fetch`, the Service Worker, WebAuthn, etc. are mocked where a script under test touches them. These are development/test tooling only (§1) — they exercise the real production `.js` files directly, never a reimplementation of their logic, and exist to catch regressions in deterministic, DOM-adjacent frontend logic (form validation, client-side computed state) fast and without a browser.
- **Playwright + headless Chromium** (`tests/e2e/`) — end-to-end tests against a real, running ScoutMagic. One canonical command, `npm run e2e` (`scripts/e2e.sh`), provisions a throwaway install (its own `storage/`, its own generated secrets, its own empty database migrated from `schema/core.sql` by the real `Core\Database\MigrationRunner`, and **every** module activated through the real `Core\Module\ModuleManager::activate()` — the instance points its statistics destination at itself, so even the receiver-only module is visible and wired), serves it with `php -S` over the **real** `public/index.php`, drives it with a real browser, and tears all of it down — on success, on failure, and on Ctrl-C. It answers the one question the other two stacks structurally cannot: *does the application boot at all?* PHPUnit instantiates controllers directly and never executes the composition root in `public/index.php`, which is exactly how a `TypeError` on every request once reached production (see AGENTS.md § Static analysis). Every module is activated at provisioning time for the same reason: that composition root wires each enabled module before routing anything, so a module left off is a block of it no scenario executes — and the second time that `TypeError` reached production, it was in a module the harness did not enable. `all-modules-enabled.spec.js` asserts the invariant against the real Modules page, so a module added later is covered the day it lands. Deliberately kept to a very small number of high-value scenarios: this is a merge-blocking CI check and a release gate (`scripts/release.sh`), so determinism matters far more than coverage. Assertions are semantic (ARIA roles, accessible names, the document title) wherever a role or a name identifies the element; the few places where none does fall back to the ids and classes the module's own JavaScript binds to — a contract rather than incidental structure — and say so in the spec that does it. Two scenarios go further than "does it boot". `scout-year-transition.spec.js` replays the whole scout-year changeover — preview, Desk import, staff year, public switch — against the workflow described on `/admin/scout-year`, which is its specification and carries a reminder to that effect (as does `ScoutYearController::buildTransitionSteps()`, where the step wording lives). `groups-discussion.spec.js` writes in a discussion group — a message, a message carrying a link, a poll and a vote, a comment, a reaction, and then a second member commenting so the first is told something is new and can report it, a phone-sized viewport with `groups.js` blocked (the only check anywhere that this module's standing "everything still works with no JavaScript" promise holds), and a comment whose whole content is a photo, previewed before it is sent — because the groups composer is the one place where the BROWSER decides what the server receives: `public/assets/js/groups.js` intercepts the form's submit and hand-builds the request body, so neither PHPUnit (a `$_POST` array the test wrote) nor Vitest (a jsdom form with no server behind it) can see whether that body still carries what the form declares. Three defects lived in exactly that gap and were found by adding the scenario. It needs the super-admin to have a member identity and a name on the account, both hard requirements of `Modules\Groups\Service\GroupAccessService`, which `scripts/e2e-support.php` provisions (`e2e_seed_member_for_admin()`) rather than bypasses — plus a second ordinary member and a section both belong to, since a comment is never new to whoever wrote it and reporting is never offered on your own message; because that fixture is bound to the current scout year, the scenario must run before `scout-year-transition.spec.js` moves the public year — Playwright's alphabetical file ordering is what guarantees it. The harness drops `storage/temp/twig_cache` at provisioning, and `tests/bootstrap.php` does the same for PHPUnit: `TwigFactory` keys compiled templates on VERSION alone with `auto_reload` off whenever `debug` is false — right for production, where an install upgrades by version, and wrong for a checkout that edits templates all day, where it makes both suites assert against a template that is no longer on disk (`Tests\Bootstrap\TwigCacheFreshnessTest` is the guard that keeps the drop happening). Optionally, the run also reports PHP line coverage: with `E2E_COVERAGE=1`, pcov collects inside the `php -S` process through an `auto_prepend_file` (`scripts/e2e-coverage-prepend.php`, one fragment per request) and `scripts/e2e-support.php merge-coverage` folds the fragments into `coverage-e2e.xml`, which SonarQube Cloud merges with PHPUnit's report — the only coverage `public/index.php` ever gets. Canonical documentation: README.md § Tests de bout en bout.

Frontend unit tests are a complement to, never a replacement for, PHPUnit's integration tests or the manual mobile (~375px) and desktop (~1280px) visual verification every page/component still requires — they mock the server/browser boundary precisely so they can run in isolation, which is also exactly why they can't substitute for either of those two.

A fourth, non-test mechanism runs alongside these three: JavaScript static analysis (`npm run typecheck`, TypeScript's `checkJs` over `public/assets/js/`, no build step — see `AGENTS.md` § Static analysis and README.md § Analyse statique JavaScript) is the JavaScript equivalent of `vendor/bin/phpstan analyse` — it catches unresolved identifiers, wrong argument counts, and statically-detectable invalid property access *before* any test runs, which is a different guarantee than Vitest exercising behavior at runtime.

Automated tests are mandatory for every feature and must be kept up to date as the codebase evolves. The RBAC guard must have explicit test coverage on every role boundary.
